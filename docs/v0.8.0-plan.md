# native-theme v0.8.0 — Implementation Plan

**Status:** Proposed; pairs with [v0.8.0-spec.md](v0.8.0-spec.md). An implementing session needs this file and the spec sections its task names, not `docs/v0.8.0-rationale.md`.
**Branch:** `v0.8.0` (from `main` at `v0.7.2`). `v0.8.0-rc1` stays untouched as a read-only source (`git show v0.8.0-rc1:<path>`).
**Goal:** the model of the spec, carrying everything `0.7.2` carries plus issue #4's leftovers, with the workspace green at every commit, and with the design measured on a small slice before the bulk is built.

---

## 1. Rules of the Work

1. **The new model is built beside the old one, and the old one is removed last.** The new code lives in `native-theme/src/next/` (`native_theme::next`, not re-exported from the crate root) until milestone `M5`. Until then nothing of `0.7.2` is deleted, every crate of the workspace compiles, and `scripts/check_release.sh` and CI work as they do today. Reasons, checked against the repository on 2026-11-22:
   - A cut at the start cannot compile: `icons.rs`, `rasterize.rs`, `fonts.rs`, `detect.rs`, `detect/icon_theme.rs`, `spinners.rs`, `watch/*` and the eight `model/*.rs` files that stay all import items of the flat model (`Rgba`, the old `Error`, `model::*`, the readers, `pipeline`).
   - The three connectors, their showcases and `tools/showcase-support` are about 210,000 lines of Rust that read the flat model (section 4). With the old model alive they are ported one crate at a time against a running reference, and `main`'s `0.7.x` releases merge into the branch without conflict until then.
   - `check_release.sh`, `ci.yml`, `publish.yml` and the scripts of section 3 name files the cut deletes.
2. **Equivalence with `0.7.2` is the gate, not review.** While both models exist, tests compare them directly:
   - *model parity* (`native-theme`, `next::parity` tests): for each of the seven platform presets of `0.7.2` and both schemes, every field of the old resolved theme equals the value at its new home. The table of homes is that test's data, kept as one file (`native-theme/tests/next_homes.toml`) with one row per `0.7.2` field: the key as the old `ResolvedTheme` serialises it → its home as (widget, part, state, property), or a named global or metric. The test takes the list of old keys from the JSON serialisation (TOML leaves out an unset option, JSON writes `null`), treating an enum value such as a font's `defined_size` as one leaf, and fails for a key without a row; the four fields of the old `Resolved` wrapper, which does not serialise (`mode`, `icon_set`, `icon_theme`, `icon_theme_explicit`), have rows written by hand. Thus the list of 304 fields is never compiled by hand. A row may name several homes, each compared (`0.7.2`'s `checkbox.*` fields are shared by `checkbox` and `radio`), a home per preset where a field's meaning differs by platform (`list.border.padding` is Breeze's highlight margin and elsewhere a padding; `menu.border`'s radius), and a fallback where `0.7.2` has one (`radio_indicator_width` unset means `indicator_width`). A field without a home is a spec defect, fixed before its widget is built. (The ten community presets have no equal: they become palettes, whose state colours the builders derive.)
   - *reader parity* (same tests): the theme the old reader path produces from a system's settings equals the one the new builder produces when fed the same settings as `SystemOverrides`, on the KDE fixtures (`tests/fixtures/kde/*.ini`), on GNOME through the pure function that takes the portal's data (`build_gnome_spec_pure`), and, on the CI runners, on the live macOS and Windows systems.
   - *connector parity* (each connector's tests): what the connector hands to its toolkit (the global theme struct and each widget's style) is equal when computed from the old model and from the new one, for each of the seven presets and both schemes. A toolkit type without `PartialEq` is compared through its `Debug` form, and one without that through the connector's own value that feeds it; each connector's first parity task lists the form per type. For gpui: `gpui_component::Theme` through `Debug` (its `Serialize` skips `notification`, `motion` and `cursor_blink`), and the scroll bar, which goes into a second global that has neither `Debug` nor `PartialEq`, through the connector's `ScrollbarGeometry`. A connector's parity test names the presets it covers: lane B adds a preset to it in a task of its own after merging that preset's unit, and fixes or lists what differs, so a new preset never turns a consumer's test red in lane A.
   - A difference is allowed only when listed in the test with its reason (a corrected value with its citation, or an issue #4 item).
   These tests are scaffolding and are deleted at the cut. What stays is the golden snapshots of the new resolved themes, from `ResolvedTheme`'s `Serialize`, written in `M2` as each preset and each reader passes its parity: one per preset and scheme (`tests/snapshots/<preset>.<scheme>.json`), and one per reader fixture (the theme resolved from each `tests/fixtures/kde/*.ini` and from the GNOME test data), which take over what `tests/reader_kde.rs` guards today. From then on a changed value shows as a snapshot diff, to be justified by its citation in the same commit. The snapshot tests need the `serde` feature, which is no default after the cut: at the cut `serde` joins the features with which `check_release.sh` and CI test `native-theme`, or the tests would compile out unnoticed. The snapshots are also the new model's field list for the ported scripts: its unit is (widget, part, property) plus each direct metric and global, as the snapshot spells them.
   The table of homes is written once and used four times: by the parity test; as the placement of a preset's constants (`M2`); as the dictionary of a consumer's port, where a read of an old field becomes the query its row names (`M4`); and, through the snapshots, as the field list of the ported scripts.
3. **Where a value comes from.** In this order: the `0.7.2` preset TOML of that platform (shipped; verified where it carries a citation: counted on 2026-11-22, 1,469 of about 3,150 values in the seven platform files have a citation of `docs/platform-facts.md` directly above them, `kde-breeze.toml`'s and `adwaita.toml`'s headers say that an uncited value is unchecked, and `ios-13.toml`'s that a value without a comment has no primary source); `docs/issues/0004_kde-leftovers-rationale.md` and the measurements it names; the facts verified on `v0.8.0-rc1` (`docs/facts/`: colour roles, tokens and `button` per platform — the only widget taken to full depth there); a pinned upstream source that states the value directly. The gap-map documents list missing capabilities and hold no values. A value with none of these sources is not written: the property stays unstated (spec §2, `stated`), the axis value gets no rule, and the item goes to `docs/todo.md` for a later `0.8.x` release (the builders report such items; the orchestrator writes the file at each unit's end, so no two lanes edit it). No new measurement campaign is part of this plan.
4. **Citations.** Every platform constant in `next/presets/*.rs` carries a comment naming its source: `platform-facts.md (§x.y)` for an in-repo fact (the document and section, no line number), or the upstream file at its pinned version. A value taken from a `0.7.2` TOML takes the citation of the comment directly above it there (the section and the upstream reference, the line number dropped; `ios-13.toml`'s short names for its sources go into the module documentation with their definitions), so nobody looks it up again; a comment is not stretched over the lines below it. A value the TOML leaves uncited is carried with the comment `0.7.2 <file> (uncited)`: it is neither dropped (parity) nor given a citation nobody checked. After a unit's snapshots exist, one `worker` task per platform (no cargo, beside the lanes) looks these values up in the facts verified on `v0.8.0-rc1` where their kind is covered there (a colour role, a token such as a text style, a property of `button`). Those facts are keyed by rc1's model and were read at other upstream versions, so a match is made through the upstream source, not by key. A fact that agrees replaces `(uncited)` by the citation of the upstream source it names, a change of comments only; one that differs is recorded in `docs/todo.md` with both values and the versions they were read at, and is not applied in the port. `scripts/check_preset_citations.py`, ported in `M2`'s KDE unit, checks every citation that is there, accepts that form as it accepts an uncited TOML value today, and prints its count per preset; the counts go into `docs/todo.md`, and verifying those values is not part of `0.8.0` (rule 3).
5. **Licences and the clean room.** Reading LGPL/GPL sources for facts (a constant, a colour, which state draws what) is allowed and cited. No code is written from them: a function whose reference is LGPL/GPL is made in two roles — a describer reads the source and writes a behavioural description and a vector table produced by running the reference (PySide6, a GTK run); an implementer who sees only those two writes the function, and the vectors prove it. Apache-2.0 and MIT references may be ported, each file with its file-level notice and an entry in `native-theme/NOTICE`. Every implementer and reviewer brief quotes this rule.
6. **`unsafe` and panics.** No new `unsafe` beyond the lines `0.7.2` has (`macos.rs`, `windows.rs`, `sficons.rs`, `winicons.rs`, `watch/{macos,windows}.rs`) without the maintainer's grant; a reader upgrade that needs new FFI waits for one. No panic-prone code (`unwrap`, `expect`, indexing that can fail, `unwrap_or` with a made-up number). The allocation-counting tests of spec §11 would need an `unsafe impl GlobalAlloc` if written by hand; they use the dev-dependency `dhat` in its testing mode instead, in an integration test binary of their own. `M0`'s first task confirms that it serves (it counts allocations and live bytes, and the locked workspace still passes the MSRV check); if not, the grant is asked for before `M0` goes on.
7. **Gates, from narrow to wide.** A test runs where it can first fail; the wide gates run seldom.
   - *In a round* (an edit, a review's fix): the tests the change reaches — `cargo nextest run -p native-theme next::<module>`, or in a consumer that crate's parity test.
   - *At a task's end, when its diff lies wholly in `native-theme/src/next/`, `native-theme/tests/next_*` and `native-theme/tests/{vectors,snapshots}/`:* `scripts/check_next.sh`, the core crate's own steps with the commands `check_release.sh` uses: `cargo fmt --all`; clippy on `-p native-theme --all-targets` without features and with the script's Linux features, `-D warnings`; `check_strict_panic.sh -p native-theme --lib` with both; the crate's tests with both; its two rustdoc steps (`-D warnings`); `check_panic_patterns.py` and `check_readme_versions.py` (seconds each). In a task of the Windows or macOS unit it also runs the script's cross-target clippy and strict-panic steps of `native-theme` for that target, since no host step compiles code behind that target's `cfg`. What it leaves to `--commit`: the MSRV checks (their build folder is removed after each run, so each is a cold build; timed in `M0`), the feature combinations and every other crate. A task that writes a `#[cfg(feature = …)]` gate or edits a `Cargo.toml` is not such a task and ends with `--quick`. It is written in `M0`'s first task and deleted at the cut. Reason: `--quick` skips a step only when nothing its crates reach has changed, and every consumer reaches `native-theme`, so `--quick` after an edit in `next/` runs the steps of all crates again, although before `M4` the only code outside `native-theme` that sees `next` is the gpui connector's mapping and parity test from `M0`. From `M0`'s step 4 on, `check_next.sh` therefore also runs `cargo check -p native-theme-gpui --all-targets` and that parity test.
   - *At any other task's end:* `scripts/check_release.sh --quick`. A builder in a worktree runs its own crate's steps there (`-p`); the orchestrator runs `--quick` in the main checkout after the merge.
   - *Every third task merged (counted over both lanes), at the end of a platform unit (`M2`) and of a consumer crate (`M4`), and at a milestone's end:* `--commit`, in the main checkout.
   - Merges into the main checkout and the orchestrator's gates there happen between lane A's tasks, never during one: the tree is then whole, and no more than two cargo processes run.
   - *CI* (a push to the draft PR): at a milestone's end, and at the end of `M2`'s Windows and macOS units, whose parity tests run only there. The script's cross-target checks pass locally first, so CI is not used to find compile errors. Nobody waits for a CI run: a failure comes back as a fix task.
   - The full check runs in `M5` (section 2).
   - Timings (`resolve`, a part query) are measured with the release-mode bench on the maintainer's machine at `M0`, when the last preset is in, and after the cut, and written into section 4; `cargo test` asserts only what scheduling cannot disturb (sizes, allocation counts).
8. **Reviews.** Every diff that changes behaviour is reviewed before it merges, the reviewer getting the diff and the spec clauses; the review starts on the task's commit while its gate runs. The hard-core reviewer gets `rules.rs` (the evaluator), the resolution pipeline, and any diff that changes a line inside an `unsafe` block (the readers' FFI is reused, so a refactor around it is an ordinary review). A reviewer does not check again against the sources a value the parity tests prove equal to `0.7.2`'s: in a preset or a consumer it reads the listed differences with their citations, the values beyond `0.7.2`, and the code that derives or maps. The three documents get no further review pass: an amendment of the spec (a home, a field of `SystemOverrides`) is proven by the parity test it enables.
9. **`0.7.x` compatibility on `main`; issue #4 `L2`/`L3` in `0.8.0`.** `0.7.3` is skipped for `L2`/`L3` (not urgent; spares throwaway flat-model + connector + showcase churn). All remaining issue #4 items ship in `0.8.0` (`L2` in `M0`; clean-room `qt_lighter` + `L3` in `M2`). `main` remains open for urgent toolkit-compatibility `0.7.x` releases, merged into `v0.8.0` at each milestone's end.
10. **Stop rule.** A milestone that passes twice its estimate from `M0` stops, and the maintainer gets the numbers and one recommendation (cut scope, change the approach, or continue), with its reasons.

## 2. Milestones

**Order and lanes.** `M0`, `M1`, `M2`'s KDE unit and `M3`, one builder, in the main checkout. At `M1`'s end the model's types, the table of homes and `SystemOverrides` are complete. From `M3`'s merge two lanes run side by side on disjoint crates, one builder each (the machine carries two cargo processes; other agents beside them run no cargo):

- *lane A, `native-theme`, in the main checkout:* `M2`'s other platform units;
- *lane B, the consumers, in a worktree:* `M4`. It starts when `M3` is merged. By then every row of the table of homes that `kde-breeze` states has carried real data once (the KDE unit), so a home that cannot hold its value has been found for those; and the system entry points and the watcher hook exist, which the connectors' `from_system` and `watch` paths and the showcases call. A later platform unit only adds data and its reader's arm; lane B takes it by merging the branch, and then extends its parity tests to that preset in a task of its own (rule 2).

When lane A is done, its builder takes the next consumer crate not yet started; the worktree's builder stays the owner of the parity scripts, `docs/showcase-*.toml` and the lock file, and the other reports its entries to it. `M5` follows both lanes. Lane B's build folder is removed when the lane ends. The two lanes never edit the same file. `scripts/`, `docs/*.toml` and the lock file are lane A's until lane B starts (the citation script's port is in the KDE unit) and lane B's afterwards: an edit there changes the key of every `--quick` step. A change that crosses this line (a spec defect in the model after `M1`, a script lane A needs changed) is one task of its own, merged into both lanes before either goes on.

**Task size.** Small items of one shape go into one task (widgets by family, not one task per widget), sized from `M0`'s figure per widget so that the agent's context stays below about 300 k tokens. A task goes to a fresh agent with the spec clauses quoted in its brief; agents run long commands in the foreground, report once, start no sub-agents, and search with `locate`.

### `M0` — The Slice: One Preset, Six Widgets, One Connector, Measured

**Purpose:** get, with the smallest build, the results that could refute the design: that a compiled builder states a real preset compactly and exactly; that a connector can take everything it needs from part queries; what the whole costs.

1. **Core types** in `next/` (spec §§2–3): `color.rs` (`Color` beside the old `Rgba`), `paint.rs`, `geometry.rs`, `style.rs` (with `stated`), `query.rs`, `rules.rs`; `size_of` tests and the allocation-counting test of `RuleSet::eval` and `PartStyle::clone` (rule 6, with `scripts/check_next.sh` in this first task).
2. **`kde-breeze`, light and dark, for `button`, `checkbox`, `radio`, `list`, `scrollbar`, `tooltip`** (five ruled widgets and one static), as the builder of spec §6 in its real shape: it takes the resolve inputs, computes the colour roles (from the preset's constants or from the system's colours) and derives the widgets from them. In `0.7.2` that derivation sits in the KDE reader (`kde/colors.rs` assigns about 90 widget fields directly); a builder that only copied `kde-breeze.toml`'s constants would measure the wrong thing and be written again in `M2`. So `M0` also defines the KDE part of `SystemOverrides` (spec §8, amended from what the `0.7.2` KDE reader writes; Appendix A) and a function from the `kdeglobals` data, read through the existing parser, to that part; `reader/kde.rs` reuses it in `M2`, and the old reader goes on writing the flat model beside it. `M0`'s resolved theme holds the globals and these six widgets only (the 27-widget `ResolvedTheme` is `M1`'s); the measurements are projected per widget. Included: issue #4's `L2` (`HOVER | UNFOCUSED_VIEW`, no new math kernel), `L4` and `S1`–`S4`, and `kde-breeze`'s complete globals (`ColorRoles`, `Typography`, `LayoutMetrics`, timings), every slot without a source reported at the checkpoint. No palette and no patch yet.
3. **Parity table and tests** for those six widgets and the globals (rule 2): model parity on the static preset, and reader parity on every `.ini` fixture of `tests/fixtures/kde` (Breeze Light and Dark, the custom accent, high DPI, and the minimal, partial and malformed files, on which both paths must agree as well), settling the homes Appendix A lists for them.
4. **Connector parity in `native-theme-gpui`** for the same widgets on `kde-breeze`: the new mapping functions (kept for `M4`) against the connector's current output, on the leaves that these six widgets and the globals feed (the connector's contract tables name each leaf's source). gpui is chosen because it is the toolkit issue #4 came from and the largest consumer; it writes two globals and geometry helpers, compared as rule 2 says.
5. **Order inside `M0`.** One builder: step 1; then the rows of the table of homes for the six widgets and the globals, and the KDE part of `SystemOverrides` (amendments of the spec, and the input of steps 2 and 4); then steps 2 and 3; then step 4. Beside it, with no cargo: the describer's half of the clean-room `qt_lighter` (rule 5; the description and the PySide6 vector table), which `L3` needs under every outcome of the checkpoint.
6. **Measurements**, written into section 4 with their arithmetic:
   - lines of the builder per widget, and the symbol size of `next::presets` in a release build per widget → the projection for 27 widgets and all presets, against the spec's 150 KB;
   - `resolve()` time, a part query's time, the resolved theme's heap bytes (release bench, median);
   - the edit-test cycle of `cargo test -p native-theme next::` with both models in the crate (before `next/` exists: section 4), and the time of `check_next.sh`, of `--quick` after an edit in `next/`, and of `--commit`;
   - the share of the builder's statements that are constants copied unchanged from the TOML → whether `M2`'s constants are written by hand or emitted by a one-off script from the TOMLs and the table of homes, whichever these figures show to be cheaper (such a script is a port tool, run once and not kept in the tree or the build, and its output is committed Rust, reviewed and gated like hand-written code — not the standing preset codegen spec §1 rules out; the parity tests are the gate either way; the roles, the derivations and the values beyond `0.7.2` are written by hand in both cases);
   - agent time and tokens per part of `M0` → the estimate for `M1`–`M5` in weeks, per milestone.
7. **`M0` gate and checkpoint:** tests green, `--commit` green. Then the work stops for the maintainer, who gets the measurements and the estimate. The design is re-opened before any further code if the projection misses a hard target of spec §11 (compiled size, `resolve` under 1 ms, a query under 100 ns), or if the connector parity needed something the model cannot say; otherwise `M1` starts on his word.

### `M1` — The Whole Model

Everything of spec §§2–7 that is not a preset's data, still in `next/`:

1. `error.rs`, `motion.rs`, `roles.rs`, `typography.rs`, `layout.rs`, `window.rs`, `widgets.rs` (27 widgets, `ResolvedTheme`), each widget added together with its rows of the parity table (so a missing home is found here, per widget, not in `M4`). `SystemOverrides` is amended here for the portal, macOS and Windows readers too, from a list of what each `0.7.2` reader assigns (a search task, no cargo; Appendix A), so that the model is complete when the lanes part.
2. `preset.rs` (`Preset`, `Theme` and the resolution steps of spec §6; the builders are crate-private functions chosen by a `match` on `Preset`, and a preset whose builder is not written yet resolves to a theme with nothing stated), `presets/helpers.rs` (the shared scaffold).
3. `palette.rs` with the bundled palettes; `patch.rs` with validation and the TOML/JSON schema. The `#[cfg(feature = …)]` gates of spec §9 are written from the start; until the cut `palettes`, `serde` and `toml = ["serde"]` are additive features in `default` (Cargo accepts a feature named like a required dependency, and `scripts/check_features.sh` automatically exercises `--no-default-features` and each feature alone). They are in `default` until the cut because the gates' test steps name their features, and code behind a feature they do not name would go untested; the cut sets spec §9's default and adds `serde` to the gates' list (rule 2).
4. Icons, fonts, detection (one builder for the whole of `M1`: `IconThemeSpec` and `IconSizes` come before item 1, whose `ResolvedTheme` holds them, and `Preset::detect()` after item 2, which defines `Preset`): additive only — `IconThemeSpec`, `IconSizes`, `IconRole::mirrors_in_rtl()`, a width-aware `select_face` beside the present one, `Preset::detect()` on top of `detect.rs`. Their switch from `Rgba` to `Color` and from `arc-swap` to `RwLock` is part of the cut.
5. The spec's smoke target as `tests/next_prelude_smoke.rs` (`tests/prelude_smoke.rs` is the old model's until the cut), with `palettes`/`toml` blocks gated by `#[cfg(feature = ...)]` so `check_release.sh`'s `--all-targets --no-default-features` clippy check passes.
6. **Gate:** pipeline tests (layer order, single-scheme lock against the light/dark pair, suspension under `Contrast::High`, `validate()`'s rejections, `WindowChrome` queries allocation-free, TOML and JSON round trips); `--commit`.

### `M2` — The Platforms: Preset and Reader Together

One unit per platform, each building the preset file in `next/presets/` and that platform's reader in `next/reader/`, one after the other by the same builder. Reason: in `0.7.2` a platform's reader assigns widget fields itself (the KDE reader about 90), so the builder that takes those derivations over and the reader that only reads are two halves of one change, with the same sources in context; done in two milestones, each platform's sources would be read twice.

Units, in this order (`M3` is built between the first and the second): **KDE** (`kde.rs`: the rest of `kde-breeze`, with the clean-room `qt_lighter` by rule 5 for `L3` and every remaining issue #4 item of spec §5's table; `reader/kde.rs`); **GNOME** (`adwaita.rs`; `reader/portal.rs`); **Windows** (`windows.rs`; `reader/windows.rs`); **macOS** (`macos.rs` with `macos-monterey` and `macos-tahoe`; `reader/macos.rs`); **Material** (`material.rs`); **iOS** (`ios.rs` with `ios-13`; and `ios-26` if the facts verified on `v0.8.0-rc1` fill the 38 fields that `docs/todo.md` lists as without an iOS 26 source — checked when this file is written — otherwise it follows in `0.8.x`).

- **What a unit's builder reads:** the spec sections of its task, the `0.7.2` TOMLs of its platform, the `0.7.2` reader of its platform, and `platform-facts.md` only for a value beyond the TOMLs. Nothing of another platform, and nothing of `v0.8.0-rc1`'s facts: the look-up of uncited values there is a separate task after the unit (rule 4).
- **The preset.** Constants are placed by the table of homes, by hand or by the one-off script (`M0`'s measurement decides), each with the citation its TOML carries (rule 4). A preset's data beyond `0.7.2`'s (a variant, a size, a contrast level, a material) is written only where rule 3 gives a source; each preset's module documentation lists the variants, sizes and contrast levels it defines. The colour kernels are taken from `v0.8.0-rc1` in the task that first calls each (Appendix B), so no dead code waits in the tree.
- **The reader** produces a `SystemSnapshot` from what the `0.7.2` reader of that platform reads. The reading itself (files, registry, AppKit, portal) is the existing code, refactored so that both paths call it, not copied; what the old reader derives from it for widgets is now the builder's. A read `0.7.2` does not make is added only where it needs no new `unsafe`. A clean-room parser from `v0.8.0-rc1` (`QFont` strings, Pango descriptions, KDE colour schemes, the nearest libadwaita accent) replaces a parse of `0.7.2` only where its vector table from rc1, run against `0.7.2`'s code as the unit's first test and compared on the outputs `0.7.2`'s function returns (family, size, weight and style of a font; the scheme's colours; the accent), has a failing case; where `0.7.2` has no such parse, the parser comes in only with a read the unit adds.
- Each unit reads its platform's list padding cell (`platform-facts.md` §2.15) again under the new meaning — a row's padding, or the margin of its highlight — and places it accordingly (issue #4's `L4`; the table of homes has a home per preset for it).
- The bundled palettes are checked on every preset here (the invariants of spec §11).
- **Gate per unit:** model parity for that platform's presets in both schemes; reader parity (rule 2) for its reader; invariants; for KDE the issue #4 tests; then that platform's golden snapshots, its reader fixtures' among them, are written; `--commit`. The Windows and macOS units push for CI (rule 7). **Gate of `M2`:** the measurements repeated on all presets; the feature matrix; `--commit`.

### `M3` — System Entry Points and Watchers

Built directly after `M2`'s KDE unit, because the consumers' port needs it (see *Order and lanes*).

1. `Theme::from_system`, `from_system_with_preset`, `from_system_or_default` on top of the KDE reader, with one arm per platform; each later unit of `M2` adds its reader's arm. The watcher calls `detect::invalidate_caches()` before the callback.
2. `Preset::detect()` on macOS without the `macos` feature (reading `SystemVersion.plist`) is proven on the `macos-26` runner or left returning `MacosMonterey`, as `0.7.2` does.
3. **Gate:** on the maintainer's KDE desktop the theme from the live system is equal through both paths; `--commit`. The feature matrix over all four readers is part of `M2`'s gate.

### `M4` — The Consumers, One Crate at a Time

Order: `tools/showcase-support` (every showcase depends on it), then `native-theme-gpui` (the largest, and its mapping began in `M0`), `native-theme-iced`, `native-theme-egui` with `native-theme-egui-widgets`; a second builder, once lane A is done, takes the next of these not yet started. `native-theme-build` follows last (`native_theme::theme::IconSet` → the new path; the re-export it needs in `native-theme` is part of that task, lane A being done by then).

What is kept twice and what is not: a library keeps its old path beside the new one until `M5` (a connector's `src`, because its parity test needs both; `showcase-support`'s API, because showcases not yet ported call it). A showcase, an example and a README doctest are switched in place, in their crate's task; nothing of them is written twice.

For each crate:

1. the connector reads `next::ResolvedTheme`: each read of an old field is replaced by the query its row in the table of homes names; then connector parity (rule 2) for every widget, preset and scheme, and each visible property the new model states and the toolkit can draw wired through (what a toolkit cannot draw is in the connector's README);
2. its showcase, Widget Info claims, README doctests and examples follow, by the same table. The showcases' theme pickers and READMEs move from the ten community presets to a preset with a palette. `check_connector_parity.py`, `check_showcase_parity.py`, `check_widget_coverage.py` and `showcase-support`'s value paths learn the new form in the first connector's task and keep the old one beside it: a connector or showcase not yet ported stays checked as it is today, and the sibling rule of `check_connector_parity.py` (a function of one connector must be in the others) compares new paths only with new paths. The old form goes at the cut;
3. **gate:** the crate's parity test covers all seven presets in both schemes (asserted by the test itself against the list of platform presets, so that `M5` cannot delete an incomplete one); `--commit`; then, once per showcase and not per fix round, its captures under `kde-breeze` compared side by side with `0.7.2`'s at 1280×720. The released screenshots and GIFs are made once, by `M5`'s asset run.

### `M5` — The Cut and the Close-Out

1. **The cut**, in six steps, each one commit ending with `--quick`, and `--commit` after the last:
   1. in the consumers, remove the old paths and the parity tests, so that nothing outside `native-theme` reads the flat model;
   2. the gates stop reading the old model: section 3's retirements and the scripts' old forms, with their steps in `check_release.sh` and `ci.yml`;
   3. `detect.rs` from `arc-swap` to `RwLock`;
   4. the deletion: the flat model, `native-theme-derive`, the 17 preset TOMLs, the old readers' wrappers, the old model's tests (`merge_behavior`, `preset_loading`, `proptest_roundtrip`, `serde_roundtrip`, `resolve_and_validate`, `timings`, `reader_kde`, `platform_facts_xref`, `prelude_smoke`), the scaffolding of rule 2 and `check_next.sh`. In the same commit: every edit that names a deleted path (the derive's steps in `check_release.sh`, `ci.yml` and `publish.yml`, the workspace member, the provenance paths), and the switch of every kept module that imports the flat model to the new types (on 2026-11-22: `icons.rs`, `fonts.rs`, `detect.rs`, `detect/icon_theme.rs`, `freedesktop.rs`, `winicons.rs`; the compiler names the rest);
   5. the move of `next/*` to the crate root and the rewrite of the `native_theme::next::` paths in the consumers, nothing else;
   6. prune the dependencies and set the features of spec §9: every consumer that calls `Theme::from_toml` or serialises a theme (the three connectors and `showcase-support`) enables `native-theme`'s `toml` or `serde` feature, `tests/icon_sources.rs` gets `required-features = ["toml"]`, and `serde` joins the gates' feature list (rule 2); `native-theme/Cargo.toml`'s licence expression and `NOTICE`; what is left of section 3 (the theme lists of the capture scripts, `.claude/`).
2. Documentation, written by a second agent beside the cut (no cargo) and gated with it: root and connector READMEs, `CHANGELOG.md` (what changes for users of the community presets and of the async entry points), `ROADMAP.md`, `docs/todo.md` (the items rule 3 deferred), the `platform-fact` skill and the `preset-validator` agent.
3. Archive the three `docs/v0.8.0-*.md` and the parked `docs/todo_v0.8.0_model-completeness-*` documents. This comes before the release's checks, which read the archive index, and no file of the tree changes after them.
4. The release's checks, in the order that makes each run once: versions to `0.8.0`; the compatibility run; push; the full `check_release.sh` (with the docs.rs emulation) while CI runs; with both green, the asset run; the full check again for the two stamps. Every edit of `src` or of an example, a comment included, is in before the compatibility run: a later one makes the asset stamp stale, in a connector the compatibility stamp too, and repeats those runs. Then remove merged branches and worktrees with their build folders; `sweep-target.sh`.
5. Merging to `main`, the tag, publishing and the GitHub release are the maintainer's.

## 5. Risks

| Risk | What limits it |
|---|---|
| The effort is far above what the maintainer accepts | `M0`'s estimate and checkpoint; rule 10 |
| The compiled presets are much larger or slower than the targets | measured in `M0` on six widgets, before 21 more are written |
| A value changes unnoticed in the port | model and connector parity on every preset and scheme; snapshots after the cut |
| macOS and Windows code cannot run on the development machine | the readers' reading code is reused, not rewritten (`M2`); the script's cross-target checks compile it locally; CI's macOS and Windows jobs run the parity tests there |
| Two models in one crate slow the edit-test cycle | today the crate rebuilds its tests in about 2 s after a touch (section 4); measured again in `M0` with `next/` in it |
| The lanes collide, or lane B builds on a model that then changes | disjoint crates and one owner per shared file; the model and the table of homes are frozen at `M1`'s end, and lane B starts only after the KDE unit has put real data through every row and `M3` has given it the entry points |
| `main` moves on (toolkit-compat `0.7.x` releases) | merged at each milestone's end while the old model still exists (rule 9) |

## Appendix A — Remaining `0.7.2` Fields to Settle in `M0`/`M1`

Found by comparing `0.7.2`'s 304 resolved fields with spec §§4–5 (the global defaults — `disabled_text`, `shadow`, `line_height_multiplier`, `font_whole_pixels: Option<bool>`, `LayoutMetrics` default border geometry, `ResolvedTheme::focus_ring`, and `IconThemeSpec::theme_explicit` — are already settled in spec §4). Each remaining item is settled when its widget's parity rows are written (`M0` for the slice, `M1` for the rest), by amending the spec first:

- **No home yet:** a font's `defined_size` (the size as the source states it, pt or px — decide in `M0` whether `TextStyle` needs `defined_size` for Qt DPI re-derivation/Widget Info or whether `size_px` + `font_dpi` suffices).
- **Several candidate homes:** `defaults.surface_color` (`card`, `dialog` or `popover`); `text_scale.section_heading` and `dialog_title` (which of the eleven `Typography` slots); `menu.border`'s radius (KDE's item highlight, Material's container); `checkbox.background_color` and `unchecked_background`, `unchecked_border_color` and `border.color` (two fields, one property each).
- **Focus colours:** `button`/`input` `focus_border_color`, `slider.thumb_focus_border_color` — the part's stroke under `FOCUSED`, or `focus.stroke`.
- **Inactive title bar:** `window.inactive_title_bar_background`/`_text_color` are reachable only by resolving with `window_active = false`; the parity test does so.
- **`input.selection_background`/`selection_text_color`:** only the global `colors.text_selection`.
- **Reader-written fields without a home in `SystemOverrides`** (spec §8 has a UI font, a monospace font and colour roles; the `0.7.2` readers write more): KDE — the menu, toolbar and title-bar fonts and the caption size, the `text_scale` entries `section_heading` and `dialog_title`, and the inputs of its widget derivations: `[Colors:View]` `DecorationHover` and `BackgroundAlternate`, `[KDE]` `frameContrast` and `contrast`, and the icon sizes read from the icon theme's `index.theme`; Windows — the title-bar, menu, status-bar and tooltip fonts, the scroll bar's groove width and minimum thumb length, two icon sizes, the line width, the disabled text colour, the input placeholder colour, both title-bar colour pairs; macOS — the scroller style (spec §8 has `overlay_scrollbars`) with the groove width of each style, the input placeholder colour, the list's alternate row and grid colours, the switch's disabled checked fill; GNOME — the dialog title and title-bar fonts, the text-scale entries, the tab's active indicator colour. The list is completed from the readers' assignments when each reader's part of `SystemOverrides` is amended (KDE in `M0`, the others in `M1`).
- **Open items of issue #4's list with no home yet** (`docs/todo.md`): GNOME's keyboard focus ring that fades after 3 s; whether a toolbar button is a tab stop; Qt's 18 px line box against the model's 17.68; the check box's 4 px radius drawn 2 px inside its 20 px cell (`indicator.margin` can carry it). They stay in `docs/todo.md` unless their widget's parity needs them.

## Appendix B — Taking Code from `v0.8.0-rc1`

- **Kernels** (`native-theme/src/platform/`, 20 modules besides `mod.rs` and `kde_accent_operands.rs`): each is copied in the task that first calls it, as `pub(crate)`.
