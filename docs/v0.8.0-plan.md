# native-theme v0.8.0 — Implementation Plan

**Status:** Proposed; pairs with [v0.8.0-spec.md](v0.8.0-spec.md). An implementing session needs this file and the spec sections its task names, not `docs/v0.8.0-rationale.md`.
**Branch:** `v0.8.0` (from `main` at `v0.7.2`). `v0.8.0-rc1` stays untouched as a read-only source (`git show v0.8.0-rc1:<path>`).
**Goal:** the model of the spec, carrying everything `0.7.2` carries plus issue #4's leftovers, with the workspace green at every commit, and with the design measured on a small slice before the bulk is built.

---

## 1. Rules of the Work

1. **The new model is built beside the old one, and the old one is removed last.** The new code lives in `native-theme/src/next/` (`native_theme::next`, not re-exported from the crate root) until milestone `M5`. Until then nothing of `0.7.2` is deleted, every crate of the workspace compiles, and `scripts/check_release.sh` and CI work as they do today. Reasons, checked against the repository on 2026-11-22:
   - A cut at the start cannot compile: `icons.rs`, `rasterize.rs`, `fonts.rs`, `detect.rs`, `detect/icon_theme.rs`, `spinners.rs`, `watch/*` and the eight `model/*.rs` files that stay all import items of the flat model (`Rgba`, the old `Error`, `model::*`, the readers, `pipeline`).
   - The three connectors, their showcases and `tools/showcase-support` are about 212,000 lines of Rust that read the flat model (section 4). With the old model alive they are ported one crate at a time against a running reference, and `main`'s `0.7.x` releases merge into the branch without conflict until then.
   - `check_release.sh`, `ci.yml`, `publish.yml`'s provenance gate and nine scripts name files the cut deletes (section 3).
2. **Equivalence with `0.7.2` is the gate, not review.** While both models exist, tests compare them directly:
   - *model parity* (`native-theme`, `next::parity` tests): for each of the seven platform presets of `0.7.2` and both schemes, every field of the old resolved theme equals the value at its new home. The table of homes (old key → new getter) is that test's data; a field without a home is a spec defect, fixed before its widget is built. (The ten community presets have no equal: they become palettes, whose state colours the builders derive.)
   - *reader parity* (same tests): the theme the old reader path produces from a system's settings equals the one the new builder produces when fed the same settings as `SystemOverrides`, on the KDE fixtures (`tests/fixtures/kde`) and, on the CI runners, on the live macOS and Windows systems.
   - *connector parity* (each connector's tests): what the connector hands to its toolkit (the global theme struct and each widget's style) is equal when computed from the old model and from the new one, for each of the seven presets and both schemes. A toolkit type without `PartialEq` is compared through its serialised or `Debug` form (gpui's `Theme` is `Serialize`).
   - A difference is allowed only when listed in the test with its reason (a corrected value with its citation, or an issue #4 item).
   These tests are scaffolding and are deleted at the cut. What stays is the golden snapshots of the new resolved themes (`tests/snapshots/<preset>.<scheme>.json`, from `ResolvedTheme`'s `Serialize`), written in `M2` as each preset passes its parity: from then on a changed value shows as a snapshot diff, to be justified by its citation in the same commit. The snapshots are also the new model's field list for the ported scripts: its unit is (widget, part, property) plus each direct metric and global, as the snapshot spells them.
3. **Where a value comes from.** In this order: the `0.7.2` preset TOML of that platform (verified and shipped; cited there to `docs/platform-facts.md`); `docs/issues/0004_kde-leftovers-rationale.md` and the measurements it names; the facts verified on `v0.8.0-rc1` (`docs/facts/`: colour roles, tokens and `button` per platform — the only widget taken to full depth there); a pinned upstream source that states the value directly. The gap-map documents list missing capabilities and hold no values. A value with none of these sources is not written: the property stays unstated (spec §2, `stated`), the axis value gets no rule, and the item goes to `docs/todo.md` for a later `0.8.x` release. No new measurement campaign is part of this plan.
4. **Citations.** Every platform constant in `next/presets/*.rs` carries a comment naming its source: `platform-facts.md (§x.y)` for an in-repo fact (the document and section, no line number), or the upstream file at its pinned version. `scripts/check_preset_citations.py` is ported to check this on the Rust presets (`M2`).
5. **Licences and the clean room.** Reading LGPL/GPL sources for facts (a constant, a colour, which state draws what) is allowed and cited. No code is written from them: a function whose reference is LGPL/GPL is made in two roles — a describer reads the source and writes a behavioural description and a vector table produced by running the reference (PySide6, a GTK run); an implementer who sees only those two writes the function, and the vectors prove it. Apache-2.0 and MIT references may be ported, each file with its file-level notice and an entry in `native-theme/NOTICE`. Every implementer and reviewer brief quotes this rule.
6. **`unsafe` and panics.** No new `unsafe` beyond the lines `0.7.2` has (`macos.rs`, `windows.rs`, `sficons.rs`, `winicons.rs`, `watch/{macos,windows}.rs`) without the maintainer's grant; a reader upgrade that needs new FFI waits for one. No panic-prone code (`unwrap`, `expect`, indexing that can fail, `unwrap_or` with a made-up number).
7. **Gates per round.** In a task: the tests the change reaches (`cargo test -p native-theme next::<module>`). At a task's end: `scripts/check_release.sh --quick`. At a milestone's end: `--commit`, and CI on the pushed branch's draft PR. The full check once, in `M5`. Timings (`resolve`, a part query) are measured with the release-mode bench on the maintainer's machine at `M0` and at each milestone's end and written into section 4; `cargo test` asserts only what scheduling cannot disturb (sizes, allocation counts).
8. **Reviews.** Every diff that changes behaviour is reviewed before it merges, the reviewer getting the diff and the spec clauses; `rules.rs` (the evaluator), the resolution pipeline and the readers' FFI get the hard-core reviewer.
9. **`0.7.x` compatibility on `main`; issue #4 `L2`/`L3` in `0.8.0`.** `0.7.3` is skipped for `L2`/`L3` (not urgent; spares throwaway flat-model + connector + showcase churn). All remaining issue #4 items ship in `0.8.0` (`L2` in `M0`; clean-room `qt_lighter` + `L3` in `M2`). `main` remains open for urgent toolkit-compatibility `0.7.x` releases, merged into `v0.8.0` at each milestone's end.
10. **Stop rule.** A milestone that passes twice its estimate from `M0` stops, and the maintainer gets the numbers and the choices (cut scope, change approach, continue).

## 2. Milestones

### `M0` — The Slice: One Preset, Six Widgets, One Connector, Measured

**Purpose:** get, with the smallest build, the results that could refute the design: that a compiled builder states a real preset compactly and exactly; that a connector can take everything it needs from part queries; what the whole costs.

1. **Core types** in `next/` (spec §§2–3): `color.rs` (`Color` beside the old `Rgba`), `paint.rs`, `geometry.rs`, `style.rs` (with `stated`), `query.rs`, `rules.rs`; `size_of` tests and the counting-allocator test of `RuleSet::eval` and `PartStyle::clone`.
2. **`kde-breeze`, light and dark, for `button`, `checkbox`, `radio`, `list`, `scrollbar`, `tooltip`** (five ruled widgets and one static), as the builder of spec §6 in its real shape: it takes the resolve inputs, computes the colour roles (from the preset's constants or from the system's colours) and derives the widgets from them. In `0.7.2` that derivation sits in the KDE reader (`kde/colors.rs` assigns about 90 widget fields directly); a builder that only copied `kde-breeze.toml`'s constants would measure the wrong thing and be written again in `M3`. So `M0` also defines the KDE part of `SystemOverrides` (spec §8, amended from what the `0.7.2` KDE reader writes; Appendix A) and a conversion from the old reader's parsed colours into it. Included: issue #4's `L2` (`HOVER | UNFOCUSED_VIEW`, no new math kernel), `L4` and `S1`–`S4`, and `kde-breeze`'s complete globals (`ColorRoles`, `Typography`, `LayoutMetrics`, timings), every slot without a source reported at the checkpoint. No palette and no patch yet.
3. **Parity table and tests** for those six widgets (rule 2): model parity on the static preset, and reader parity on `tests/fixtures/kde` (the Breeze Dark and custom-accent fixtures), settling the homes Appendix A lists for them.
4. **Connector parity in `native-theme-gpui`** for the same widgets on `kde-breeze`: the new mapping functions (kept for `M4`) against the connector's current output. gpui is chosen because it is the tightest fit: one global `gpui_component` theme plus geometry helpers, and it is the toolkit issue #4 came from.
5. **Measurements**, written into section 4 with their arithmetic:
   - lines of the builder per widget, and the symbol size of `next::presets` in a release build per widget → the projection for 27 widgets and all presets, against the spec's 150 KB;
   - `resolve()` time, a part query's time, the resolved theme's heap bytes (release bench, median);
   - the edit-test cycle of `cargo test -p native-theme next::` with both models in the crate;
   - agent time and tokens per part of `M0` → the estimate for `M1`–`M5` in weeks, per milestone.
6. **`M0` gate and checkpoint:** tests green, `--commit` green. Then the work stops for the maintainer, who gets the measurements and the estimate. The design is re-opened before any further code if the projection misses a hard target of spec §11 (compiled size, `resolve` under 1 ms, a query under 100 ns), or if the connector parity needed something the model cannot say; otherwise `M1` starts on his word.

### `M1` — The Whole Model

Everything of spec §§2–7 that is not a preset's data, still in `next/`:

1. `error.rs`, `motion.rs`, `roles.rs`, `typography.rs`, `layout.rs`, `window.rs`, `widgets.rs` (27 widgets, `ResolvedTheme`), each widget added together with its rows of the parity table (so a missing home is found here, per widget, not in `M4`).
2. `preset.rs` (`Preset`, `Theme` and the resolution steps of spec §6; the builders are crate-private functions chosen by a `match` on `Preset`, and a preset whose builder is not written yet resolves to a theme with nothing stated), `presets/helpers.rs` (the shared scaffold).
3. `palette.rs` with the bundled palettes; `patch.rs` with validation and the TOML/JSON schema. The `#[cfg(feature = …)]` gates of spec §9 are written from the start; until the cut `palettes`, `serde` and `toml = ["serde"]` are additive features in `default` (Cargo accepts a feature named like a required dependency, and `scripts/check_features.sh` automatically exercises `--no-default-features` and each feature alone).
4. Icons, fonts, detection: additive only — `IconThemeSpec`, `IconSizes`, `IconRole::mirrors_in_rtl()`, a width-aware `select_face` beside the present one, `Preset::detect()` on top of `detect.rs`. Their switch from `Rgba` to `Color` and from `arc-swap` to `RwLock` is part of the cut.
5. The spec's smoke target as `tests/next_prelude_smoke.rs` (`tests/prelude_smoke.rs` is the old model's until the cut), with `palettes`/`toml` blocks gated by `#[cfg(feature = ...)]` so `check_release.sh`'s `--all-targets --no-default-features` clippy check passes.
6. **Gate:** pipeline tests (layer order, single-scheme lock against the light/dark pair, suspension under `Contrast::High`, `validate()`'s rejections, `WindowChrome` queries allocation-free, TOML and JSON round trips); `--commit`.

### `M2` — The Presets

One file per platform in `next/presets/`, each with the `0.7.2` TOML of that platform and its `platform-facts.md` sections in context and nothing else: `kde.rs` (the rest of `kde-breeze`, with clean-room `qt_lighter` by rule 5 for `L3` and every remaining issue #4 item of spec §5's table), `adwaita.rs`, `macos.rs` (`macos-monterey`, `macos-tahoe`), `windows.rs`, `material.rs`, `ios.rs` (`ios-13`; and `ios-26` if the facts verified on `v0.8.0-rc1` fill the 38 fields that `docs/todo.md` lists as without an iOS 26 source — checked when this file is written — otherwise it follows in `0.8.x`). The colour kernels are taken from `v0.8.0-rc1` in the task that first calls each (Appendix B), so no dead code waits in the tree.

- A preset's data beyond `0.7.2`'s (a variant, a size, a contrast level, a material) is written only where rule 3 gives a source; each preset's module documentation lists the variants, sizes and contrast levels it defines.
- The bundled palettes are checked on every preset here (the invariants of spec §11).
- **Gate per file:** model parity for that platform's presets, both schemes; invariants; for `kde.rs` the issue #4 tests; then that preset's golden snapshots are written. **Gate of `M2`:** measurements repeated on all presets; `--commit`.

### `M3` — Readers and Watchers

1. `next/reader/{kde,portal,macos,windows}.rs`: each produces a `SystemSnapshot` from what the `0.7.2` reader of that platform reads. `SystemOverrides` is first amended to hold all of it (Appendix A's reader list). The reading itself (files, registry, AppKit, portal) is the existing code, refactored so that both paths call it, not copied; what the old readers derive from it for widgets is the builders' job since `M2`. plus the four clean-room parsers from `v0.8.0-rc1` where they replace a weaker parse (`QFont` strings, Pango descriptions, KDE colour schemes, the nearest libadwaita accent). A read `0.7.2` does not make is added only where it needs no new `unsafe`.
2. `Theme::from_system`, `from_system_with_preset`, `from_system_or_default`; the watcher calls `detect::invalidate_caches()` before the callback.
3. `Preset::detect()` on macOS without the `macos` feature (reading `SystemVersion.plist`) is proven on the `macos-26` runner or left returning `MacosMonterey`, as `0.7.2` does.
4. **Gate:** reader parity (rule 2) for all four readers; on the maintainer's desktop the theme from the live system is equal through both paths; the feature matrix; `--commit`.

### `M4` — The Consumers, One Crate at a Time

Order: `tools/showcase-support`, `native-theme-iced`, `native-theme-egui` with `native-theme-egui-widgets`, `native-theme-gpui`. Every consumer gains the new path beside its old one (the showcases depend on `showcase-support`, so its old API must stay until they have moved); the old paths go in `M5`. For each crate:

1. the connector reads `next::ResolvedTheme`, with connector parity (rule 2) for every widget, preset and scheme, and each visible property the new model states and the toolkit can draw wired through (what a toolkit cannot draw is in the connector's README);
2. its showcase, Widget Info claims, README doctests and examples follow. The showcases' theme pickers, captures and READMEs move from the ten community presets to a preset with a palette. `check_connector_parity.py`, `check_showcase_parity.py` and `showcase-support`'s value paths are ported to the snapshots' field list (rule 2), in the first crate's task;
3. **gate:** `--commit`; the showcase's captures under `kde-breeze` compared side by side with `0.7.2`'s at 1280×720.

`native-theme-build` follows last (`native_theme::theme::IconSet` → the new path).

### `M5` — The Cut and the Close-Out

1. **The cut**, one commit per step, each green: delete the flat model, `native-theme-derive`, the 17 preset TOMLs, the old readers' wrappers, the old paths in `showcase-support` and the connectors, the old model's tests (`merge_behavior`, `preset_loading`, `proptest_roundtrip`, `serde_roundtrip`, `resolve_and_validate`, `timings`, `reader_kde`, `platform_facts_xref`, `prelude_smoke`) and the scaffolding tests of rule 2; move `next/*` to the crate root; switch `icons`/`rasterize`/`spinners` to `Color`; prune the dependencies and set the features of spec §9 (enabling `native-theme/serde` in `tools/showcase-support/Cargo.toml` if needed, and gating `tests/icon_sources.rs` behind `required-features = ["toml"]`); `native-theme/Cargo.toml`'s licence expression and `NOTICE`; every script, workflow and local tool of section 3.
2. Documentation: root and connector READMEs, `CHANGELOG.md` (what changes for users of the community presets and of the async entry points), `ROADMAP.md`, `docs/todo.md` (the items rule 3 deferred), the `platform-fact` skill and the `preset-validator` agent.
3. Versions to `0.8.0`; the compatibility run; the full `check_release.sh`; the asset run; the docs.rs emulation.
4. Archive the three `docs/v0.8.0-*.md` and the parked `docs/todo_v0.8.0_model-completeness-*` documents; remove merged branches and worktrees; `sweep-target.sh`.
5. Merging to `main`, the tag, publishing and the GitHub release are the maintainer's.

## 5. Risks

| Risk | What limits it |
|---|---|
| The effort is far above what the maintainer accepts | `M0`'s estimate and checkpoint; rule 10 |
| The compiled presets are much larger or slower than the targets | measured in `M0` on six widgets, before 21 more are written |
| A value changes unnoticed in the port | model and connector parity on every preset and scheme; snapshots after the cut |

| `main` moves on (toolkit-compat `0.7.x` releases) | merged at each milestone's end while the old model still exists (rule 9) |

## Appendix A — Remaining `0.7.2` Fields to Settle in `M0`/`M1`

Found by comparing `0.7.2`'s 304 resolved fields with spec §§4–5 (the global defaults — `disabled_text`, `shadow`, `line_height_multiplier`, `font_whole_pixels: Option<bool>`, `LayoutMetrics` default border geometry, `ResolvedTheme::focus_ring`, and `IconThemeSpec::theme_explicit` — are already settled in spec §4). Each remaining item is settled when its widget's parity rows are written (`M0` for the slice, `M1` for the rest), by amending the spec first:

- **No home yet:** a font's `defined_size` (the size as the source states it, pt or px — decide in `M0` whether `TextStyle` needs `defined_size` for Qt DPI re-derivation/Widget Info or whether `size_px` + `font_dpi` suffices).
- **Several candidate homes:** `defaults.surface_color` (`card`, `dialog` or `popover`); `text_scale.section_heading` and `dialog_title` (which of the eleven `Typography` slots); `menu.row_height` (exact) and `min_row_height` (floor) both on `item.min_size`; `menu.border`'s radius (KDE's item highlight, Material's container); `checkbox.background_color` and `unchecked_background`, `unchecked_border_color` and `border.color` (two fields, one property each).
- **Focus colours:** `button`/`input` `focus_border_color`, `slider.thumb_focus_border_color` — the part's stroke under `FOCUSED`, or `focus.stroke`.
- **Inactive title bar:** `window.inactive_title_bar_background`/`_text_color` are reachable only by resolving with `window_active = false`; the parity test does so.
- **`input.selection_background`/`selection_text_color`:** only the global `colors.text_selection`.
- **Reader-written fields without a home in `SystemOverrides`** (spec §8 has a UI font, a monospace font and colour roles; the `0.7.2` readers write more): KDE — the menu, toolbar and title-bar fonts and the caption size; Windows — the title-bar, menu, status-bar and tooltip fonts, the scroll bar's groove width and minimum thumb length, two icon sizes, the line width, the disabled text colour, the input placeholder colour, both title-bar colour pairs; macOS — the input placeholder colour, the list's alternate row and grid colours, the switch's disabled checked fill; GNOME — the dialog title and title-bar fonts, the text-scale entries, the tab's active indicator colour. The list is completed from the readers' assignments when each reader's part of `SystemOverrides` is amended (KDE in `M0`, the others before `M3`).
- **Open items of issue #4's list with no home yet** (`docs/todo.md`): GNOME's keyboard focus ring that fades after 3 s; whether a toolbar button is a tab stop; Qt's 18 px line box against the model's 17.68; the check box's 4 px radius drawn 2 px inside its 20 px cell (`indicator.margin` can carry it). They stay in `docs/todo.md` unless their widget's parity needs them.

## Appendix B — Taking Code from `v0.8.0-rc1`

- **Kernels** (`native-theme/src/platform/`, 20 modules besides `mod.rs` and `kde_accent_operands.rs`): each is copied in the task that first calls it, as `pub(crate)`. They import items that do not exist on `main` and must be supplied in `next/`: `Scheme`; `TextRole` and `ContentSizeCategory` (`dynamic_type`); `KdeGroup`, `KdeRoleKind`, `KdeIntensityEffect`, `KdeColorEffect`, `KdeContrastEffect` (`kde_effects`, `kde_selection_inactive`); `MaterialVariant` and a `Color` method named in a doc link (`m3_role`). `mod.rs`'s `Named` impls and `kde_accent_operands.rs` belong to the expression VM and are not taken. `src/ripple.rs` is not taken. The `kirigami_*` kernels are not taken: nothing in `0.8.0` calls them.
- **Vector tests:** `tests/platform_vectors.rs` on rc1 is an integration test importing ten types from the crate root; its checks become unit tests beside the kernels. Sixteen kernel tables and the 4 reader tables come with the code that reads them (the three `kirigami_*` tables stay on rc1 with their kernels); `main` already holds three of them with identical content.
- **Clean-room parsers** (`src/cleanroom_readers/`, four files, no `crate::` import): rc1 includes them by `#[path]` from its reader modules; `M3` declares them as an ordinary module.
- **Vector generators are not taken.** They need `scripts/citations.py`, `tools/pinned.py`, `docs/facts/sources.toml` and the source cache, and `tools/gnome-vectors` exists only on `v0.8.0-tools`. Each table's header names its generator; a table is regenerated on rc1 if its reference ever changes. New vectors (`qt_lighter`) extend `main`'s `scripts/generate_qt_color_vectors.py` (PySide6).
- **Licences:** `NOTICE` on rc1 names Apache-2.0 for `platform/android_non_linear.rs`, `platform/m3_role.rs` and `src/ripple.rs`, and MIT for `platform/win_ui.rs`; the `ripple.rs` entry is dropped. `main` has no `NOTICE` and uses the workspace licence; both change at the cut, and only if a ported file is in the tree by then.
