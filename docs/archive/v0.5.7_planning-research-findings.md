# Research findings — dependencies, pitfalls, and open questions

The pre-implementation research that informed each phase: which crate was chosen
over which alternative and why, what not to hand-roll, the platform-specific traps
found before hitting them, and the questions that were genuinely open at planning
time along with how they were resolved.

Consolidated from the per-phase research records kept outside the source tree
(`.planning/phases/*/*-RESEARCH.md`) before that directory was removed. All
content is reproduced verbatim.

This is the "why not the other thing" record. The
[decision log](v0.5.7_planning-decision-log.md) says what was chosen; this says what was
rejected and at what cost. That matters most when revisiting a dependency: the
tradeoff that made `configparser` beat `rust-ini`, or `freedesktop-icons` beat a
hand-rolled spec implementation, is not recoverable from the source tree.

Related archive documents:

- [v0.5.7_planning-decision-log.md](v0.5.7_planning-decision-log.md) — what was ultimately decided
- [v0.5.7_planning-milestone-history.md](v0.5.7_planning-milestone-history.md) — which milestone each phase belongs to
- [v0.5.7_planning-deviations-and-deferrals.md](v0.5.7_planning-deviations-and-deferrals.md) — where research predictions did not survive contact with implementation

## How to read this

Four sections, each grouped by phase directory:

1. **[Alternatives considered](#alternatives-considered)** — dependency and approach choices with their tradeoffs.
2. **[Do not hand-roll](#do-not-hand-roll)** — problems where an existing crate or std facility was the right answer, and why.
3. **[Anti-patterns and pitfalls](#anti-patterns-and-pitfalls)** — traps identified before implementation. Many are platform quirks (KDE INI case sensitivity, premultiplied alpha on macOS, Windows font fallback chains) that would otherwise have to be rediscovered.
4. **[Open questions and their resolutions](#open-questions-and-their-resolutions)** — what was genuinely undecided at planning time. Each carries what was known, what was unclear, and the recommendation that was acted on.

Research was written before each phase ran, so some predictions were wrong.
Where implementation contradicted research, the
[decision log](v0.5.7_planning-decision-log.md) and
[deviations record](v0.5.7_planning-deviations-and-deferrals.md) hold the correction —
this document preserves what was believed at the time.

Phase numbers map to milestones via the phase index in
[v0.5.7_planning-milestone-history.md](v0.5.7_planning-milestone-history.md).

## Alternatives considered

Dependency and approach choices, with the tradeoff that decided each one.

### 01-data-model-foundation

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| serde_with for skip_serializing_none | Manual per-field annotations | serde_with adds a compile dep but eliminates ~50 lines of repetitive annotations and prevents forgetting one |
| Custom hex serde for Rgba | hex_color or serde-hex crate | Custom is ~60 lines, avoids an extra dependency in the always-on path; hex parsing is trivially correct |
| thiserror for Error enum | Manual Display + Error impls | thiserror is convenient but adds a proc-macro dep for ~30 lines of hand-written code; either works |
**Installation (Cargo.toml):**
```toml

name = "native-theme"
version = "0.1.0"
edition = "2024"
license = "MIT OR Apache-2.0"
[dependencies]
serde = { version = "1", features = ["derive"] }
serde_with = "3"
toml = "1"
```

### 03-kde-reader

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| configparser | rust-ini | rust-ini is also zero-dep and handles INI files, but configparser's `IniDefault` system gives explicit control over delimiters and case sensitivity needed for KDE files |
| configparser | Manual parsing | KDE INI files have edge cases (comments with `#`, multiline values in some configs, empty values like `ChangeSelectionColor=`); a tested parser avoids subtle bugs |
| dirs crate | std::env::var | `std::env::var("XDG_CONFIG_HOME")` + fallback to `$HOME/.config` is 5 lines of code; avoids adding a dependency just for one path lookup |
**Installation (Cargo.toml):**
```toml

[dependencies]

```

### 04-gnome-portal-reader

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| ashpd | Raw zbus 5.x | ashpd provides typed `ColorScheme`, `Contrast` enums and `Color` struct with `accent_color()` convenience. Raw zbus requires manual D-Bus interface/method calls, string-based namespace/key lookups, and manual `OwnedValue` deserialization. The abstraction saves ~100 lines and prevents typo bugs. |
| ashpd | dconf/GSettings directly | Portal is the correct abstraction for sandboxed apps (Flatpak, Snap). dconf requires direct filesystem/D-Bus access to GSettings backend. Portal works universally. |
**Installation (Cargo.toml changes):**
```toml
[features]
portal = ["dep:ashpd"]
portal-tokio = ["portal", "ashpd/tokio"]
portal-async-io = ["portal", "ashpd/async-io"]
[dependencies]
ashpd = { version = "0.13", optional = true, default-features = false, features = ["settings"] }
```

### 05-windows-reader

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| windows | windows-sys | windows-sys does NOT support WinRT APIs (UISettings). Only provides raw Win32 bindings. Would require a completely different approach for accent color (registry reading, which is fragile and undocumented). |
| windows | winapi (deprecated) | Unmaintained since 2021, does not support WinRT. Use windows crate instead. |
| windows (UISettings) | Registry HKCU\...\Personalize\AccentColor | Undocumented, fragile, does not track "automatic accent color" correctly. UISettings is the official API. |
**Installation (Cargo.toml changes):**

```toml
[dependencies]

    "UI_ViewManagement",

] }
```

### 17-bundled-svg-icons

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Raw `include_bytes!` per file | `include_dir!` crate | Adds a proc-macro dependency for directory-level inclusion; unnecessary for 42 known files with stable names |
| Raw SVG bytes | `icondata`-style decomposed struct | Decomposing SVGs into fields (viewBox, paths, etc.) adds complexity; our `IconData::Svg(Vec<u8>)` expects raw SVG bytes, so decomposition would need re-serialization |
| Checking in SVG files | Build script downloading at build time | Network dependency at build time is fragile; 42 small files (~18KB total) are trivially small for git |
| Static `&[u8]` returns | Pre-constructing `IconData::Svg` at compile time | `IconData::Svg(Vec<u8>)` uses owned `Vec<u8>`, which cannot be const; returning `&'static [u8]` and letting callers `.to_vec()` is cleaner and avoids forced allocation |
**Installation:**

### 19-macos-icon-loading

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| CGBitmapContext rasterization | NSBitmapImageRep.bitmapData | NSBitmapImageRep format varies (could be ARGB, float, planar); CGBitmapContext guarantees exact format |

**Dependency additions to Cargo.toml:**

```toml
    "CGBitmapContext", "CGColorSpace", "CGContext", "CGImage",
```

### 20-windows-icon-loading

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| GetGlyphOutlineW (GDI) | DirectWrite + D2D DrawGlyphRun | DirectWrite produces higher quality text but requires COM initialization, ID2D1Factory, IWICImagingFactory -- massive complexity for monochrome icon glyphs |
| GetGlyphOutlineW (GDI) | GDI ExtTextOut + CreateDIBSection | ExtTextOut destroys the alpha channel on 32-bit bitmaps -- unusable for transparent icon rendering |
| GetDIBits for HICON pixels | GetBitmapBits | GetBitmapBits is deprecated; GetDIBits with proper BITMAPINFOHEADER is the correct modern approach |
**Feature additions to Cargo.toml:**
```toml
#### Add Win32_UI_Shell to the existing windows dependency features:
windows = { version = ">=0.59, <=0.62", optional = true, default-features = false, features = [
    "UI_ViewManagement",
    "Win32_UI_WindowsAndMessaging",
    "Win32_UI_HiDpi",
    "Win32_Graphics_Gdi",
    "Win32_UI_Shell",        # NEW: SHGetStockIconInfo, SHSTOCKICONID, SHGSI_FLAGS
    "Foundation_Metadata",
] }
#### Update system-icons feature to include windows dep:
system-icons = ["dep:freedesktop-icons", "dep:objc2-core-graphics", "dep:windows", "material-icons"]
```
Note: The `windows` crate is NOT platform-gated in the dependency section (it already handles cross-platform via cfg internally), but it IS optional. Adding `"dep:windows"` to system-icons ensures the `windows` crate activates when `system-icons` is enabled. Since the `windows` crate itself only provides Windows APIs on Windows targets, this is safe.
Wait -- re-checking the existing Cargo.toml: `windows` is already in the top-level `[dependencies]` (not under `[target.'cfg(target_os = "windows")'.dependencies]`), and the `windows` feature already includes `"dep:windows"`. So `system-icons` does NOT need to add `"dep:windows"` -- the module just needs to be cfg-gated. The only change needed is adding `"Win32_UI_Shell"` to the windows crate features list.

### 28-bundled-svg-spinner-frames

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Static SVG files + include_bytes! | Inline SVG string literals in Rust | Files are easier to inspect, validate independently, and diff. Inline strings would avoid the file tree but make SVGs unreadable and untestable outside Rust. |
| Programmatic SVG generation at compile time (build.rs) | Static SVG files | Build-time generation adds complexity and makes frames harder to inspect. Static files are simpler and the frame count is small enough (~100 total across all sets). |
| Single-file Rust const arrays of SVG bytes | Separate .svg files per frame | Const arrays pollute source code and are harder to validate. Separate files match the existing `icons/` pattern. |

### 29-freedesktop-sprite-sheet-parser

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| String/regex viewBox rewriting | Full XML parser (quick-xml, roxmltree) | XML parser is overkill -- we only need to change the `viewBox` attribute value. String replacement is simpler, faster, and adds no dependency. The viewBox attribute has a predictable format in SVG files. |
| freedesktop-icons crate for icon lookup | Manual filesystem traversal | The crate already handles theme inheritance, hicolor fallback, XDG base dirs, and index.theme parsing. Manual traversal would duplicate all that. |
| Loading at runtime | Pre-parsing at compile time | Sprite sheets are theme-dependent and installed on the user's system. Runtime loading is the only option. |
**No new dependencies required.** All functionality uses existing crate dependencies.

## Anti-patterns and pitfalls

Traps identified during research, before implementation hit them.

### 01-data-model-foundation

- **Using #[serde(flatten)] with TOML:** Known issues with flatten in the toml crate. Flatten causes problems with `default`, `alias`, and round-trip serialization. Use natural struct nesting instead -- it maps cleanly to TOML table sections.
- **Wrapping sub-struct groups in Option<T>:** Creates double-Option ergonomic pain and complicates the merge macro. Use `#[serde(default)]` on non-Option sub-struct fields instead.
- **Manual merge() implementations:** Writing merge() by hand for each struct is the desynchronization risk identified in the roadmap. Always generate via the declarative macro.
- **Deriving PartialEq on structs containing f32:** ThemeFonts, ThemeGeometry, ThemeSpacing contain `Option<f32>`. Deriving PartialEq is fine for tests (exact equality after round-trip), but document that float comparison is exact, not approximate.

### 01-v0-3-2-quality-improvements

- **Adding OnceLock to from_system() or from_linux():** These are explicitly NOT to be cached (user decision).
- **Breaking the connector API:** `pick_variant` free functions must remain as deprecated wrappers, not be removed yet.
- **Adding XML parsing to colorize_svg:** Explicitly rejected by user decision.
- **Bypassing apply_config entirely:** Would lose side effects (light_theme/dark_theme Rc, highlight theme).

### 02-core-presets

- **Parsing at compile time with proc macros:** Don't use `static-toml` or custom proc macros. The presets are small; runtime deserialization with `toml::from_str()` on `&'static str` is negligible cost and keeps the build simple.
- **Lazy static / once_cell for parsed presets:** Don't cache parsed NativeTheme in a global static. Each `preset()` call should return a fresh owned `NativeTheme` so callers can freely mutate it (e.g., merge user overrides). The deserialization cost for ~100 lines of TOML is microseconds.
- **HashMap-based registry:** Don't use a HashMap for 3 entries. A match statement is clearer, faster, and catches missing cases at compile time.
- **Putting TOML content inline in Rust source:** Keep preset TOML in separate `.toml` files for readability, independent validation, and potential reuse by external tools.

### 03-kde-reader

- **Case-insensitive parser for KDE files:** KDE key names are PascalCase (`BackgroundNormal`, `ForegroundActive`). Using `Ini::new()` lowercases everything, causing lookup failures when you try to `get("Colors:View", "BackgroundNormal")`. Use `Ini::new_cs()` or `new_from_defaults()` with `case_sensitive: true`.
- **Default delimiters with configparser:** The default includes `:` as a delimiter. While section names still parse correctly (text between `[` and `]`), lines like `another:value` would be misinterpreted as key-value pairs. Use `delimiters: vec!['=']` to be safe.
- **Assuming both light and dark are available:** kdeglobals contains ONE color scheme. Populate only the detected variant (light or dark), leave the other as `None`.
- **Hardcoding `~/.config/kdeglobals`:** Must respect `XDG_CONFIG_HOME` environment variable.
- **Parsing all 60 KDE color keys:** Only map the ones that have semantic equivalents in `ThemeColors`. Unmapped keys are simply not used.

### 04-gnome-portal-reader

- **Returning Error when portal is unavailable:** The spec says fall back to Adwaita defaults, not fail. Only catastrophic errors (cannot construct Adwaita base) should produce Err.
- **Enabling ashpd default features:** This forces tokio on all consumers via feature unification. Always use `default-features = false`.
- **Clamping out-of-range accent color values:** Per the XDG portal spec, out-of-range RGB values (outside [0,1]) mean "no accent color set." Treat as None, not as a clamped color.
- **Providing a sync wrapper with block_on:** This creates problems when called from within an existing async runtime. Keep `from_gnome()` as `async fn` and let consumers handle the sync/async boundary.
- **Populating both light AND dark variants from portal:** Color scheme tells us which variant the user prefers. Populate only the selected variant (like KDE reader), use the corresponding Adwaita base variant.

### 05-windows-reader

- **Using UIColorType::Complement:** This variant throws an exception at runtime per Microsoft docs. Never pass it to `GetColorValue()`.
- **Reading registry for accent color:** The registry key `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize\AccentColor` is undocumented and does not track "automatic accent color" correctly. Always use UISettings.
- **Assuming UISettings always succeeds:** It requires WinRT, which requires Windows 10+. Always handle the `Err` case from `UISettings::new()`.
- **Naming the module `windows`:** The Rust module name `windows` would collide with the `windows` crate name in scope. Name the file/module `windows.rs` but use `#[path = "windows.rs"] mod windows_reader;` or simply name it `win.rs` to avoid ambiguity. Alternatively, use `mod windows` since Rust can disambiguate between the module and the external crate via the `::windows` (crate) vs `crate::windows` (module) paths, but be careful about confusion.

### 06-cross-platform-dispatch

- **Calling `from_gnome()` from `from_system()`:** `from_gnome()` is async. Blocking on it (via `block_on`) would require pulling in a runtime dependency (tokio/async-std). The reference design explicitly avoids this -- GNOME gets the Adwaita preset from `from_system()`.
- **Using `cfg!(...)` macro (runtime) instead of `#[cfg(...)]` (compile-time):** `cfg!()` evaluates to a bool at runtime but does NOT remove dead code. Using it for platform dispatch would cause compilation errors on platforms where the reader module is not available.
- **Exact string equality on XDG_CURRENT_DESKTOP:** The variable is a colon-separated list. Using `de == "KDE"` would miss `"ubuntu:KDE"` or `"KDE:plasma"`. Always split on `:` and check each component.
- **Adding detect-desktop-environment as a dependency:** The crate is well-made but we need exactly one 5-line check. Adding a dependency for this is over-engineering.

### 07-extended-presets

- **Inventing colors for the opposite variant:** Don't hand-pick arbitrary colors. Use official light/dark variants from each theme's documentation, or for Catppuccin use the Latte palette as the light base for all flavors.
- **Using alpha/opacity colors in hex strings:** Pre-compute all alpha colors to solid hex. The Rgba parser handles `#RRGGBBAA` format, but presets should use pre-computed solid colors for visual accuracy. Exception: shadow colors with alpha (e.g., `#00000040`) are fine since they are intentionally semi-transparent.
- **Forgetting to update all three locations:** Every new preset needs: (1) TOML file, (2) `include_str!()` constant, (3) match arm in `preset()`, (4) entry in `PRESET_NAMES`.
- **Copying Phase 2 font values blindly:** Each platform/community preset should have appropriate font families. Platform presets use their native font (Segoe UI, SF Pro, Roboto). Community presets use "sans-serif"/"monospace" since they are not tied to a platform.

### 08-documentation

- **Stale code examples:** Code blocks that reference nonexistent API or wrong field names. Prevention: `#[cfg(doctest)]` catches this on every `cargo test`.
- **Overly abstract examples:** Showing just `let theme = preset("default")?;` without showing what to DO with the theme. Each example must show end-to-end: load -> extract fields -> apply.
- **Toolkit version coupling:** Examples must NOT use toolkit-specific version numbers in comments or code. Write `egui::Color32` not "egui 0.33's Color32". The mapping pattern is stable across versions.
- **Documenting private API:** Only document the public re-exports from lib.rs. Don't mention internal module paths like `model::colors::CoreColors` -- use the re-exported `native_theme::CoreColors`.

### 09-cargo-workspace

- **Root package workspace instead of virtual:** Putting `[package]` in the root Cargo.toml makes `cargo test` only run root package tests by default. Virtual workspaces run all members.
- **Not setting `resolver = "3"` in virtual workspace:** Virtual workspaces have no `package.edition` to infer resolver from. Without explicit setting, Cargo defaults to resolver v1, which has worse feature unification behavior.
- **Hardcoding dependency versions in each member:** Use `[workspace.dependencies]` to define shared deps once. Members reference them with `{ workspace = true }`.
- **Flat connector directories at root:** Putting `native-theme-gpui/` at repo root creates clutter. Use a `connectors/` grouping directory.

### 10-api-breaking-changes

- **Partial migration:** Do NOT leave some code using `theme.colors.core.accent` and other code using `theme.colors.accent`. Every reference must be updated atomically per wave.
- **Name collision via `#[serde(flatten)]`:** Do NOT use serde flatten to combine sub-structs -- it creates confusing error messages and prevents `#[serde(deny_unknown_fields)]`. Use explicit flat fields.
- **Keeping sub-struct types public:** After flattening, remove `CoreColors`, `ActionColors`, etc. from public exports. They serve no purpose in the flat model.

### 11-platform-readers

- **Reading colors without setting NSAppearance.current:** NSColor semantic colors resolve to the *current* appearance. Without explicitly setting it, you get whatever appearance the process happens to have, which is unpredictable in non-GUI contexts.
- **Calling WinRT APIs without capability checks:** AccentDark/Light shades exist on Windows 10 10240+ but calling GetColorValue can return E_INVALIDARG on some Windows versions or SKUs. Always handle errors gracefully.
- **Blocking on D-Bus in synchronous contexts:** The portal reader is async. from_kde_with_portal must be async too. Don't use block_on() inside library code.
- **Linking gio/glib for a single gsettings read:** The GNOME font read is a single key lookup. Using std::process::Command to call `gsettings` avoids pulling in the entire GIO/GLib C dependency chain.

### 12-widget-metrics

- **Making sub-struct fields non-optional:** Every field MUST be `Option<f32>`. Toolkits need to know "was this specified?" vs "use my default."
- **Putting metrics in ThemeGeometry:** Widget-specific metrics are per-widget, not global geometry. They are a separate concern.
- **Using concrete sub-struct types as fields in ThemeVariant:** The requirement specifies `Option<WidgetMetrics>` as a single field, not 12 separate fields on ThemeVariant.
- **Exhaustive structs:** All sub-structs MUST be `#[non_exhaustive]` for future-proofing.
- **Deep nesting in TOML:** Keep TOML path depth reasonable. `[light.widget_metrics.button]` (3 levels) is the max.

### 13-ci-pipeline

- **`--all-features` on a single runner:** Will fail because `windows` + `macos` + `kde` cannot all compile on one platform.
- **Cross-product matrix (os x features):** Testing `--features macos` on `ubuntu-latest` will fail to compile. Use `include` to whitelist valid combos.
- **`cargo test --workspace --features X`:** Feature flags don't propagate to workspace members properly with `--workspace`. Use `-p native-theme --features X` instead.
- **Running `cargo fmt` on multiple platforms:** Formatting is platform-independent. Run once on `ubuntu-latest` only.
- **Skipping `fail-fast: false`:** If one matrix entry fails, you want to see ALL failures, not just the first.

### 14-toolkit-connectors

- **Intermediate data model:** Do NOT create a `ConnectorTheme` struct between NativeTheme and toolkit types. Map directly.
- **Hardcoded fallback colors in mapping functions:** Use the toolkit's defaults as fallback (e.g., `iced::Color::BLACK` for missing text), NOT custom constants scattered through the code.
- **Blocking on OS theme in examples:** Use `NativeTheme::preset("default")` as initial fallback in examples; OS theme reading may fail or be slow.
- **Exhaustive match on all 108 gpui-component fields in one function:** Split into logical groups (interactive states, list/table, sidebar, charts, etc.) for maintainability.
- **Using iced 0.13:** The project should use 0.14 which has warning in Palette and improved color generation.

### 15-publishing-prep

- **Publishing connector before core**: The iced connector depends on `native-theme` from crates.io, so core must be published and indexed first
- **Omitting version on workspace path dependency**: `cargo publish` fails for downstream crates if the workspace dependency lacks a `version` field
- **Setting rust-version higher than MSRV**: Edition 2024 requires Rust 1.85.0 minimum; do not set higher without testing
- **Forgetting readme in crate subdirectory**: `readme` in Cargo.toml is relative to the crate's directory, not the workspace root; each publishable crate needs its own README or a path that resolves correctly

### 16-icon-data-model

- **Nested enums for categories:** Don't create `IconCategory::Dialog(DialogIcon::Error)` -- the user locked the decision on flat prefixed naming.
- **Custom(String) variant:** Don't add catch-all string variants to IconRole -- the user explicitly excluded custom icons.
- **Cow<[u8]> in IconData:** Don't use `Cow<'a, [u8]>` -- it adds a lifetime parameter that infects every struct holding an `IconData`, making the API harder to use. Bundled SVGs (Phase 17) can cheaply `.to_vec()` from static `&[u8]` slices; the allocation is tiny (~2-5KB per icon).
- **Typed IconSet for TOML field:** Don't use `Option<IconSet>` for the TOML field -- user TOML files may contain icon set names that don't map to a known enum variant (e.g., a future icon set or a user-defined one). Keep it `Option<String>` for flexibility.

### 17-bundled-svg-icons

- **Downloading SVGs at build time:** Do not use a build script that fetches SVGs from the network. This breaks offline builds and hermetic CI. Check the SVG files into the repository.
- **Using a proc macro for inclusion:** Do not write a custom proc macro to iterate a directory and generate `include_bytes!` calls. For 42 known, stable files, explicit `include_bytes!` per file is simpler, more transparent, and easier to audit.
- **Returning `IconData` directly from bundled function:** Do not return `IconData::Svg(Vec<u8>)` -- this forces an allocation every time the function is called, even if the caller just wants to check existence. Return `&'static [u8]` instead.
- **Single mega-file embedding:** Do not concatenate all SVGs into one blob with an index. Individual `include_bytes!` per file is cleaner, and the compiler handles them efficiently for this small number of files.
- **Forgetting the `#[allow(unreachable_patterns)]` on match:** The `#[non_exhaustive]` wildcard arm generates unreachable pattern warnings inside the defining crate. Use `#[allow(unreachable_patterns)]` as established in `icons.rs`.

### 18-linux-icon-loading

- **Hardcoding `/usr/share/icons`:** The freedesktop spec mandates checking `$XDG_DATA_HOME/icons`, `$HOME/.icons`, and all `$XDG_DATA_DIRS/icons`. The crate handles this; do not bypass it.
- **Assuming SVG always exists:** Some themes or hicolor may only have PNG for certain icons. Use `.force_svg()` to prefer SVG, but handle the fallback to bundled icons when no SVG is found.
- **Ignoring the `-symbolic` suffix:** Adwaita (GNOME 42+) moved most action/status/UI icons to symbolic-only variants. A single-pass lookup will miss roughly half of all icons on GNOME desktops.
- **Using `.with_cache()` unconditionally:** The crate's cache uses `once_cell` and is process-global. For a library crate that consumers may use alongside their own `freedesktop-icons` usage, avoid polluting the cache. Only use `.with_cache()` if documented as a performance feature.

### 19-macos-icon-loading

- **Using lockFocus/unlockFocus:** These are deprecated since macOS 10.14. Use CGBitmapContext instead.
- **Assuming CGImage pixel format:** CGImages from `CGImageForProposedRect` may have various internal formats (BGRA, ARGB, premultiplied, etc.). Always normalize through CGBitmapContext.
- **Skipping unpremultiply:** CGBitmapContext only supports premultiplied alpha. The project's `IconData::Rgba` contract specifies straight alpha. Consumers (gpui, iced) expect straight alpha.
- **Hardcoding pixel dimensions:** SF Symbols are vector-based and render at the configured point size. The actual pixel dimensions come from the configured `NSImageSymbolConfiguration`, not a hardcoded constant.
- **Forgetting Retina scale:** On Retina displays, a 24pt symbol produces a 48px image. The function should accept a `size` parameter in pixels and configure the point size accordingly (or let the caller specify scale).

### 20-windows-icon-loading

- **Using ExtTextOut/DrawText for glyph rendering:** GDI text drawing functions destroy the alpha channel on 32-bit bitmaps, making them unusable for transparent icon rendering. Use `GetGlyphOutlineW` with `GGO_GRAY8_BITMAP` instead.
- **Assuming RGBA byte order from GetDIBits:** Windows GDI returns BGRA format. Failing to swap B/R channels produces icons with swapped red and blue channels.
- **Using GetBitmapBits instead of GetDIBits:** `GetBitmapBits` is deprecated since Win32. Use `GetDIBits` with a properly initialized `BITMAPINFOHEADER` (negative height for top-down, 32-bit, BI_RGB).
- **Forgetting to DestroyIcon after SHGetStockIconInfo:** The HICON returned must be freed with `DestroyIcon`. The `SHSTOCKICONINFO` docs explicitly state this responsibility.
- **Hardcoding "Segoe Fluent Icons" without fallback:** This font is only present on Windows 11 and newer Windows 10 installs. Always try "Segoe MDL2 Assets" as a secondary font, then bundled SVG as final fallback.
- **Skipping premultiplied alpha conversion for stock icons:** Stock icons from `SHGetStockIconInfo` may contain premultiplied alpha pixels. The same `unpremultiply_alpha()` pass from sficons.rs should be applied.

### 21-integration-and-connectors

- **Caching in the core crate:** Prior decision (Out of Scope in REQUIREMENTS.md) says "consumers cache at toolkit level; core crate is stateless." Do not add icon caching to `load_icon()`.
- **Encoding RGBA as PNG in the hot path:** If gpui needs encoded images, do the encoding once at load time, not on every render call.
- **Using `image` crate for PNG encoding:** The `image` crate is heavy; for simple RGBA-to-PNG encoding, use a lighter alternative like `png` crate or avoid the encoding entirely.
- **Blocking on resvg in UI thread:** SVG parsing + rasterization can take milliseconds. For real-time UIs, load icons on startup or in a background task.

### 22-core-trait-and-loading-functions

- **Adding associated types to IconProvider:** Breaks object safety. The user explicitly chose no associated type.
- **Cross-set fallback in load_custom_icon:** Explicitly forbidden. If a set returns None, that's the final answer.
- **Consuming `self` in trait methods:** Use `&self` for object safety and because enum variants are Copy.
- **Requiring `Clone + Copy + Hash + Eq` on the trait:** These are derived on concrete enums independently, not part of the trait.
- **Breaking `load_icon(IconRole, &str)` signature:** While pre-v1.0, the existing API should still compile. Add new functions alongside.

### 23-build-crate-and-code-generation

- **Generating code into `src/`:** Always use `OUT_DIR`. Generating into `src/` creates gitignore problems and merge conflicts.
- **Using relative paths in `include_bytes!`:** The generated file lives in `OUT_DIR`, so relative paths resolve from there, NOT from the project root. Always use `concat!(env!("CARGO_MANIFEST_DIR"), "/...")`.
- **Failing on first error:** Collect and report ALL validation errors before exiting, so the developer can fix everything in one pass.
- **Separate provider struct:** The design doc's `AppIconProvider` struct pattern is obsolete. The actual `IconProvider` trait (Phase 22) has no associated type -- the enum directly implements it.

### 24-linux-de-audit-and-freedesktop-de-aware-mapping

- **Adding LinuxDesktop variants for every compositor:** Hyprland, Sway, COSMIC, i3, awesome, etc. do NOT need their own variants. They use freedesktop icon themes just like other DEs. The `Unknown` variant (with `default` mapping) is the correct handler.
- **Reading XDG_CURRENT_DESKTOP at build time:** DE detection must happen at RUNTIME in the generated code, not at build time. The same binary may run on KDE today and GNOME tomorrow.
- **Caching detect_linux_de in generated code:** The existing `from_linux()` in `lib.rs` already calls `detect_linux_de()` without caching. The env var read is negligible. Generated code should follow the same pattern.
- **Validating DE keys against LinuxDesktop variants at build time:** The build crate does NOT depend on the core crate. It can hard-code the known DE key set, but should NOT import `LinuxDesktop`. Unknown DE keys in TOML (e.g., `{ cosmic = "...", default = "..." }`) should produce a build WARNING (not error) since the arm will never match at runtime but is not harmful.

### 25.1-icon-gaps-and-fallback-removal

- **Cross-set substitution:** Never return an icon from IconSet::Material when the caller asked for IconSet::Freedesktop. If the requested set does not have the icon, return `None`. The app decides how to handle absence.
- **Silent degradation:** The old pattern silently returned Material SVGs. This masks the fact that the platform icon is missing and prevents the app from making informed decisions.
- **Expanding known_gaps to hide problems:** The known_gaps list must be small and reviewed. Adding a gap should require justification.

### 25-connector-integration

- **Don't use `<P: IconProvider>` as a type parameter on structs:** These are free functions, not trait implementations. Use `impl IconProvider` in the function signature.
- **Don't add a separate `load_custom_icon` wrapper in each connector:** The core crate already handles loading. Connectors only handle conversion.
- **Don't return `Result`:** The existing helpers return `Option`. Custom helpers must match this pattern (CONN-03).
- **Don't add new feature gates for the helpers:** They work with whatever features the consumer has enabled on `native-theme`.

### 27-animation-data-model-and-breaking-changes

- **Adding AnimatedIcon variants to IconData:** The design doc explicitly chose a separate type. Do NOT add `AnimatedIcon` as a variant inside `IconData` -- they are different type categories (static vs animated).
- **Deprecating StatusLoading instead of removing:** The user locked the decision to remove, not deprecate. Pre-1.0 crate, breaking changes are expected.
- **Making loading_indicator() return a compile error for disabled features:** User explicitly reconsidered and chose the None-returning pattern consistent with load_icon().
- **Mixing icon sets in loading_indicator():** Must follow the no-cross-set-fallback rule from the MEMORY.md critical rules.

### 28-bundled-svg-spinner-frames

- **Inline SVG strings in Rust source:** SVG content should be in `.svg` files, not as `const FRAME_0: &[u8] = b"<svg>..."` literals. Files are inspectable, diffable, and can be validated by external SVG tools.
- **Using SMIL or CSS animation in SVG frames:** resvg does not support SMIL animation or CSS keyframes. Each frame must be a static SVG snapshot. The animation happens by cycling frames, not within a single SVG.
- **Generating SVG at runtime via format!():** Runtime string formatting for SVG introduces potential XML injection, encoding issues, and makes frames non-cacheable. Use pre-authored static files.
- **Mixing icon sets for spinner fallback:** Per project rules (MEMORY.md), never substitute from another icon set. If `material-icons` feature is disabled, `loading_indicator("material")` must return None, not fall back to Lucide.
- **Using the existing `progress_activity.svg` for Material spinner frames:** The existing file has `viewBox="0 -960 960 960"` (Material's native 960x960 coordinate space). Spinner frames must use `viewBox="0 0 24 24"` per SPIN-06. Create new frame SVGs.

### 29-freedesktop-sprite-sheet-parser

- **Using a full XML parser:** The viewBox attribute has a well-defined format (`"minX minY width height"`). String find-and-replace is sufficient and avoids pulling in a parsing dependency. The SVG is valid as-is; we only change one attribute value.
- **Attempting to split the SVG DOM into separate elements per frame:** The sprite sheet's `<path>` elements use absolute coordinates that are already correct relative to the full viewBox. Rewriting just the viewBox "windows" into the right frame without touching any paths.
- **Looking up animation icons at size 24:** Breeze stores animated icons at sizes 16 and 22 (not 24). Use size 22 for the animation lookup. The existing `find_icon()` for static icons uses 24, but sprite sheets live in `animations/22/` directories.
- **Caching the loaded sprite sheet in a static:** The `loading_indicator()` function is already not cached (it constructs a new `AnimatedIcon` each call). Keep it consistent. The filesystem read is fast enough for a function called once per application lifetime.

### 30-reduced-motion-accessibility

- **Separate module file for a single function:** The existing pattern puts small utility functions in `lib.rs`. Do NOT create an `accessibility.rs` module for one function.
- **Async implementation:** The requirements explicitly state sync. The Out of Scope section in REQUIREMENTS.md says "Async prefers_reduced_motion -- Sync is sufficient; D-Bus portal not needed when gsettings works."
- **Feature-gating the function itself:** The function should always be available. Only the platform backends need `cfg` gating. On unsupported platforms, it should return `false`, not be absent.

### 31-connector-integration

- **Connector owns animation state:** The connector is a pure data conversion layer. It must NOT store frame indices, timers, or elapsed time. That belongs to the application.
- **Adding full iced as dependency:** The iced connector depends only on iced_core. Adding the full iced crate would pull in a GPU backend, windowing system, and async runtime -- unacceptable for a thin conversion layer.
- **Rasterizing every frame on each tick:** Pre-convert all frames to ImageSource/svg::Handle once, then index into the pre-built Vec. The gpui connector's SVG rasterization (svg_to_bmp_source) is expensive.
- **Ignoring prefers_reduced_motion():** Applications should check `native_theme::prefers_reduced_motion()` and either show the static first_frame() or disable animation. Document this in function doc comments but do NOT enforce it in the connector (the app decides).

### 33-quick-fixes-and-version-consistency

- **Updating versions in archived design docs:** `docs/custom-icon-roles.md` line 606 has `"0.3"` but since it's a historical design doc being archived, do NOT update the version reference -- leave it as-is for historical accuracy.
- **Adding `#![warn(missing_docs)]` without checking current doc coverage:** Running `cargo doc` first to see how many warnings appear helps gauge if there are many undocumented items that would spam the build output. If the count is manageable, add the attribute. If hundreds of warnings appear, it may be better to defer until docs are added.

### 34-animated-icon-documentation

- **Duplicating the full API reference in README:** READMEs should show usage patterns and link to docs.rs for full details. Do not reproduce all function signatures.
- **Using `rust` (not `ignore`) for code examples that need features:** README code blocks are not compiled by default. Use `rust,ignore` for examples that require feature flags or toolkit contexts.
- **Inconsistent formatting across READMEs:** Follow the exact heading level, backtick-quoting, and link style used in each README's existing sections.

### 35-animated-icon-showcase-examples

- **Calling `animated_frames_to_image_sources()` or `animated_frames_to_svg_handles()` on every frame tick:** These do SVG rasterization. Cache the result once at init/icon-set-change time.
- **Using `Rotation::Solid` for iced spin animations:** Causes layout jitter during rotation. Must use `Rotation::Floating`.
- **Hardcoding frame counts or durations:** Read `frame_duration_ms` and `frames.len()` from the `AnimatedIcon` data. Different icon sets have different frame counts (Material: 12, freedesktop: 20, Windows: 60) and timings.
- **Mixing icon sets:** Never substitute a spinner from one set when another set is selected. If `loading_indicator("lucide")` returns the Lucide spinner, show Lucide. If a set returns `None`, show a "not available" placeholder.
- **Running animation timer when Icons tab is not active:** Waste of CPU. Only tick when the Icons tab (or animated section) is visible.

### 36-screenshot-and-gif-generation

- **Attempting Wayland screen recording with X11 tools:** grim, maim, scrot all fail on KDE Wayland. Only spectacle works reliably.
- **Interactive GUI automation (xdotool-style):** xdotool is X11-only and won't work on Wayland. KDE Wayland has no equivalent for window-level input automation.
- **Recording full animation cycles via screen capture:** Wayland KDE lacks scriptable screen recording. Frame-based compositing from SVGs is more reliable and reproducible.
- **Storing assets in root `assets/`:** Root `assets/` is for application graphics (icons etc). Documentation graphics go in `docs/assets/`.

### 37-community-files-and-github-templates

- **Over-engineering templates:** This is a small-to-medium Rust crate, not a corporate monorepo. Keep templates short and focused. Two issue forms (bug + feature) plus one PR template is sufficient.
- **Requiring too many fields:** Mark most fields as `required: false`. Only the core description should be mandatory. Over-requiring fields discourages reports.
- **Stale version lists in templates:** Do NOT hardcode version numbers in dropdown options. Use a textarea/input field and ask users to paste `cargo tree | grep native-theme` output instead, so templates never go stale.
- **Copying the Rust Code of Conduct verbatim for a non-Rust-org project:** The Rust CoC is for Rust project participants. Individual crates should use Contributor Covenant, which the Rust CoC is based on.
- **Putting SECURITY.md in .github/:** While supported, root-level is more discoverable for cloners and GitHub recognizes both locations.

### 38-ci-smoke-tests-and-release

### 43-self-capture-screenshots-with-window-decorations

- **Using PrintWindow on GPU-rendered windows:** Both gpui (blade-graphics) and iced (wgpu) use Vulkan/OpenGL. PrintWindow sends GDI messages that GPU windows don't handle -- client area comes back black. Always use BitBlt from screen DC.
- **Using CGWindowListCreateImage on macOS 15+:** Deprecated and removed. Use `screencapture` CLI or ScreenCaptureKit instead.
- **Assuming no permission needed on macOS:** Since macOS 14, even own-window capture with CGWindowListCreateImage needs screen recording auth. CI needs TCC.db workaround.

### 44-per-widget-data-model-and-preset-migration

- **Splitting the ThemeVariant rewrite across multiple commits with partial TOML migration:** The old and new TOML formats are incompatible. If ThemeVariant changes but TOMLs are not yet updated (or vice versa), all 17 preset deserialization tests fail. The struct rewrite and all 17 TOML rewrites MUST be in the same commit.
- **Putting derived fields in cross-platform presets:** Per the design doc, fields like `button.primary_bg` (derived from `defaults.accent`) should NOT appear in any TOML. `resolve()` fills them. Including them defeats DRY and creates inconsistency.
- **Using `Option<FontSpec>` on ThemeDefaults for font/mono_font:** The design doc specifies plain `FontSpec`. A default FontSpec (all None) already means "not set". Wrapping in Option adds a third state (None vs Some(all-None)) that complicates merge logic.

### 45-resolution-engine

- **Resolving fields in random order:** Dependencies between inheritance rules mean order matters. Always use the 4-phase structure.
- **Panicking on None in validate():** Must collect ALL missing fields, not fail-fast on the first one. Users need the complete list.
- **Implementing Deserialize on ResolvedTheme:** This is an output type. Input is always ThemeVariant.
- **Hardcoding fallback colors in resolve():** resolve() copies from `defaults.X`, never from hardcoded hex values. Hardcoded values are forbidden per project memory.
- **Using unwrap_or_default() for resolution:** `or(defaults.X)` is the only correct pattern. Default trait values would produce nonsensical themes.

### 46-os-reader-extensions

- **Hardcoding fallback values in readers:** Readers must NOT contain color/font fallbacks. If the OS API returns nothing, the field stays `None`. Fallbacks come from the platform TOML overlay or `resolve()`. This is explicitly stated in the project's CLAUDE.md-equivalent memory: "No hardcoded theme values."
- **Embedding presets in readers:** The GNOME reader currently embeds Adwaita. Readers should be pure OS data extractors. Preset loading belongs in the pipeline.
- **Mixing old and new model types:** All references to `ThemeColors`, `ThemeFonts`, `ThemeGeometry`, `WidgetMetrics` must be eliminated. Readers populate `ThemeVariant` directly.
- **Testing OS API calls directly:** All readers must have a testable core function (e.g., `build_theme()` or `from_kde_content()`) that accepts parsed data and returns a `NativeTheme`. OS API calls happen in one thin outer function.

### 47-os-first-pipeline

- **Resolving after merge but before app overlay:** The first resolve fills derived fields. If the app overlay changes a source field (e.g., accent), the derived fields are stale. Must re-resolve after each merge.
- **Returning ResolvedTheme without keeping ThemeVariant:** If a consumer wants to apply an overlay later, they need the pre-validate ThemeVariant. But this conflicts with the goal of returning only ResolvedTheme. Solution: the overlay API should internally retain the ThemeVariant.
- **Merging onto ResolvedTheme:** ResolvedTheme has no merge(). Overlays must be applied to ThemeVariant before validate(). The pipeline must enforce this ordering.
- **Double-embedding preset in GNOME:** The GNOME reader already loads the adwaita preset internally. If the pipeline also loads it, the preset gets loaded twice. Solution: either (a) have the pipeline skip preset loading for GNOME since from_gnome() already does it, or (b) refactor from_gnome() to return a sparse variant like other readers and let the pipeline handle the preset merge uniformly.

### 48-connector-migration

- **Re-introducing fallback defaults in connectors:** The whole point of ResolvedTheme is that resolution already happened. Connectors must NOT re-derive fallback values. If a connector needs a color, read it from the resolved struct. If the field doesn't exist on the resolved struct, it means it genuinely doesn't apply.
- **Keeping ThemeVariant as connector input "for backwards compatibility":** Old API consumers can trivially adapt by calling `resolve()` + `validate()` before passing to the connector. Don't maintain dual entry points.
- **Ignoring per-widget fields:** ResolvedTheme has 25 per-widget structs with direct color and geometry data. Connectors should prefer per-widget values (e.g., `resolved.button.background`) over deriving from base colors (e.g., `resolved.defaults.surface`).

### 49-additive-type-definitions

- **Adding BorderSpec fields to widget structs in Phase 49:** Phase 49 is additive type definitions ONLY. Widget integration (replacing flat `border`, `radius`, `padding_horizontal` etc. with `border: Option<BorderSpec>`) happens in Phase 50.
- **Modifying resolve.rs:** Resolution engine changes are Phase 51. Phase 49 only defines the types.
- **Modifying presets:** Preset rewriting is Phase 50. Phase 49 only defines structs that presets will eventually use.
- **Adding LayoutTheme to ThemeVariant:** The user explicitly decided layout lives on ThemeSpec, not ThemeVariant.
- **Making LayoutTheme fields non-Option in LayoutTheme (not Resolved):** The Option-variant struct must use `Option<f32>` for merge semantics. Only `ResolvedLayoutTheme` has concrete `f32` fields.

### 50-atomic-schema-commit

- **Partial rename:** Never leave the codebase in a state where some fields use old names and others use new names. The entire change must compile atomically.
- **serde(rename) aliases:** Decision was already made (pre-1.0, presets bundled): no aliases. Clean break.
- **Changing resolve.rs inheritance logic:** Phase 50 only renames field references in resolve.rs. The inheritance rules themselves stay the same -- Phase 51 fixes those.
- **Adding interactive state colors:** Phase 52 handles those. Phase 50 only adds the non-state fields listed in SCHEMA-06.

### 51-resolution-engine-overhaul

- **Inventing values in resolve():** NEVER add fallback values not in inheritance-rules.toml. If a field has no inheritance rule, it must come from preset/OS reader and validate() catches missing ones.
- **Partial border inheritance:** Don't inherit only some sub-fields. Either a widget is in `border_inheritance.widgets_with_border` (gets all 4 sub-fields) or it isn't (gets nothing from defaults). Sidebar and status_bar get explicit color+line_width only.
- **Font color = text_color:** The current code sets `font.color = d.text_color` in resolve_color_inheritance. With the new resolve_font() handling all 5 sub-fields including color, this should flow through defaults.font.color (which equals defaults.text_color). The defaults.font.color must be set from defaults.text_color in defaults_internal.
- **Mixing resolve and validate placeholders:** The 57 placeholder bindings at lines 1966-2025 exist to satisfy the ResolvedThemeVariant constructor. Phase 51 must replace ALL of them with proper require() calls.

### 52-interactive-state-colors

- **Adding fields to presets in this phase:** Preset values are Phase 53 scope. Fields should remain None in presets.
- **Inventing inheritance rules not in platform-facts.md:** Every rule must be documented. If all 4 platforms show distinct values, the field has no_inheritance.
- **Forgetting validate():** Every new field needs a `require()` call AND inclusion in the `Resolved*Theme { ... }` construction block. Missing either causes compile errors.
- **Forgetting property-registry.toml:** This is the source of truth. If a field is in the struct but not the registry, audit tests will eventually catch it.

### 53-preset-completeness

- **Inventing color values** -- every value must be traceable to platform-facts.md or the theme's official palette. Never make up a hex color.
- **Using ratio-derived text_scale values** -- the whole point of PRESET-02 is to eliminate the 0.82x/1.0x/1.2x/2.0x pattern.
- **Changing light values on the dark side** -- each variant (light/dark) has different state colors. Do not copy light hover colors to dark variant.
- **Forgetting line_height** -- text_scale entries may also have `line_height` values that need updating when size changes.

### 54-connector-migration

- **Mapping semantic mismatches:** gpui's `tc.primary` comes from `button.primary_background` but `button.hover_background` is the DEFAULT button hover, not the primary button hover. Do not blindly map `tc.primary_hover = button.hover_background` -- see Open Questions.

- **Changing test semantics:** Existing tests verify `tc.primary_hover != tc.primary`. After migration, tests should verify the value matches the resolved theme field, not just that it differs.

### 55-correctness-safety-ci

- **Not using `try_wait()` polling for subprocess timeout**: `Command::output()` blocks indefinitely. Always use spawn + try_wait for external processes that might hang.
- **Not silencing all publish errors**: `continue-on-error: true` hides real failures. Use exit-code-based detection or `--skip-if-version-exists` flags.
- **Modifying example names without updating scripts**: `scripts/generate_screenshots.sh` and `scripts/generate_gpui_screenshots.sh` may reference `showcase` by name.

### 56-testing

- **Generating only fully-populated themes:** Property tests must also generate sparse themes (many None fields) to catch skip_serializing_if/serde(default) edge cases. The existing `fully_populated_variant()` helper only covers the dense case.
- **Floating-point exact equality in round-trips:** TOML f32 values may have representation differences. Use the existing PartialEq (which compares f32 bitwise via derive) since TOML's toml crate preserves f32 precision for reasonable values. If tests fail on edge cases (NaN, Infinity), constrain the strategy to exclude them.

### 65-themewatcher-core-api

- **Putting theme data in the event:** The event should be a signal, not carry `ResolvedThemeVariant`. This avoids coupling the watcher to the resolution pipeline and keeps the watcher simple.
- **Using `Arc<AtomicBool>` for shutdown instead of a channel:** An atomic bool requires polling in the watcher thread. A channel integrates naturally with `mpsc::Receiver::recv_timeout()` used in the debounce loop, so the thread can block efficiently waiting for either a file event or a shutdown signal.
- **Making ThemeWatcher Clone:** The handle owns a thread. Cloning would create ambiguous ownership of shutdown. It must be a move-only type.
- **Blocking in Drop forever:** The `join()` in Drop must not hang. The shutdown signal must cause the background thread to exit promptly. Use `recv_timeout()` patterns in the watcher loop, not `recv()` which blocks indefinitely.

### 66-linux-watchers

- **Watching individual files directly with inotify:** KDE uses `QSaveFile` atomic writes (tmp file + rename). A watch on the file inode is lost when the file is replaced. Always watch the parent directory. [VERIFIED: KDE phabricator D14890, D7671]
- **Exposing tokio to the consumer:** The `on_theme_change()` API is sync. Use `zbus::blocking` which handles async reactor internally. Never `#[tokio::main]` or `Runtime::new()` in the library. [CITED: docs.rs/zbus/latest/zbus/blocking]
- **Watching the entire ~/.config/ recursively:** Would fire on every config file change from any app. Watch `NonRecursive` + filter by filename. [Phase requirement: success criterion 3]
- **Using notify-debouncer-mini for debouncing:** Adds an unnecessary dependency for a 10-line `Instant` check. The debounce logic is trivial for 2 files.

### 67-macos-windows-watchers

- **Running CFRunLoop::run() without a stop mechanism:** `CFRunLoop::run()` blocks forever. Must either use `run_in_mode()` with timeout for periodic shutdown checks, or store the `CFRunLoop` handle and call `stop()` from the Drop handler.
- **Creating UISettings without COM STA:** UISettings is a WinRT type requiring STA initialization. Without `CoInitializeEx(COINIT_APARTMENTTHREADED)`, event callbacks will not fire.
- **Forgetting the message pump on Windows:** WinRT events on an STA thread are dispatched via the Windows message loop. Without `GetMessageW`/`DispatchMessageW`, `ColorValuesChanged` events are never delivered.
- **Letting UISettings go out of scope:** The `UISettings` instance must remain alive for the entire watcher lifetime. If it is dropped (e.g., local variable in a short-lived scope), the event subscription is cancelled.
- **Using NSApplication for the macOS watcher:** `NSApplication` creates a full app process with menu bar entry. `NSDistributedNotificationCenter` works without it -- just needs a running run loop.
- **Calling unsafe Objective-C FFI without #[allow(unsafe_code)]:** The crate has `#![deny(unsafe_code)]` at the crate root. Platform watcher modules need `#![allow(unsafe_code)]` at the module level, matching the pattern in `macos.rs` line 7.

### 68-implement-docs-todo-v0-5-6-gtk-icon-theme-md

- **Modifying connectors instead of the core crate:** Connectors cannot distinguish symbolic from non-symbolic icons. Replacing `#2e3436` at the connector level would affect ALL SVGs, including non-symbolic ones that legitimately use that color. [VERIFIED: spec Section 3, Option B analysis]

## Open questions and their resolutions

What was genuinely undecided at planning time, with the recommendation acted on.

### 01-data-model-foundation

1. **Naming collision in nested colors: `surface` appears as both a CoreColors field and a ThemeColors sub-struct group name (SurfaceColors)**
   - What we know: The IMPLEMENTATION.md uses `surface` as a CoreColors field (card/view/content background) and the research proposes SurfaceColors as a group for sidebar/tooltip/popover
   - What's unclear: Whether the TOML path `colors.surface.sidebar` reads well or is confusing (does `surface` refer to the surface color or the surface group?)
   - Recommendation: Rename the CoreColors field to `content_background` or keep `surface` and name the group `panels` instead of `surface`. Alternatively, rename the sub-struct to `SurfaceVariants` or `PanelColors`. The planner should make a decision here. A simple rename of the group to something like `panel` avoids the collision: `[light.colors.panel]` for sidebar/tooltip/popover.
2. **serde_with dependency weight**
   - What we know: serde_with 3.17.0 is a proc-macro crate that adds compile time
   - What's unclear: Whether the compile-time cost is acceptable for a library crate that aims to be lightweight
   - Recommendation: Use serde_with. The alternative is ~50 identical `#[serde(skip_serializing_if = "Option::is_none")]` annotations. The compile-time cost is paid once and is modest. If compile time becomes a concern, these annotations can be added manually later as a mechanical replacement.
3. **NativeTheme merge behavior for `name` field**
   - What we know: NativeTheme has a `name: String` field. The merge macro handles `Option<T>` and nested structs, but `name` is a plain `String`.
   - What's unclear: Should merge replace the name? Keep the base name? Concatenate?
   - Recommendation: Keep the base name (do not replace). The name identifies the base theme. If the user wants a different name, they set it explicitly after merge. NativeTheme.merge() should handle name separately from the macro (it already needs custom logic for Option<ThemeVariant> fields).

### 01-v0-3-2-quality-improvements

1. **gpui-component apply_config future changes**
   - What we know: v0.5.1 `apply_config` overwrites all colors and sets non-color fields. All Theme fields are pub.
   - What's unclear: Whether future gpui-component versions might add more side effects to `apply_config`.
   - Recommendation: Keep the apply_config pattern with improved comments. It's more future-proof than bypassing it.
2. **#[must_use] on NativeTheme type -- test impact**
   - What we know: Adding `#[must_use]` to the type will warn on any unused NativeTheme value, including in tests.
   - What's unclear: Whether any existing tests create NativeTheme without using the value.
   - Recommendation: Add `#[must_use]` to the type; fix any resulting test warnings with `let _theme = ...` or actual assertions.

### 02-core-presets

1. **Font family names for presets**
   - What we know: KDE Breeze uses "Noto Sans" (default install), Adwaita now uses "Adwaita Sans" (based on Inter, since GNOME 48), monospace is "Adwaita Mono" (based on Iosevka).
   - What's unclear: Should presets use the actual platform font names (may not be installed cross-platform) or generic names like "sans-serif"?
   - Recommendation: Use actual platform font names in KDE/Adwaita presets (these are the correct values when running on those platforms). Use generic names in the "default" preset. Consuming apps handle font fallback.
2. **Adwaita foreground color with alpha**
   - What we know: libadwaita uses `rgb(0 0 6 / 80%)` for light-mode foreground, which is a near-black with 80% opacity.
   - What's unclear: Should the preset use the alpha-blended color or pre-compute against white background?
   - Recommendation: Pre-compute to a solid color for simplicity. 80% of rgb(0,0,6) on white = approximately #333336. This is the practical color that users see. Alternatively, use the traditional GTK foreground #2e3436 which is what most Adwaita implementations use.
3. **Spacing and geometry values for Adwaita/Breeze**
   - What we know: Exact spacing scales are not standardized in the color scheme files.
   - What's unclear: What are the "correct" spacing values for each platform?
   - Recommendation: Use sensible defaults that match visual inspection of each platform. KDE Breeze: typically 2,4,6,8,12,16,24. Adwaita: typically 2,4,6,12,18,24,36 (6px base grid). Document that these are approximations.

### 03-kde-reader

1. **Should from_kde() also read `/etc/xdg/kdeglobals` as a fallback?**
   - What we know: `$XDG_CONFIG_HOME/kdeglobals` is the per-user file. `/etc/xdg/kdeglobals` is the system default.
   - What's unclear: Whether we should merge system defaults with user overrides (KDE itself does this).
   - Recommendation: For v1, read only the user file. If missing, return `Error::Unavailable`. System-level fallback can be added later. Keep it simple.
2. **Should the theme name be extracted from kdeglobals?**
   - What we know: `[General] ColorScheme=BreezeDark` gives the scheme name. `[KDE] LookAndFeelPackage=org.kde.breezedark.desktop` gives the global theme.
   - What's unclear: Which one to use, or whether to hardcode "KDE" as the name.
   - Recommendation: Use `[General] ColorScheme` if available, fall back to "KDE" as the theme name.
3. **Should we populate both light AND dark variants?**
   - What we know: kdeglobals has ONE color scheme. KDE Breeze preset has both variants because we hand-authored them.
   - What's unclear: Whether users expect both variants from a live reader.
   - Recommendation: Populate only the detected variant (light or dark). Leave the other `None`. Users who want both can merge with the `kde-breeze` preset for the missing variant.

### 04-gnome-portal-reader

1. **Should `from_gnome()` populate BOTH light and dark variants?**
   - What we know: Portal tells us the user's preference (dark/light). Adwaita base has both variants.
   - What's unclear: Whether to return both Adwaita variants (with accent applied to each) or only the active one.
   - Recommendation: Populate only the active variant (matching KDE reader pattern). Users who want both can merge with `preset("adwaita")`. This is consistent with the KDE reader behavior.
2. **Should the bare `portal` feature work without specifying a runtime?**
   - What we know: ashpd with `default-features = false` and `features = ["settings"]` but no runtime feature will fail to compile (zbus needs a runtime).
   - What's unclear: Whether `portal` alone (without `portal-tokio` or `portal-async-io`) should be a valid feature.

1. **Other GTK-convention icon themes (Yaru, elementary, Pop)**
   - What we know: The spec says these themes use the same GTK convention. Adwaita is verified on this system. Yaru/elementary/Pop are not installed.
   - What's unclear: Whether they use exactly the same four hex colors or have theme-specific variations.
   - Recommendation: The four colors (`#2e3436`, `#2e3434`, `#222222`, `#474747`) are the Tango palette standard that GTK defines. Other GTK-convention themes are expected to use the same palette. If a theme uses different colors, those icons would still render (just with their original dark colors, same as today). This is a progressive improvement, not all-or-nothing. No action needed now.
2. **GTK4 `.gpa` format icons**
   - What we know: GTK 4.16+ introduced a new `.gpa` icon format with named symbolic colors. [CITED: https://docs.gtk.org/gtk4/icon-format.html]
   - What's unclear: Whether any icon theme ships `.gpa` files instead of/alongside `-symbolic.svg` files.
   - Recommendation: `freedesktop-icons` crate uses `force_svg()` which only finds SVG files. `.gpa` files would not be found. This is a future concern, not a blocker for this phase.
3. **`load_freedesktop_spinner` -- does it need normalization?**
   - What we know: No. Adwaita has no `process-working` icon. Breeze has one but uses `currentColor` already. The spinner function uses direct `freedesktop_icons::lookup` calls, not `find_icon`. [VERIFIED: no `process-working*` files in Adwaita icons on this system; Breeze's spinner uses `currentColor`]
   - Recommendation: No changes to `load_freedesktop_spinner`. The spec explicitly lists it as unchanged.
