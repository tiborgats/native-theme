## Principled deviations

Two deviations were formalised in the design record rather than fixed, because
the root cause sits outside this project. Both are documented in full in
[v0.5.7_gaps.md](v0.5.7_gaps.md) §G10 and §G11.

**§G11 — `cargo test --workspace` is not the release gate.** `naga 27.0.3`, pinned
transitively by `gpui-component`, fails to compile against `codespan-reporting
0.12.0`, which removed the `impl WriteColor for String` that naga relied on. No
fix exists inside this project: `naga 27.0.4` does not exist on crates.io, and
28.x is rejected by gpui-component's semver pin. The accepted resolution is that
`pre-release-check.sh`'s per-crate posture *is* the gate, with
`native-theme-gpui` treated as a soft check. Re-evaluation trigger:
`cargo update -p gpui-component && cargo test --workspace --all-features` — when
that passes, the workspace-scope criterion can be restored.

**§G10 — Windows dialog button order.** The gap document asserted that modern
WinUI 3 uses primary-rightmost and that `platform-facts.md` tracked an obsolete
Win7 guideline. Live Microsoft WinUI 3 Dialog controls documentation
(`ms.date 2025-08-05`, verified 2026-04-20) states the opposite: `PrimaryButton`
appears leftmost, `CloseButton` rightmost. The premise was inverted; the existing
documentation was already correct, and the "required fix" would have introduced a
bug. Resolved by appending a modern continuity citation rather than editing the
claim. The code sites now agree on `PrimaryLeft`
(`native-theme/src/windows.rs:525`, `presets/windows-11.toml`,
`resolve/inheritance.rs:71`).

The general lesson recorded from §G10: when a plan's premise is contradicted by a
live-verified source, stop and re-verify the canonical source before executing.
Revise scope by appending to the plan rather than rewriting it, so the original
premise and the correction both survive.

# Named deviations and deferrals, v0.5.1–v0.5.4

Recorded in a longer form during the API-review milestones, several with explicit revisit conditions.

### 01-01 — 01-core-crate-api

#### Key Decisions

- `ResolvedFontSpec` stays named as-is (already has `Spec` suffix matching `FontSpec`), but moved from `model::widgets` to `model::font` for module consistency.
- Existing `resolve()` and `validate()` methods kept for debugging/advanced use alongside the new `into_resolved()`.

#### Notes

- A pre-existing `naga` dependency compilation error (transitive via gpui) prevents `cargo test --workspace` from running, but all 4 project crates build, test, and lint cleanly.

### 01-02 — 01-core-crate-api

#### Deviation: Linux Portal Path Deferred

**What:** AC-4 (Linux D-Bus portal query in `system_is_dark()`) was not implemented.

**Why:** `ashpd` is async-only — no blocking/synchronous API for portal settings queries. Using its transitive `zbus` dependency directly would be fragile and could break if ashpd changes internals. Building an async runtime just for one sync function is over-engineered.

**Impact:** Low. The gsettings subprocess approach works on all major Linux DEs. KDE already has a file-based fallback (no subprocess) when `kde` feature is enabled. Apps needing portal-based detection use the async `from_system()` pipeline.

**Revisit when:** ashpd adds a sync/blocking API, or if subprocess failures are reported in sandboxed environments (Flatpak/Snap).

### 01-03 — 01-core-crate-api

#### Deviation: ThemeVariant::icon_set Kept as Option\<String\>

**What:** AC-2 was not implemented. `ThemeVariant::icon_set` and `ResolvedThemeVariant::icon_set` remain as `Option<String>` / `String`.

**Why:** The field is dual-purpose:
- In TOML presets: stores icon naming convention ("freedesktop", "sf-symbols") matching `IconSet` variants
- In platform readers (KDE/GNOME): stores the system's icon theme name ("Adwaita", "breeze", "Papirus") which is NOT an `IconSet` variant

Changing to `Option<IconSet>` would break KDE reader (`variant.icon_set = Some(theme_name)` where `theme_name = "breeze"`) and GNOME reader (`variant.icon_set = Some(icon_theme)` where `icon_theme = "Adwaita"`).

**Impact:** Low. The function signatures are the primary safety improvement — typos in icon set names are now compile errors. The field type change would require separating "icon naming convention" from "icon theme name" into distinct fields, which is a design change beyond this plan's scope.

### 01-05 — 01-core-crate-api

#### Deviation: impl_merge! kept as #[macro_export]

**What:** `#[macro_export]` could not be fully removed from `impl_merge!`.

**Why:** The `define_widget_pair!` macro in `widgets/mod.rs` invokes `$crate::impl_merge!(...)`. The `$crate::` path prefix only works for macros that are `#[macro_export]`ed. Without it, the macro is invisible across module boundaries in this pattern.

**Mitigation:** Added `#[doc(hidden)]` which hides the macro from rustdoc and IDE discovery. Consumers won't see it in autocomplete or documentation. The macro is still technically accessible via `native_theme::impl_merge!` but not discoverable.

### 01-08 — 01-core-crate-api

#### Deferred Issues

**Issue 25 (widget field doc comments):** ~200 fields across 50 structs need doc comments. Requires extending the `define_widget_pair!` macro to accept per-field attributes. Better suited to a dedicated documentation effort.

**Issue 30 (strict TOML parsing):** `from_toml_strict()` requires mirroring the entire `ThemeSpec` → `ThemeVariant` → 25 widget type hierarchy with `#[serde(deny_unknown_fields)]`. This is a significant implementation that should be done as a standalone feature.
