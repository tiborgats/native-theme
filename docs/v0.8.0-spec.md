### Crate-Wide Invariants

- **Lints:** `#![warn(missing_docs)]`, `#![deny(clippy::unwrap_used)]`, `#![deny(clippy::expect_used)]`, `#![deny(unsafe_code)]`. `scripts/check_strict_panic.sh` additionally denies `panic`, `todo`, `unimplemented`, `unreachable`, `manual_assert`, `unwrap_in_result`, `indexing_slicing`, `string_slice`, `arithmetic_side_effects`, `integer_division`, `modulo_arithmetic`, `exit`, and `panic_in_result_fn` on `native-theme --lib` (use `.get(...)`, `.saturating_add(...)`/`.checked_add(...)`, and avoid `unwrap_or` with hardcoded literals in `src/`). Localized `#[allow(unsafe_code)]` with `// SAFETY:` comments stays where `0.7.2` has it (`reader/{macos,windows}` from `macos.rs`/`windows.rs`, `sficons.rs`, `winicons.rs`, `watch/{macos,windows}`); `tests/unsafe_safety_comments.rs` checks the comments. New `unsafe` needs the maintainer's grant.
- **Thread safety & traits:** `Theme`, `ResolvedTheme`, `Palette`, `ThemePatch`, `SystemOverrides`, and all visual/widget types are `Clone + Debug + Send + Sync`. `ResolvedTheme` and all resolved value structs additionally implement `PartialEq`.
- **Exhaustive vs `#[non_exhaustive]`:**
  - **Exhaustive (fixed math, bitflag, and closed-domain primitives):** `Color`, `Edges`, `Paint`, `Stroke`, `StrokeSide`, `Corners`, `GradientStop`, `ShadowLayer`, `Transform`, `Transition`, `TextDecoration`, `FontWidth` *(private inner field)*, `FontSize`, `WidgetState`, `EdgeFlags`, `PartStated`, `TextStated`, `IconStated`, `Scheme`, `Direction`, `Orientation`, `ButtonKind`, `ListKind`, `RoleOrigin`, `WidgetOrigin`, `DialogButtonOrder`, `ArrowSide`, `LabelSide`, `TabIndicatorSide`, `WindowsAccentRamp`, `KdeIntensityEffect`, `KdeColorEffect`, `KdeContrastEffect`.
  - **`#[non_exhaustive]` (extensible toward `1.0`):** `ResolvedTheme`, `ThemeContext`, `StyleQuery`, `RuleSelector`, `ColorRoles`, `SurfaceColors`, `SelectionColors`, `AccentColors`, `StatusColors`, `Typography`, `TextRendering`, `IconThemeSpec`, `IconSizes`, `LayoutMetrics`, `CaretSpec`, `UiTimings`, `MotionTokens`, `WindowChrome`, `WindowState`, `CaptionLayout`, `PartStyle`, `TextStyle`, `IconStyle`, `FocusIndicator`, `RippleSpec`, `MaterialSpec`, `ComplexPaint`, `ComplexStroke`, `SystemSnapshot`, `SystemOverrides`, `OsColors`, `OsSurfaceOverrides`, `OsSelectionColors`, `KdeColorEffects`, `KdeStateEffects`, `OsFont`, `DiagnosticEntry`, `Palette`, `ThemePatch`, `PartPatch`, `TextPatch`, `IconPatch`, `Error`, `ErrorKind`, `ThemeChangeEvent`, and all widget/variant/shape/kind/prop enums (`Preset`, `Contrast`, `MotionPreference`, `ControlSize`, `Surface`, `GroupPosition`, `ButtonVariant`, `ButtonShape`, `InputVariant`, `TabVariant`, `ListVariant`, `PartProp`, `TextProp`, `IconProp`, `MaterialKind`, `BlendMode`, `Timing`, `Cursor`, `CaptionButtonKind`, `DialogEntranceStyle`, `ThemeChangePolicy`, etc.).
- **Infallible resolution & queries:** `Theme::resolve(&self, ctx: &ThemeContext) -> ResolvedTheme` and every widget part query are infallible and never panic or emit `NaN`.
- **Stated and unstated values:** a preset writes a value only where a source states it. `PartStyle`, `TextStyle` and `IconStyle` carry a `stated` bit set saying which of their properties the theme states; an unstated property holds its neutral default and a connector leaves the toolkit's own value in place. Every value outside a part — a widget's direct metric, a colour role, a motion token, an icon size, a font family, a layout metric, a timing — is an `Option` wherever a bundled preset has no source for it; a surface's colours are taken from another surface only where a cited source says the platform uses them there. This carries `0.7.2`'s soft options; no builder fills a gap with a number of its own. The types below show `Option` where the gap is already known. The plan's first milestone writes one preset's complete globals and reports every further slot without a source; those become `Option` by an amendment here before the second milestone.
- **Constructors:** every `#[non_exhaustive]` struct that a caller must be able to make (`Palette`, `SurfaceColors`, `SelectionColors`, `SystemOverrides`'s parts such as `OsColors`, `OsSelectionColors`, `OsFont`, `CaptionLayout`, `KdeColorEffects`, `DiagnosticEntry`; `FocusIndicator`, `RippleSpec`, `ComplexStroke` via `Stroke::sides(top, right, bottom, left, align)`, `MaterialSpec`) has a `new(…)` taking its present fields, and the patch types have `new()` plus chained setters (§7). `IconSizes` and `TextRendering` have one because `SystemOverrides` holds them. A struct that only `resolve()` makes — `ColorRoles` with its `AccentColors` and `StatusColors`, `Typography`, `LayoutMetrics`, `UiTimings`, `MotionTokens` — has no `new`: no public function takes one, a caller changes it through a palette, a patch, or field by field in a transform (`#[non_exhaustive]` forbids only the struct literal outside the crate), and the builders, inside the crate, write the literal. A struct whose every field is an `Option` derives `Default`, which states nothing (`SurfaceColors`, `CaretSpec`, `TextRendering`, `OsColors`, `OsSelectionColors`, and likewise `UiTimings`, `MotionTokens` and `IconSizes`); `ColorRoles`, `AccentColors`, `StatusColors`, `Typography` and `LayoutMetrics` hold values without a neutral default (a colour, a font family, a radius) and have none.
- **Axis values without data:** a query for a variant, size, surface or position that a preset has no rule for returns the part's base style. Each preset's module documentation lists the variants, sizes and contrast levels it defines.
- **Hard non-goals (do not introduce):**
  - No TOML expression language or runtime AST evaluator (platform math is compiled Rust).
  - No CSS DOM ancestor/sibling matcher or `FontMetrics` callback in core queries.
  - No runtime combinatorial validator (`validate/combos`).
  - No animation/scroll-fling runtime engines or frame-by-frame `ripple.rs` shader engine (declarative timing/curve/spring/ripple specs only).
  - No runtime main-thread AppKit offscreen `NSButton` bitmap rendering (use measured glyph geometry/stroke/color tokens + platform icon loaders).
  - No proc-macro model generator (`native-theme-derive`), `inventory` registry, 66 MB `docs/facts/` DB, or Python preset codegen as a standing mechanism (a one-off port script whose output is committed Rust is not one; plan, `M0`).

## 2. Core Visual Primitives

### `Color` and `Edges` (Exhaustive)

```rust
/// Gamma-encoded extended-sRGB color (matching AppKit/UIKit `extendedSRGB` and the CSS sRGB
/// transfer function extended symmetrically beyond `0.0..=1.0`).
/// Channels may lie outside `0.0..=1.0` to represent Display P3 losslessly; `a` is in `0.0..=1.0`.
#[derive(Clone, Copy, Debug, Default, PartialEq)]
pub struct Color {
    pub r: f32,
    pub g: f32,
    pub b: f32,
    pub a: f32,
}

impl Color {
    pub const TRANSPARENT: Self = Self { r: 0.0, g: 0.0, b: 0.0, a: 0.0 };
    pub const BLACK: Self       = Self { r: 0.0, g: 0.0, b: 0.0, a: 1.0 };
    pub const WHITE: Self       = Self { r: 1.0, g: 1.0, b: 1.0, a: 1.0 };

    pub const fn new(r: f32, g: f32, b: f32, a: f32) -> Self;
    pub const fn rgb(r: f32, g: f32, b: f32) -> Self;
    pub fn from_srgb8(r: u8, g: u8, b: u8, a: u8) -> Self;
    pub fn from_hex(hex: &str) -> Result<Self, Error>;      // #rgb, #rgba, #rrggbb, #rrggbbaa
    pub fn from_display_p3(r: f32, g: f32, b: f32, a: f32) -> Self;
    pub fn with_alpha(self, a: f32) -> Self;                 // clamps finite a to 0.0..=1.0; non-finite -> 0.0
    pub fn mul_alpha(self, factor: f32) -> Self;             // multiplies existing alpha; non-finite -> 0.0
    pub fn clamped(self) -> Self;                            // clamps finite r,g,b,a to 0.0..=1.0; non-finite -> 0.0
    pub fn to_srgb8(self) -> [u8; 4];                        // clamps then rounds to u8
    pub fn to_premultiplied_srgb8(self) -> [u8; 4];
    pub fn to_display_p3(self) -> [f32; 4];
    pub fn composite_over(self, backdrop: Self) -> Self;     // Porter-Duff source-over
    pub fn mix_srgb(self, other: Self, t: f32) -> Self;      // premultiplied CSS color-mix(in srgb)
    pub fn relative_luminance(self) -> f32;                  // WCAG 2.1 luminance (clamped >= 0.0)
    pub fn contrast_ratio(self, other: Self) -> f32;         // WCAG 2.1 contrast ratio (>= 1.0)
}
// Implements `Display` & `FromStr` (`#rgb`, `#rgba`, `#rrggbb`, `#rrggbbaa`, `srgb(r,g,b,a)`, `p3(r,g,b,a)`).
// Under `serde`: serializes as `#rrggbb`/`#rrggbbaa` when exact sRGB8 in `0.0..=1.0`, else lossless
// `srgb(r, g, b, a)`; deserializes all string forms as well as `{ r, g, b, a }` maps.

#[derive(Clone, Copy, Debug, Default, PartialEq)]
pub struct Edges {
    pub top: f32,
    pub right: f32,
    pub bottom: f32,
    pub left: f32,
}
impl Edges {
    pub const ZERO: Self = Self { top: 0.0, right: 0.0, bottom: 0.0, left: 0.0 };
    pub const fn all(v: f32) -> Self;
    pub const fn symmetric(vertical: f32, horizontal: f32) -> Self;
    pub const fn new(top: f32, right: f32, bottom: f32, left: f32) -> Self;
}
```

### `FocusIndicator`, `RippleSpec`, `Transition`, `PartStyle`, `TextStyle`, `IconStyle`

```rust
#[derive(Clone, Debug, PartialEq)]
#[non_exhaustive]
pub struct FocusIndicator {
    pub kind: FocusKind,
    pub stroke: Stroke,
    pub inner_stroke: Stroke,       // e.g. WinUI dual white/black focus ring; Stroke::None when unused
    pub offset: f32,                // from the part's edge to the inner edge of `stroke`: positive outside the part, negative inside
    pub corners: Option<Corners>,   // of the line `offset` places; None = the part's radii plus `offset`
    pub trigger: Option<FocusTrigger>, // None where the theme states no keyboard-only vs always rule (0.7.2's `focus_ring_keyboard_only: Option<bool>`)
}

#[derive(Clone, Copy, Debug, Default, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum FocusKind { #[default] Ring, Fill, Underline }

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)] // no `Default`: the type stands only in `Option` fields, where a default would be an invented value
#[non_exhaustive]
pub enum FocusTrigger { KeyboardOnly, Always }
// Contract: a preset states `PartStyle.focus` on a focusable part where its platform's indicator has a
// source (it describes *how* to draw the indicator, and state rules such as `INVALID` can override it);
// where `FOCUS` is unstated, the toolkit's own indicator stays. Connectors draw a stated one when
// `(trigger == Some(KeyboardOnly) && state.contains(FOCUS_VISIBLE))`,
// `(trigger == Some(Always) && state.intersects(FOCUSED | FOCUS_VISIBLE))`, or
// `(trigger.is_none() && /* toolkit default focus trigger */)`.
// Geometry of a `Ring` (CSS's `outline` and `outline-offset`): the base line is the part's outline moved by
// `offset`. `stroke` is a band of its width outward from that line; `inner_stroke` a band of its width inward
// from it, touching. The base line's corners are `corners` where stated, else the part's radii plus `offset`,
// floored at 0; each band's far edge is concentric. A ring has no fill, so a ring stroke's `align` says
// nothing: presets write `Stroke::uniform`, connectors do not read it. The ring is painted over the part
// (source-over), takes no layout space, and is drawn where it lies, inside the part included.

#[derive(Clone, Copy, Debug, PartialEq)]
#[non_exhaustive]
pub struct RippleSpec {
    pub color: Color,
    pub bounded: bool,
    pub enter_ms: u32,
    pub exit_ms: u32,
}

#[derive(Clone, Copy, Debug, PartialEq)]
pub struct Transition {
    pub duration_ms: u32,
    pub delay_ms: u32,
    pub timing: Timing,
}

#[derive(Clone, Copy, Debug, Default, PartialEq)]
#[non_exhaustive]
pub enum Timing {
    #[default]
    Linear,
    CubicBezier(f32, f32, f32, f32),
    Spring { mass: f32, stiffness: f32, damping: f32 },
    Steps(u16),
    SineInOut,
    ExpoOut,
}

#[derive(Clone, Copy, Debug, Default, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum Cursor {
    #[default]
    Default, Pointer, Text, Grab, Grabbing, ColResize, RowResize, NotAllowed, Progress,
}

#[derive(Clone, Debug, PartialEq)]
#[non_exhaustive]
pub struct PartStyle {
    pub fill: Paint,                              // 24 B
    pub stroke: Stroke,                           // 24 B
    pub corners: Corners,                         // 24 B
    pub shadows: Option<Arc<[ShadowLayer]>>,      // 16 B
    pub opacity: f32,                             // 4 B  (default 1.0)
    pub transform: Transform,                     // 28 B
    pub padding: Edges,                           // 16 B  between the stroke's inner edge and the content, as 0.7.2's padding
    pub margin: Edges,                            // 16 B
    pub min_size: [Option<f32>; 2],               // 16 B [width, height]
    pub max_size: [Option<f32>; 2],               // 16 B [width, height]
    pub focus: Option<Arc<FocusIndicator>>,       // 8 B
    pub ripple: Option<Arc<RippleSpec>>,          // 8 B
    pub transition: Option<Transition>,           // 28 B
    pub cursor: Cursor,                           // 1 B
    pub stated: PartStated,                       // 4 B  which properties the theme states
    pub from_state: PartStated,                   // 4 B  which of them got their value from a rule that requires a state flag of the query
} // Total <= 256 B (240 B as laid out by rustc 2024, `from_state` included: it fits in what was padding); zero heap allocation on Clone.

// Fill and stroke: which area each paints. The part's outline is its box (what `min_size` and `max_size` measure)
// rounded by `corners`. The stroke is a band of its `width` along the inside of that outline, whatever its `align`:
// it never reaches outside the box, no alignment moves layout, and `padding` starts at its inner edge. The edge
// that `StrokeAlign` names is the edge of the fill, so `align` says how far the fill runs under the stroke:
//   `Inside`  - the stroke lies inside the fill: the fill covers the whole outline (CSS's `background-clip:
//               border-box`; WinUI's `BackgroundSizing="OuterBorderEdge"`);
//   `Center`  - the stroke is centred on the fill's edge: the fill ends at the stroke's centre line, half the
//               width inside the outline (one path painted with a brush and a pen, as Breeze does through Qt);
//   `Outside` - the stroke lies around the fill: the fill ends at the stroke's inner edge (`padding-box`; WinUI's
//               `BackgroundSizing="InnerBorderEdge"`).
// The stroke is painted over the fill (source-over), so a translucent stroke shows the fill only where the fill
// runs under it; under an opaque stroke the three alignments paint the same picture, and a preset states `Center`
// or `Outside` only where a source or a measurement shows that extent. A `ComplexStroke` follows the rule side by
// side, each side with its own width. A `FocusIndicator`'s strokes are placed by its `offset`; this rule is not theirs, and their `align` is not read.
// Contract for connectors: a toolkit that paints the background under its whole border (gpui) draws `Inside` from
// the stated colours, one that ends the background at the border's inner edge (iced on wgpu, egui) draws `Outside`
// from them. For another alignment, where fill and stroke are solid colours, the connector gives the toolkit the
// border colour this rule computes: on a toolkit of the second kind, the stroke over the fill for `Inside`, and
// the stroke over the fill at half its alpha for `Center` (the band's mean colour; exact where the band is one
// device pixel wide). Where a colour cannot say it (a translucent `Center` or `Outside` stroke on a toolkit of the
// first kind, a gradient), the connector draws the fill and the stroke as two shapes where it paints the part
// itself, and otherwise leaves the toolkit's extent and records the limit (§10, rule 4).

/// One bit per `PartStyle` property the theme states; `padding` and `margin` have one bit per side.
/// `min_size` and `max_size` need none: each dimension is its own `Option`. A size its source gives as exact
/// (a check box's indicator, a row's height) is stated as `min_size` and `max_size` equal in that dimension;
/// a floor is `min_size` alone.
/// For the other `Option`-typed properties (`shadows`, `focus`, `ripple`, `transition`) the bit tells two
/// meanings of `None` apart: bit clear, the theme states nothing and the toolkit's own applies; bit set, the
/// theme states that the part has none. An empty shadow list is not used. The same holds for the `Option`
/// fields of `TextStyle` and `IconStyle`.
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq, Hash)]
pub struct PartStated(u32); // FILL, STROKE, CORNERS, SHADOWS, OPACITY, TRANSFORM, PADDING_TOP..LEFT, MARGIN_TOP..LEFT,
                            // FOCUS, RIPPLE, TRANSITION, CURSOR; `contains`, `union`, bit operators as `WidgetState`
// `TextStated(u16)` and `IconStated(u8)` are the same for `TextStyle`'s and `IconStyle`'s fields.
// `from_state` (on `PartStyle`, `TextStyle` and `IconStyle`, of the same bit-set type as `stated`): the properties whose
// value in this result was written by a rule whose `required_states` is not empty, i.e. a value the theme states *for
// this state*. `0.7.2` told an unset state value (`None`) from a value; a query returns the resting value for a state
// without a rule, and a value stated equal to the resting one looks the same, so the result says which it is.
// Contract for connectors: where a property's bit is clear in `from_state` for a state the toolkit has its own
// treatment of (a pressed fill, a hover outline), the theme states nothing for that state and the toolkit's own
// treatment stays, exactly as for an unstated property; where it is set, the theme's value is drawn. A rule that
// matches by variant, size, surface, position or orientation alone sets no `from_state` bit.
// `PartStated` also has `MIN_SIZE` and `MAX_SIZE` (one bit each for both dimensions), set only in `from_state` (a state rule
// wrote that size; a hover thickness), never in `stated`, where each dimension's `Option` says it.
// The bit says that a rule for some flag of the query wrote the value, not for which flag: `indicator(CHECKED | HOVER)` has
// `FILL` set by the `CHECKED` rule. A connector that keeps its own treatment of one flag (a hover tint) over a value stated
// for another asks the query with that flag alone (`indicator(HOVER).from_state`) whether the theme states it.
// A state the toolkit has no treatment of at all is §10's rule 0a.
```

```rust
/// Matches a widget's variant value `V` against a rule's matcher `M`.
pub trait VariantMatcher<V>: Copy + Default + std::fmt::Debug + PartialEq + Eq {
    fn matches(&self, value: &V) -> bool;
}
// Impls: `()` matches `()`; `Option<V>` matches `V` (InputVariant, TabVariant);
// `ButtonMatcher { variant: Option<ButtonVariant>, shape: Option<ButtonShape> }` matches `ButtonKind`;
// `ListMatcher { variant: Option<ListVariant>, alternate: Option<bool> }` matches `ListKind`.

#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
#[non_exhaustive]
pub struct RuleSelector<M = ()> {
    pub required_states: WidgetState,
    pub forbidden_states: WidgetState,
    pub size: Option<ControlSize>,
    pub surface: Option<Surface>,
    pub position: Option<GroupPosition>,
    pub orientation: Option<Orientation>,
    pub matcher: M,
}

#[derive(Clone, Debug, PartialEq)]
pub struct RuleSet<T, P, M = ()> {
    base: T,
    exclusive: &'static [&'static [WidgetState]], // e.g. &[&[DISABLED, PRESSED, HOVER]]
    rules: Arc<[RuleEntry<M>]>,                   // RuleSelector<M> + (start: u32, len: u32)
    props: Arc<[P]>,                              // single flat allocation at resolve(); zero-alloc Clone
}
```

**Evaluation contract (`RuleSet::eval`):**
0. If `query.state` contains `FOCUS_VISIBLE`, add `FOCUSED`.
1. Normalize `query.state` against each ordered slice in `exclusive`: if any flag in the slice is set, keep only the earliest (highest-precedence) flag in that slice and clear the rest. The slices are applied in their stated order, each to the result of the one before it. If this clears `FOCUSED`, it clears `FOCUS_VISIBLE` too (`FOCUS_VISIBLE` implies `FOCUSED`, so a keyboard-focus rule never matches a part whose focus a higher-precedence state has overridden).
2. Clone `self.base` (zero heap allocations — only value copies and `Arc::clone`).
3. Iterate `self.rules` in stated order; when a rule's selector matches the normalized query, apply `self.props.get(start..start + len)` onto the result (`last-match-wins`), setting the `stated` bit of each property applied. The base carries the bits of what the builder stated in it. A rule whose `required_states` is not empty also sets the property's bit in `from_state`; the base's `from_state` is empty, and a later matching rule without required states that overwrites the property clears the bit again (the value then no longer comes from a state).
4. Return the concrete `T`. Guaranteed **zero heap allocations** and **panic-free** (uses safe slicing, never panics on bounds).

**State combinations a source does not state.** A builder writes a rule only for a state its source states, and a part's exclusive group names only flags that part has a rule for. A combination without data then returns what the query returns without the flag that has no data (a pressed, hovered check box indicator with no pressed value keeps its hover look), which is the rule of "Axis values without data" (§1) applied to states. Where two rules can both match (a variant and a state, a state and `SELECTED`), their order is a statement the preset makes: each preset's module documentation lists every part's exclusive group and each such precedence with its source, and a precedence without one follows what `0.7.2`'s connectors draw from its fields. The parity tests cannot see these combinations (`0.7.2` has no field for them); they are covered by the preset's own tests and by review.

`PartProp::MinSize` and `MaxSize` merge per dimension: a `Some` replaces, a `None` leaves what was there (so a rule stating only a height keeps the base's width). Similarly, `PartProp::PaddingSides(edges, mask)` and `MarginSides(edges, mask)` overwrite ONLY the sides flagged in `mask` and set only those sides' `PartStated` bits, leaving unflagged sides and their `stated` bits untouched. `RuleSet::eval` computes slice bounds with `.saturating_add(...)` and `.get(...)` to satisfy `check_strict_panic.sh`.

```rust
    // defines no such style: no size is invented for it, and a caller falls back to `body`.
    // A slot that is `Some` states only what its source states for that style (0.7.2's `text_scale` entry: a
    // size, a weight and a line height). A property it leaves unstated is `body`'s, property by property: 0.7.2

    // `[text_scale_inheritance]`) and its consumers drew a role in `defaults.font`'s family, style and colour.
    // The properties that belong to a size (`line_height`, `letter_spacing`, `optical_size`, and `defined_size`
    // with `size_px`) are `body`'s only where the slot states no size; beside a size of its own they stay the
    // slot's, stated or not, and an unstated `line_height` is then the one the `line_height` rule below gives
    // (the size by `line_height_multiplier`).
    // `Typography::over_body` is the one reader of this rule. It changes nothing in the slot: the serialised
    // form and Widget Info show a slot as stated. `monospace` is never laid over `body`.

    // A slot's `line_height`, where its source states none, is `line_height_multiplier` times the slot's size
    // before whole-pixel rounding (0.7.2's rule for a `text_scale` entry). `body` and `monospace` follow it too, so a role
    // that falls back to `body` reads what 0.7.2 resolved for it (kde-breeze's `display`: 1.36 × 13.33 = 18.13).
    pub display: Option<TextStyle>,
    pub title1: Option<TextStyle>,
    pub title2: Option<TextStyle>,
```

## 5. Widget Inventory & `ResolvedTheme`

Every widget carries `pub origin: WidgetOrigin` (`Native | Synthesized`) with `pub fn is_native(&self) -> bool`. Where a mobile preset (`ios-13`, `material-3`) genuinely lacks a desktop-only control (`status_bar`, `splitter`, `menu_bar`, `tooltip`, etc.), its builder synthesizes a cohesive style strictly from that platform's own verified `ColorRoles`, `Typography`, and `Corners`, tagged `WidgetOrigin::Synthesized` (the crate's own labelled estimate; the preset file lists these widgets). `Synthesized` is only for a control the platform does not have; an unsourced property of a native control is left unstated. Ruled widgets expose per-part getters accepting `impl Into<Query>` plus a combined `parts(query)` convenience struct; static widgets expose direct public fields.

**Notes to the table:**

- **Direct metrics** are `Option` where a bundled preset has no source for one (`0.7.2`'s soft options decide which).
- **`disabled_opacity: Option<f32>`** is a further direct metric of `button`, `input`, `checkbox`, `radio`, `slider`, `switch`, `combo_box` and `segmented_control`: the opacity of the whole disabled widget drawn as one group, which per-part `opacity` cannot say (overlapping parts would blend twice). `Some(1.0)` where the platform's facts state that a disabled widget is recoloured and not faded (KDE, macOS, Windows and Material in `platform-facts.md` §2.1.6): that is a stated value, which a connector applies over its toolkit's own fade. `None` only where no source states it.
- **The switch's label** has no `0.7.2` field: `0.7.2`'s switch has no label, and its connectors draw one after the track at the toolkit's own gap. Three direct metrics place it; each is `None` where no source states it, and a connector then keeps its toolkit's own placement (§10, rule 0).
  - `label_side: Option<LabelSide>`: `LabelSide::Leading`, the label before the track, or `LabelSide::Trailing`, the label after it; leading and trailing are the reading direction's, as `ArrowSide`'s. Trailing on KDE (qqc2-desktop-style's `Switch`) and Windows (`ToggleSwitch`'s content); leading on GNOME (`AdwSwitchRow`), Android (`MaterialSwitch`), macOS and iOS (SwiftUI's `ToggleStyle.switch`: "a leading label and a trailing switch").
  - `label_gap: Option<f32>`: the space between the track and the label of a switch no wider than its content.
  - `label_gap_stretches: Option<bool>`: what a switch laid out wider than its content does with the width left over. `Some(true)`: the label and the track lie at the two ends of the width, and `label_gap` is the least space between them (GNOME's row, Android, iOS). `Some(false)`: they stay together at `label_gap`, and the width left over is not put between them (KDE and Windows, whose controls keep the two at the start; macOS). The width is the application's layout: a connector's switch does not widen itself.
  - The check box and the radio have `label_gap` alone: the facts read give them no leading and no stretching label (`platform-facts.md` §2.5; Apple's HIG: "a checkbox includes a title on its trailing side").

A value the theme states is carried as any other. A preset that states such a property from a source of its own (rectangular menu items on a platform whose facts say so) lists it as a difference.

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)]
#[non_exhaustive]
pub enum Preset {
    Adwaita, KdeBreeze, MacosMonterey, MacosTahoe, Windows11, Material3, Ios13,
    // Ios26: added when the 38 fields `docs/todo.md` lists as without an iOS 26 source have one (plan, M2)
}

impl Preset {
    pub const ALL: &'static [Self];
    /// Infallible target/DE/OS-generation detection requiring zero reader features:
    /// Linux `XDG_CURRENT_DESKTOP` (KDE -> `KdeBreeze`, else `Adwaita`), macOS (`SystemVersion.plist`
    /// / `NSProcessInfo` >= 26 -> `MacosTahoe`, else `MacosMonterey`), Windows -> `Windows11`,
    /// iOS -> `Ios13` (`Ios26` once it is bundled), Android -> `Material3`, WASM/other -> `Adwaita`.
    /// New against 0.7.2: the macOS generation without the `macos` feature (0.7.2 reads it through
    /// `NSProcessInfo` and falls back to `MacosMonterey` without the feature; the `SystemVersion.plist`
    /// read must be proven on a macOS 26 runner, else that fallback stays), and the iOS and Android arms.
    pub fn detect() -> Self;
    pub fn from_name(name: &str) -> Option<Self>;     // "adwaita", "kde-breeze", …
    pub fn as_str(self) -> &'static str;
    pub fn display_name(self) -> &'static str;        // "Adwaita", "KDE Breeze", "macOS Tahoe", …
}

// The platform builders are crate-private functions, one per preset file, chosen by a `match` on `Preset`:
//   pub(crate) fn resolve(ctx: &ThemeContext, inputs: &ResolveInputs<'_>) -> ResolvedTheme
// with `pub(crate) struct ResolveInputs<'a> { system: Option<&'a SystemOverrides>, palette: Option<&'a Palette>, accent: Option<Color> }`.
// No public source trait in 0.8.0: an implementor would need a public way to construct every part of a
// `ResolvedTheme`; Tier 3 is `Theme::with_transform`.


#[derive(Clone)] // `Debug` is written by hand: the transforms are closures
pub struct Theme { /* preset: Preset,
                      name: Option<Arc<str>>, context: ThemeContext,
                      system: Option<Arc<SystemOverrides>>, palettes, accent,
                      preserve_palette_in_high_contrast: bool,
                      patches: Vec<ThemePatch>,
                      transforms: Vec<Arc<dyn Fn(&mut ResolvedTheme) + Send + Sync>> */ }

impl Theme {
    // Construction
    pub fn preset(preset: Preset) -> Self;
    pub fn for_current_platform() -> Self;            // infallible; uses Preset::detect()
    pub fn from_system() -> Result<Self, Error>;      // requires OS reader feature
    pub fn from_system_with_preset(preset: Preset) -> Result<Self, Error>;
    pub fn from_system_or_default() -> Self;          // infallible fallback to for_current_platform()
    #[cfg(feature = "toml")]
    pub fn from_toml(toml_str: &str) -> Result<Self, Error>;

    // Configuration (all fluent, Clone + Send + Sync)
    pub fn with_name(self, name: impl Into<Arc<str>>) -> Self;
    pub fn context(&self) -> &ThemeContext;
    pub fn with_context(self, ctx: ThemeContext) -> Self;
    pub fn system_overrides(&self) -> Option<&SystemOverrides>;
    pub fn with_system_overrides(self, overrides: SystemOverrides) -> Self;
    // The three palette methods replace one another's effect where they overlap: `with_palette` clears both
    // slots and sets the lock; `with_palettes` and `with_palette_for` clear the lock.
    pub fn with_palette(self, palette: Palette) -> Self;                  // locks effective scheme to palette.scheme
    pub fn with_palettes(self, light: Palette, dark: Palette) -> Self;    // follows ctx.scheme
    pub fn with_palette_for(self, scheme: Scheme, palette: Palette) -> Self;
    pub fn preserve_palette_in_high_contrast(self, preserve: bool) -> Self; // covers the explicit accent too
    pub fn with_accent(self, accent: Color) -> Self;
    pub fn with_patch(self, patch: ThemePatch) -> Self;
    pub fn with_transform(self, f: impl Fn(&mut ResolvedTheme) + Send + Sync + 'static) -> Self;

    // Inspection & pure stateless resolution
    pub fn preset_id(&self) -> Preset;
    pub fn diagnostics(&self) -> &[DiagnosticEntry];
    pub fn resolve(&self, ctx: &ThemeContext) -> ResolvedTheme;
    pub fn resolve_current(&self) -> ResolvedTheme;   // shorthand for self.resolve(self.context())
}
```

### Resolution Algorithm (`Theme::resolve(&self, ctx)`)

The layers, lowest first: (1) the preset; (2) the live `SystemOverrides`; (3) the palette, then the explicit accent; (4) the patches, then the transforms. The numbered steps below are the order of computation.

1. **Compute effective context & active palette.** A contrast level is *available* for a scheme where the preset defines it or `SystemOverrides` carries colours for that scheme and level (a system in high contrast supplies its own colours even where the preset has no `High` data, and they must not be dropped).
   - Start from `effective = ctx.clone()` (sanitizing `text_scale` to finite `0.5..=4.0`).
   - If the requested level is `High`, it is available for `ctx.scheme`, and `!self.preserve_palette_in_high_contrast`: the active palette is `None`, the explicit accent is not passed on (preserves OS high-contrast accessibility colors), and `effective.contrast = High`. Where `High` is not available, the palette stays.
   - Otherwise select the active `palette`:
     - single-scheme lock (`.with_palette(p)`): the active palette is `Some(p)` and `effective.scheme = p.scheme`;
     - else the slot matching `effective.scheme` (`.with_palettes` / `.with_palette_for`); if present, set `effective.scheme = p.scheme`.

     Then set `effective.contrast` to the requested level if it is available for `effective.scheme` (the scheme after the palette's lock), else to the nearest level below it that is available for `effective.scheme` (`Normal` is always available: every preset defines it). Where a palette is active or an explicit accent is passed and `!self.preserve_palette_in_high_contrast`, `High` is not taken in this step (the same nearest available level below it is), so `High` and an active palette or accent meet only when preserved (§11, item 5). An entry of `SystemOverrides::color_schemes` makes a level available only where it states at least one colour (a colour field, nested ones included; the contrast scalars and effects state none).

2. **Run the preset's builder with `ResolveInputs { system, palette, accent }`:**
   - Inside each platform builder:
     - Apply scheme-independent `SystemOverrides` (fonts, `font_dpi`, `text_rendering`, `timings`, `animation_scale`, `caret`, `caption_layout`, `overlay_scrollbars`). Use `SystemOverrides::icon_theme` unless `SystemOverrides::scheme` is `Some(s)` with `s != effective.scheme` (a palette or the caller's context chose the other scheme than the one the system was read in); in that case use the preset's scheme-matched icon theme (e.g., `"breeze-dark"` vs `"breeze"`).
     - Apply scheme-scoped `SystemOverrides` colors **only** when a color slot matches `(effective.scheme, effective.contrast)`.
     - Apply the active `palette` (layer 3) over base color roles before running platform derivations (`adw_standalone`, `kde_accent`, `kcu_*`, `m3_role`, `qt_lighter`). On `macos-*`/`ios-*`, semantic palette mapping replaces Apple's literal colors while preserving Apple geometry and materials. The roles each slot states are §7's ("The roles a palette states"); the platform's settings and the widget colours a slot replaces are the preset's (§8). A derivation computes again what reads a colour a slot replaced, and never replaces a colour the palette states in a slot of its own (on `kde-breeze`, `selection_bg`, `selection_fg`, `link` and `info` stand over what Plasma's accent rule would compute from `accent`: §8, "The KDE part", *Palette*).
     - Apply the explicit `accent` (layer 3, overriding the palette's accent if both are set) before running platform derivations: `kde-breeze` runs `kde_accent`, `material-3` runs `m3_role` HCT and `adwaita` runs `adw_standalone` OKLab. `windows-11`, `macos-monterey` and `ios-13` compute no colour from an accent; `macos-tahoe` computes its checked button's fills alone, the accent mixed with `#000000` (light) or `#ffffff` (dark) in sRGB by 0.025 at rest, by 0.12 pressed and by 0.04 at alpha 0.44 disabled, the mixes the parked facts measured under both accents (§8, "The macOS part"). The variants those platforms make of an accent (Windows' six shades; AppKit's selection, text-selection and focus-ring colours) follow rules their vendors do not publish ("An accent color algorithm in the Windows shell generates light and dark shades of the accent color", Microsoft's theming documentation; the two Windows generations the OS probe ran on state different shades for nearly the same blue, `#0078d7` and `#0078d4`), so a variant is used only as the system states it (`SystemOverrides`, §8) or, those checked fills, as a measured mix gives it, and an accent given by `.with_accent()` or by a palette's `accent` slot is written as given, to the roles below and to what the builder reads from them; a slot of the palette's own (`accent_fg`, `selection_bg`, `selection_fg`, `link`, `info`, `caret`) stands over what its `accent` would write.
       - `windows-11`: `colors.accent.fill`; the accent fill of the resolved scheme (WinUI's `AccentFillColorDefault`: the primary and checked fills, the slider's, the progress bar's and the spinner's fill and, outside high contrast, the focused text field's stroke), which the builder already gives the accent where its shade is `None` (§8, "The Windows part"); `colors.info.fill`; `colors.selection.background`. `SystemOverrides::windows_accent_ramp` holds the system accent's shades and is not used for these. `colors.accent.foreground`, in which the builder draws every text and mark on the accent fill, is the palette's `accent_fg`; under an explicit accent it is the resolved scheme's `TextOnAccentFillColorPrimary` (`#FFFFFF` in light, `#000000` in dark) where its `contrast_ratio` on the accent is at least 3 (the minimum of §11, item 5), else the other scheme's. The link and its hover and pressed colours are WinUI's text shades (`AccentTextFillColorPrimary`, `Secondary` and `Tertiary`), which read on the window where the accent itself may not: an accent does not write them, and they keep the value of the layers below; under a palette the link is the palette's `link`, and its hover and pressed colours are not stated. An application that has shades for its own accent states both as `SystemOverrides::accent` and `windows_accent_ramp` and gives no explicit accent, as a WinUI application overrides `SystemAccentColor` together with its six shades.
       - `macos-*`: `colors.accent.fill`; `colors.selection.background`; `colors.text_selection`, which takes the selection's two colours; `colors.focus_ring`, the accent at alpha 0x7F (the alpha `keyboardFocusIndicatorColor` has under both accents the OS probe measured, in both appearances); `colors.caret`, unless a palette states `caret`; the disabled, checked switch's track (§8, "The macOS part"); on `macos-tahoe`, the checked button's fills, the accent mixed with black (light) or white (dark) in sRGB by 0.025 at rest, by 0.12 pressed and by 0.04 at alpha 0.44 disabled, the mixes the parked facts measured under both accents (§8, "The macOS part"). `colors.link`, the status roles, the unfocused selection and the text colour on the accent and on the selection (`alternateSelectedControlTextColor`) do not change with the accent in AppKit (the same measurement) and are not written.
       - `ios-13`: `colors.accent.fill` (UIKit's tint, which its controls draw as given), `colors.selection.background` and `colors.text_selection` as on macOS; nothing else.
       The explicit accent is the later statement of layer 3: on `kde-breeze`, what `kde_accent` writes from it replaces the palette's `selection_bg`, `selection_fg`, `link` and `info` as well as its `accent` (§8, "The KDE part", *Explicit accent*); on `windows-11` the palette's `accent`, `accent_fg`, `info`, `selection_bg` and `selection_fg` are then not applied, and on `macos-*` and `ios-13` its `accent`, `accent_fg`, `selection_bg` and `selection_fg` (where this bullet gives a foreground no rule, it is the one of the layers below the palette).
     - Scale typography sizes via `effective.text_scale` (linear on GNOME, KDE, Windows and macOS / Android `FontScaleConverter` on Material 3 / the nearest Dynamic Type category on iOS — the category whose Body size divided by the Large category's Body size is nearest the text scale, the smaller one on a tie, each text style then taking its own row of that category; preset constants and `OsFont::size` convert via `font_dpi` first, are then scaled, and the scaled size is rounded where `font_whole_pixels` (so a whole-pixel platform's sizes stay whole at every scale); `OsFont::size` is the system's own unscaled setting, so nothing double-scales).
     - Apply accessibility & window-active flags, each only through a rule that a cited source states for that platform: `bold_text` (the weight step is pending on iOS and Android and unsourced elsewhere, so in `0.8.0` it changes nothing until a source lands); `button_shapes` (a visible fill/stroke on Apple's flat and toolbar buttons); `differentiate_without_color` (unconditional link underlines, `switch.show_state_glyphs = true`, non-color state outlines); `reduced_transparency` or `!effective.window_active` swaps backdrop `Material` paints to their opaque/inactive fallback colors.
     - Apply `effective.motion` (`Full | Reduced | None`) and `SystemOverrides::animation_scale` (`>= 0.0`): `MotionPreference::None` (or `animation_scale == 0.0`) collapses transitions to `duration_ms = 0, delay_ms = 0` and sets `DialogEntranceStyle::None`; `MotionPreference::Reduced` replaces spatial/transform motion with short opacity fades or collapses motion per platform policy; `animation_scale` multiplies positive durations.
     - Emit physical left/right geometry, corners, and strokes for `effective.direction` (`Ltr | Rtl`).
     - Pre-bake stacked fills, Material 3 surface tint, and state-layer overlays into concrete `Paint` values.
   - Set `resolved.context = effective` and `resolved.name` (precedence: explicit `Theme::with_name` → active `palette.name` → `SystemOverrides::theme_name`, unless `SystemOverrides::scheme` is `Some(s)` with `s != effective.scheme`, as for the icon theme: a scheme's name does not name a resolve in the other scheme → `preset.display_name()`).
3. **Apply `ThemePatch`es in stated order (layer 4);** within one patch, in the order listed here, so a patch's scales do not touch the rules the same patch appends. `with_patch` does not validate (`ThemePatch::validate` and `from_toml` are the strict path): a value of a patch that is not finite is not applied, the rest of the patch is, and each scale is clamped again here and every scaled value kept finite, so a resolve never emits `NaN` (§1). An appended rule is evaluated under each part's exclusive groups as the preset declared them, part by part: a rule meant only for an enabled widget says so with `not_states(DISABLED)`. Scaling and appending rebuild the affected rule buffers (`Arc<[P]>` is immutable): one traversal of every part per patch, off the query path.
   - `color_overrides`: overwrites matching concrete `ColorRoles` slots directly (a status colour's `origin` becomes `Custom`). Only the role changes: widget parts already derived from it keep their colours; a `Palette` is the way to recolour coherently.
   - `font_family` / `monospace_family`: updates `typography` slots AND widget `TextStyle`s (`base` and `TextProp::Family`) matching the replaced UI/mono family.
   - `corner_scale` / `spacing_scale`: scales concrete corner radii (`Uniform`/`PerCorner`/`Concentric.min_radius` across widget `base`, `PartProp::Corners`, `WindowChrome`, plus `LayoutMetrics::{corner_radius, corner_radius_lg}`) and spacing (`LayoutMetrics::{widget_gap, container_margin, window_margin, section_gap}`, `padding`/`margin`, `*_gap` metrics — without scaling `border_width`, `border_opacity`, stroke widths, or `min_size`).
   - `widget_rules`: appends rules onto ruled widgets' `RuleSet`s in stated order, applies unconditional `PartProp`/`TextProp`/`IconProp` patches directly onto static widgets' style parts, and sets the direct metrics a patch names.
   - `custom_colors` / `custom_metrics`: merges entries into `ResolvedTheme`.
4. **Run `with_transform` hooks in stated order (layer 4)** and return the concrete `ResolvedTheme`.

Of the 20 variants `0.7.2`'s ten files hold, five are not carried over: the four the files label derived (`catppuccin-latte`'s dark variant and the light variants of `catppuccin-frappe`, `catppuccin-macchiato` and `catppuccin-mocha`), and `nord.toml`'s light variant, which the file does not label derived but which is no upstream variant either: Nord publishes one palette of sixteen colours and describes their use in "dark & bright ambiance designs", without a light variant of its own name. `alucard`, `tokyo_night_day` or `one_light` is dropped if its upstream source cannot be confirmed when its file is written. Plus `Palette::BUNDLED_NAMES: &'static [&'static str]` (empty when `palettes` is off) and `Palette::from_name(&str) -> Option<Self>` (always compiled; returns `None` when `palettes` is off so `--no-default-features --features toml` compiles cleanly).

**How a bundled palette's slots are filled.** Every slot holds a colour the upstream defines: a hex value it states, or the value of its own expression (Atom's Less variables); this crate adds no colour of its own. An opacity the upstream states is applied as stated (Catppuccin's selection background, One Dark's subtle text), so a palette's colour may carry alpha. A slot takes the colour the upstream assigns that role: in its style guide or specification, else in its own editor or UI port, a role of the user interface before one of the edited text. Where the upstream assigns none, or names several colours for it, one rule per palette family picks the upstream colour (the four Catppuccin flavours, Dracula and Alucard, the two Solarized, the two Tokyo Night, the two Gruvbox and the two One palettes alike), and a slot no family rule covers falls back: `view_bg` is `window_bg`'s colour, `tooltip_bg` is `surface_bg`'s, `divider` is `border`'s, `selection_fg` and `caret` are `foreground`'s, `link` and `info` are `accent`'s, and `accent_fg` is the one of `window_bg` and `foreground` with the higher `contrast_ratio` on `accent`. Legibility comes before an upstream pairing: a palette has one text colour, so no background slot takes an upstream colour on which `foreground` is hard to read (Atom's accent-coloured tooltip, drawn under white text; Solarized's reversed popup menu); of two upstream pairs for one role the more legible is taken; and a family's rule may replace a text colour that is hard to read on its background in one of the family's palettes. Each palette's documentation says, per slot, whether the upstream assigns the role or which of these rules filled it.

**The roles a palette states.** On every preset an active palette states, as given, the roles its slots name: `window_bg`, `view_bg`, `header_bg`, `sidebar_bg` and `tooltip_bg` are `background` of `colors.window`, `view`, `header`, `sidebar` and `tooltip`, and `surface_bg` is that of `colors.card`, `dialog` and `popover`; `foreground` is `foreground` of those eight surfaces (a palette has one text colour); `foreground_muted`, `border` and `divider` are `colors.window`'s; `accent` and `accent_fg` are `colors.accent.fill` and `foreground`; `selection_bg` and `selection_fg` are `colors.selection.background` and `foreground`; `link` and `caret` are `colors.link` and `colors.caret`; `error`, `warning`, `success` and `info` are the `fill` of the four status roles, each with `origin = Custom`. A role no slot names (`colors.osd`, `text_selection`, `focus_ring`, `link_visited`, `disabled_text`, `shadow`, a status role's `foreground`, an `unfocused_*` colour of the selection) keeps the value of the layers below, unless the preset's builder derives it from a colour a slot replaced (§6, step 2). Which settings of the platform and which widget colours each slot replaces is the preset's (§8; for `kde-breeze`, "The KDE part", *Palette*; for the `accent` slot on `windows-11`, `macos-*` and `ios-13`, §6, step 2).

```rust
// of rule patches pairing `RuleSelector<M>` with that widget's named `PartPatch`/`TextPatch`/`IconPatch` slots.
// All of these are `#[non_exhaustive]`, so each has `new()` and one chained setter per field (written by
// one `macro_rules!`): `ThemePatch::new().button(ButtonRule::new().variant(Primary).states(HOVER).body(PartPatch::new().fill(..)))`.

impl ThemePatch {
    pub fn new() -> Self;
    pub fn corner_scale(self, scale: f32) -> Self;      // clamps finite >= 0.0; NaN -> 1.0
    pub fn spacing_scale(self, scale: f32) -> Self;     // clamps finite >= 0.0; NaN -> 1.0
    pub fn font_family(self, family: impl Into<Arc<str>>) -> Self;
    pub fn monospace_family(self, family: impl Into<Arc<str>>) -> Self;
    pub fn custom_color(self, key: impl Into<String>, color: Color) -> Self;
    pub fn custom_metric(self, key: impl Into<String>, value: f32) -> Self;
```

**TOML file formats (`features = ["toml"]`):**
- `Theme::from_toml(&str)` parses a standalone theme file (`name`, `base`, optional `accent`, optional single `palette` — string name or inline `[palette]` table — OR mutually exclusive `[palettes]` with `light`/`dark` string names or inline tables, plus the `ThemePatch` sections below).
- `ThemePatch::from_toml(&str)` parses only the base-independent patch sections (`[metrics]`, `[typography]`, `[colors]`, `[widgets]`, `[custom_colors]`, `[custom_metrics]`).
- `Palette::from_toml(&str)` parses a standalone `Palette`.
- A theme file on top of the live system: `Theme::from_toml` does no OS I/O, so the caller joins the two —
  `let sys = Theme::from_system()?; Theme::from_toml(s)?.with_context(sys.context().clone()).with_system_overrides(sys.system_overrides().cloned().unwrap_or_default())`.

- **Concise deserialization & strict validation:**
  - Shorthands: `Paint` accepts `"none"`, any `Color` string (solid), a single tagged `{ kind = "solid" | "linear_gradient" | "radial_gradient" | "material", ... }` map (`blend` defaults to `Normal`), or an array of layer maps; `Stroke` accepts `"none"`, `{ width, color, align? }`, or 4-side `{ top, right, bottom, left, align? }`; `Corners` accepts `"none"`, `"pill"`, a uniform `f32`, or `{ radius, curve? }`; omitted `ShadowLayer`/`Transform` fields take identity/zero defaults. A widget's table takes its direct metrics as plain keys (`[widgets.spinner]` `color = "#ffffff"`) and, for a static widget, its parts without `rules` (`[widgets.tooltip]` `panel.fill = "#202020"`).
  - **Serde safety note:** Never combine `#[serde(flatten)]` with `#[serde(deny_unknown_fields)]` (unsupported in `serde`); declare explicit fields on `ThemeFile` and the per-variant rule patch structs so `#[serde(deny_unknown_fields)]` works reliably.
  - Strict errors: unknown keys, unknown preset/palette names (or `FeatureDisabled` when `palettes` is off), both `palette` and `palettes` specified, non-finite numbers, negative radii/widths/blur, opacity outside `0.0..=1.0`, or state/variant selectors on static widgets return `Err(Error::InvalidTheme { .. })` / `Err(Error::UnknownPreset / UnknownPalette / FeatureDisabled)`.

`SystemOverrides` as shown holds everything the four `0.7.2` readers read (KDE, the XDG portal for GNOME, macOS, Windows), so that the reader parity of §11 can pass; what a `0.7.2` reader derives from its reads for the widgets is its preset's builder's. A slot that more than one system can fill is named for what it holds (`alternate_row_background`, `title_bar`, `button`, `menu_font`, `icon_sizes`, `disabled_text`, `scrollbar_width_px`); one whose notion is KDE's own is named `kde_…`.

**The KDE part.** `SystemOverrides` carries the settings as read, each optional — the colours, the two contrast scalars and the effects in the entry of `color_schemes` for the scheme the system is in — and what the `0.7.2` reader derives from them (`kde/colors.rs`, `kde/fonts.rs`) the `kde-breeze` builder derives.
- *Colour sets:* `BackgroundNormal` and `ForegroundNormal` of `[Colors:Window]`, `[Colors:View]`, `[Colors:Button]`, `[Colors:Tooltip]` and `[Colors:Header]` are `background` and `foreground` of `surfaces.window`, `view`, `button`, `tooltip` and `header`; `ForegroundInactive` of the Window and View sets is their `foreground_muted`. Of `[Colors:View]` further: `DecorationFocus` and `DecorationHover` are `kde_decoration_focus` and `kde_decoration_hover`, `BackgroundAlternate` is `alternate_row_background`, `ForegroundLink` and `ForegroundVisited` are `link` and `link_visited`, `ForegroundNegative`, `ForegroundNeutral`, `ForegroundPositive` and `ForegroundActive` are `status[0..4]`. `[Colors:Selection]`'s pair is `selection.background` and `selection.foreground`; `[WM]`'s four colours are `surfaces.title_bar` and `title_bar_inactive`.
- *Scalars:* `[KDE] frameContrast` and `contrast` are `kde_frame_contrast` and `kde_contrast`; `[ColorEffects:Inactive]` gives `kde_effects.change_selection_color`; `[KDE] AnimationDurationFactor` is `animation_scale` and, where it is 0, `MotionPreference::None` in the snapshot's context; `[KDE] CursorBlinkRate` gives `caret_blink_on_ms` and `caret_blink_off_ms` as the `0.7.2` reader computes them (a rate of 0 or less states `caret_blink_off_ms = Some(0)` alone); `[General] ColorScheme` is `theme_name`; `[Icons] Theme` is `icon_theme` and its `index.theme` gives `icon_sizes`; `scheme` and `font_dpi` are set as the `0.7.2` reader sets them (dark where the Window background is dark; 96).
- *Fonts:* `[General] font`, `fixed`, `smallestReadableFont`, `menuFont`, `toolBarFont` and `[WM] activeFont` are `ui_font`, `monospace_font`, `caption_font`, `menu_font`, `toolbar_font` and `title_bar_font`.
- *Derived values.* A value that the `0.7.2` reader derives from one or more settings (a mix, a tint, an overlay, a shade, a translucent copy) the builder computes from the system's settings only where every colour its derivation reads is given; otherwise the preset's own value stays (`0.7.2`: a colour the reader cannot derive keeps the preset's). As in `0.7.2`, a missing Header colour is the Window set's, and a missing `kde_frame_contrast` or `kde_contrast` is KColorScheme's default. Where `ui_font.size` is given, `typography.headline` and `title1` are that size times 1.20 and 1.35 at weight 400 (Kirigami's heading levels 2 and 1, `platform-facts.md` §2.19), in its unit and before rounding.
- *Disabled text.* `view.foreground_muted` is also `colors.disabled_text` (and the input's placeholder colour) where it is given, as the `0.7.2` reader assigns it; without it the preset's own disabled colour stays. The preset's constant and the reader's value differ under Breeze, and each parity test compares its own input.
- *Accent.* The portal's accent is `SystemOverrides::accent`; `OsColors::accent` stays `None`. `colors.accent.fill` is that accent, else `kde_decoration_focus`. A given accent also replaces `colors.selection.background` (and what inherits it), the tab's active indicator and, at Breeze's `Blend_Value`, the focus ring's colour; every other value that `0.7.2` derives from `DecorationFocus` or from `[Colors:Selection] BackgroundNormal` goes on reading `kde_decoration_focus` and `selection.background` (`0.7.2`'s `apply_kde_accent`). The accent applies in whichever scheme is resolved (`0.7.2`'s reader changed only the scheme it read; the accent is one value for every scheme). An application's `SystemOverrides` may state `OsColors::accent`, `focus_ring` or `text_selection` for a scheme: the accent is then `OsColors::accent`, else `SystemOverrides::accent`, else `kde_decoration_focus`; a stated `focus_ring` is the focus ring's colour as given; a stated `text_selection` replaces the text selection's colours.
- *Palette (§6, step 2).* An active palette is laid over the settings as a colour scheme that states the keys its slots name. Each replaces the setting in force below it (the system's where `SystemOverrides` states it for the scheme and contrast resolved, else the preset's Breeze value); a key no slot names keeps that setting.
  - *Colour sets.* `window_bg`, `view_bg`, `tooltip_bg` and `header_bg` are `BackgroundNormal` of `[Colors:Window]`, `[Colors:View]`, `[Colors:Tooltip]` and `[Colors:Header]`; `foreground` is `ForegroundNormal` of those four sets (a palette has one text colour, §7); `foreground_muted` is `ForegroundInactive` of the Window and the View set, so also `colors.disabled_text` and the placeholder (*Disabled text*); `selection_bg` and `selection_fg` are `[Colors:Selection]`'s pair; `link` is `[Colors:View] ForegroundLink`; `error`, `warning`, `success` and `info` are `ForegroundNegative`, `ForegroundNeutral`, `ForegroundPositive` and `ForegroundActive` of `[Colors:View]`.
  - *Accent.* `accent` is `[Colors:View] DecorationFocus` and `DecorationHover`, and so `colors.accent.fill`. Plasma writes an accent into six settings (*Explicit accent*); the four others have slots of their own, which stand.
  - *Title bar.* `[WM] activeBackground` and `inactiveBackground` are `header_bg`, `activeForeground` and `inactiveForeground` are `foreground`: for a scheme that states no `[WM]`, Plasma's `applyScheme()` writes the group from the Header set, its Inactive group's colours for the inactive keys (plasma-workspace 6.8.2, `kcms/colors/colorsapplicator.cpp`), and KColorScheme reads a set without an `[Inactive]` group from its active colours (kcolorscheme 6.31.0, `src/kcolorscheme.cpp`); no effect is stated (*Effects not stated*).
  - *Slots without a KDE setting.* `border` is `colors.window.border`, `0.7.2`'s `defaults.border.color`, and with it every line the builder draws in that colour, the separator's too (Breeze draws a separator in the colour of its frames, `platform-facts.md` §2.18); `divider` states `colors.window.divider` alone. `surface_bg` is, beside its three roles, the fill of the card's, the dialog's and the popover's panel, and `sidebar_bg` that of the sidebar's container (`0.7.2` gives them the View set's or the Window set's background only where unstated); the menu's panel stays Breeze's mix of the Window and the View background. `accent_fg` and `caret` state their roles; the caret is then not `DecorationFocus`.
  - *Not recoloured.* `[Colors:Button]`, `BackgroundAlternate`, `ForegroundVisited`, the two contrast scalars and the effects have no slot and keep the setting in force; a colour of the preset that the `0.7.2` reader never replaces (the disabled states' colours, the tab's fills, frame and text, the sidebar's and the segment's hover fill, the expander's arrow, the shadow) keeps the preset's value, as under the system's colours.
  - *Derived values.* A value of *Derived values* that reads a setting the palette replaced is computed again, with the same kernel and arguments, from the settings in force (not only where the system states every colour it reads); every other derived value keeps what it has. The focus ring's colour is the selection's background at Breeze's `Blend_Value`, and the text selection is the selection. The system's accent (`SystemOverrides::accent`, `OsColors::accent`) is not applied, nor a `focus_ring` or `text_selection` that an application's `SystemOverrides` states: the palette, the later layer, restates those roles. The handle of the view that has the focus (§5, `S3`) is unstated, as under the system's colours.
  - *Text on a fill.* A text on a fill of `[Colors:Selection] BackgroundNormal` is `colors.selection.foreground`; one on a fill of `DecorationFocus`, of `DecorationHover` or of `colors.accent.fill` (the menu's pressed item, the menu bar's hovered and open title, the primary button) is `colors.accent.foreground`. A palette pairs `selection_fg` with `selection_bg` and `accent_fg` with `accent` (§7); without a palette both roles are `[Colors:Selection] ForegroundNormal`, so nothing changes there.
- *Explicit accent (§6, step 2).* `Theme::with_accent` is Plasma's accent setting (kdeglobals `[General] AccentColor`, `platform-facts.md` §2.1.3), and the builder computes what Plasma's `applyScheme()` writes for it over the settings in force, the palette's included, with the `kde_accent` kernel (plasma-workspace 6.8.2, `kcms/colors/colorsapplicator.cpp`; the kernel is checked against its vector table, made by running that source). It writes six settings: `[Colors:View] DecorationFocus`, `DecorationHover` and `ForegroundActive` are the accent; `ForegroundLink` is the accent, lightened or darkened where it reads poorly on `[Colors:View] BackgroundNormal`; `[Colors:Selection] BackgroundNormal` is the accent at alpha 0.7 over `[Colors:View] BackgroundNormal`, and `ForegroundNormal` black or white by Plasma's contrast measure. They replace the system's settings and the palette's `accent`, `info`, `link`, `selection_bg` and `selection_fg`. `colors.accent.fill` is the accent as written, `colors.accent.foreground` the selection's foreground (a palette's `accent_fg` belongs to the accent replaced), and the caret `DecorationFocus` unless a palette states `caret`; the derived values, the focus ring, the text selection, the system's accent and `S3` follow *Palette*'s rules. Plasma tints a scheme only where its file states `TintFactor`, and colours the title bar only where the file states `TitlebarIsAccentColored` (else `accentActiveTitlebar`, else false); Breeze's files state neither, and the reader carries neither (`0.7.2` reads neither), so neither step is run: `[WM]` and the Header set keep their colours. A fully transparent accent (`#00000000`) is Plasma's "accent from the colour scheme": no accent. The system's accent is another quantity and keeps `0.7.2`'s rule (*Accent*): the KDE portal reports `QPalette::Highlight`, the selection Plasma has already derived (`0.7.2`'s `apply_kde_accent`), where `Theme::with_accent` is that derivation's input.
- *Effects not stated.* Where `OsColors::kde_effects` is `None` (the file states neither `ChangeSelectionColor` nor `Enable`), the builder takes `change_selection_color` as true, KColorScheme's default as the `0.7.2` reader resolves such a file, and applies no inactive or disabled effect.
- *Name.* The KDE reader states `theme_name` as `[General] ColorScheme`, and `"KDE"` where the file states none, as the `0.7.2` reader names the theme; `resolved.name` is then that name (§6, step 2).


**Every reader.**
- *Scheme-wide settings.* A setting that is one value for both schemes (a font, the portal's or Windows' accent, the accent ramp, a caret time, the scroll bar's sizes) applies in whichever scheme is resolved (an icon theme and its sizes by the rule of §6, step 2); a colour read for one scheme sits in that scheme's entry of `color_schemes` and applies there only. `0.7.2`'s single-scheme readers (KDE, the portal, Windows) wrote everything into the scheme they read and left the other one to the preset, so reader parity (§11) is taken in the scheme the system was read in (`SystemOverrides::scheme`).
- *Context.* The snapshot's `ThemeContext` holds the scheme, the contrast level, the motion level, `reduced_transparency` and `text_scale` as the reader's settings give them, and every other field at its default. `0.7.2` reports the motion setting and the text scale in `accessibility` and applies neither to the theme's values; reader parity therefore resolves with the snapshot's context but `motion` and `text_scale` at their defaults and `SystemOverrides::animation_scale` unset (a factor of 0 collapses the dialog's entrance as `MotionPreference::None` does), and compares the motion setting and the text scale through their own rows of the table of homes. A text scale that is not a finite number above 0 is not carried: the context keeps 1.0 and the reader adds a `DiagnosticEntry`.
- *Caret.* `caret_blink_on_ms`, `caret_blink_off_ms` and `caret_blink_timeout_ms` hold the times as the platform's `0.7.2` reader computes them from its setting: turning a platform's blink setting into an on and an off time is the reader's parse, on every platform as on KDE.
- *Name and icon set.* Every reader states `theme_name` as its `0.7.2` reader names the theme: the KDE colour scheme's name (else `"KDE"`), `"GNOME"`, `"macOS"`, `"Windows"`. The icon set has no slot: each platform's preset states the set its `0.7.2` reader wrote.

**The GNOME part** (`reader/portal.rs`, preset `adwaita`).
- *Settings:* the portal's `color-scheme`, else gsettings `color-scheme`, gives `scheme` (light where neither answers); the portal's `accent-color` is `accent` (not carried where a channel lies outside 0..=1); gsettings `font-name`, `monospace-font-name` and `org.gnome.desktop.wm.preferences titlebar-font` are `ui_font`, `monospace_font` and `title_bar_font`, each with the weight and style its Pango description gives (400 and normal where the string names none); `overlay-scrolling` is `overlay_scrollbars`; `icon-theme` is `icon_theme`, and `icon_sizes` stays `None`; `cursor-blink-time` *t* gives `caret_blink_on_ms` = `caret_blink_off_ms` = *t* / 2, `cursor-blink` false gives `caret_blink_off_ms = Some(0)`, and `cursor-blink-timeout`, in seconds, gives `caret_blink_timeout_ms`; `font_dpi` is 96. The reader makes no entry of `color_schemes`.

From `ui_font.size`: the sizes of `typography.caption` (× 0.82), of `title1` and the dialog's title (× 1.36) and of `display` (× 1.81), in the size's unit; their weights and `headline` stay the preset's. Without an accent or a UI font the preset's values stay.

**The macOS part** (`reader/macos.rs`, presets `macos-monterey` and `macos-tahoe`).

## 10. Connector Contract (`iced`, `gpui`, `egui`, `egui-widgets`)

Each connector accepts `&ResolvedTheme` (plus optional `Arc<ResolvedTheme>` caching) and follows five uniform rules:

0. **Only what is stated:** a connector applies a part's property only if its `stated` bit is set, and a scalar only if it is `Some`; otherwise the toolkit's own value stays. It never substitutes a number of its own.
   **A state the theme leaves unstated** (§2, `from_state`) keeps the toolkit's own *treatment* of it, per property: where the toolkit's own style changes the property between rest and that state, the toolkit's value for that state; where it leaves the property unchanged, the theme's value at rest; what the theme states for the state is laid over.
0a. **A state the toolkit has no status for:** where a toolkit's widget has no status for a model state (iced's button has none for `CHECKED`) and the connector gives a function for it, the function draws what the theme states for the state (`from_state`, asked with that flag alone). A property the theme does not state for it takes the toolkit's own way of showing the state, which the connector's README names with its source. Where that way is another status or class of the toolkit, the state is drawn in that status or class as the connector themes it, so every value is the theme's or the toolkit's. The connector does not take the theme's value of another state by a chain of its own (the pressed fill, then the hovered one, for an unstated `CHECKED`): which state looks like which is the theme's to state, by a rule for that state. For iced's button the way is the primary class, by which iced's own `todos` example marks the chosen filter button (iced 0.14.0 `examples/todos/src/main.rs`): an unstated `CHECKED` fill and its label are those of the connector's primary button in the same status, on the plain button and the toolbar's; a stated `CHECKED` fill is lettered in the stated `CHECKED` label, else in the label at rest (a label is chosen for the fill it lies on, as for every state under rule 0); outline, corners, padding and shadow stay the unchecked button's. gpui-component and egui have a selected style of their own (`Button::selected`), so rule 0 holds there as written.
1. **Globals + per-widget queries:** Map global toolkit structures (`egui::Visuals`/`Style`, `gpui_component::Theme`, `iced::theme::Palette`) from `resolved.colors`, `resolved.typography`, `resolved.layout`, `resolved.icons`, `resolved.context`, and map widget styles (`iced::widget::button::Style`, `native-theme-egui-widgets`, `gpui` style helpers) directly via `resolved.<widget>.<part>(query)`. A `Typography` slot is read through `Typography::over_body` (§4): what it leaves unstated is `body`'s, not the toolkit's, and rule 0 holds for the style that returns.
2. **Color & material conversion:** Toolkits rendering 8-bit sRGB convert via `color.clamped().to_srgb8()` (or `f32` channels). Toolkits without backdrop blur render `material.fallback` (or `paint.flatten_over(surface_bg)`); toolkits supporting only one shadow layer take the primary drop shadow layer. **Corner curve:** a toolkit whose rounded rectangle is circular (iced `border::Radius`, egui `CornerRadius`, gpui `Corners<Pixels>`) draws `CornerCurve::Continuous` as the circular corner of the stated radius: the radius is the theme's, the curve the toolkit's. A stated curve never makes a value unmapped and never drops the radius; the radius's form is mapped as under `Circular`. The README names the limit (rule 4); Widget Info shows `<value> (drawn circular)`.
3. **Icons & spinners:** Use `resolved.icons` (`set`, `theme`, `sizes`) with `load_icon` / `load_icon_indicator` (`AnimatedIcon`) and `fonts::system_face` when `system-fonts` is enabled.
4. **Honest toolkit limits & lean tests:** Record any upstream toolkit limitation (e.g., lack of backdrop blur, spring animations, or per-side strokes) in the connector's README; verify the connector by connector parity during the port (its output to the toolkit from the new model equals its output from the `0.7.2` model, for each of the seven platform presets and both schemes; differences listed with reasons), and keep the existing mechanical gates, ported to the field list the golden snapshots give (§11): connector parity (every stated property read or excepted with a reason), showcase parity, the Widget Info claims, and captures compared side by side with `0.7.2`'s.

## 11. Verification & Performance Gates

The plan orders the work and names each milestone's gate; the checks themselves are these:

1. **Layout & allocation (in `cargo test`):** the `size_of` assertions of §2; an allocation-counting test (the dev-dependency `dhat` in its testing mode, so that no `unsafe impl GlobalAlloc` is written here; plan, rule 6) showing zero allocations in `RuleSet::eval`, `PartStyle::clone` and the `WindowChrome` queries; the resolved theme's heap bytes under 256 KB for every bundled preset (the live bytes that test's allocator reports after `resolve()` minus before it, the `ResolvedTheme` held).
2. **Speed and compiled size (measured, not asserted in a test — a timing assertion fails on a loaded machine):** a release-mode bench (`harness = false`, `std::time`, medians) reports `Theme::resolve` (hard limit 1 ms, target 0.5 ms) and a part query (limit 100 ns) for every bundled preset; the compiled size of the preset builders is the sum of the `presets` module's symbols in a release build (`nm --size-sort`), limit: less than the 446 KB of preset text that `0.7.2` embeds (its 17 TOML files; 347 KB for the seven platform presets), which it also parses at run time with `toml` and `serde` in every build — the first milestone's projection for all presets is 270–300 KB (plan §4), against the 150 KB first written here without data; the figure is taken again at each platform unit, and a unit that moves the projection above the limit stops the work. The figures are taken at the plan's first milestone on six widgets, projected, and taken again at each later milestone; a missed limit stops the work for a decision, it is not tuned around.
3. **Golden platform math vectors:** every salvaged or new formula against its committed `tests/vectors/*` table.
4. **Equality with `0.7.2` (while both models exist):** for each of the seven platform presets of `0.7.2` and both schemes, every field of the old resolved theme equals the value at its new home (the table of homes is the test's data); the old reader path and the new one give the same theme from the same system settings; and each connector's output to its toolkit is the same from both models. Golden snapshots of the resolved themes (`ResolvedTheme`'s `Serialize`), one per preset and scheme, are written as each preset passes and remain after these tests are deleted at the cut; the snapshots' (widget, part, property), metric and global names are the field list the ported parity scripts and the Widget Info claims read, and a Widget Info leaf is a home: that name, plus the query on a ruled part.
