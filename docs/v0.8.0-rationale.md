# native-theme v0.8.0 — Architectural Rationale

**Status:** Proposed design, branched from `v0.7.2` (`main`).
**Supersedes:** The parked model-completeness design (`docs/todo_v0.8.0_model-completeness-*` on `main` / `docs/todo_v0.7.1_model-completeness-*` on `v0.8.0-rc1`, parked 2026-11-13).
**Follow-up docs:** `docs/v0.8.0-spec.md` (exact Rust types & contracts) and `docs/v0.8.0-plan.md` (vertical implementation milestones).

---

## 1. Goal and Problem Statement

`native-theme` exists to let any Rust GUI application achieve **pixel-accurate native look and feel** across all supported platforms (`adwaita`, `kde-breeze`, `macos-monterey`, `macos-tahoe`, `windows-11`, `material-3`, `ios-13`, `ios-26`), while staying **fast**, **small in binary and memory footprint**, **easy to use**, **stable toward 1.0**, and **expressive enough for customized and fancy themes**.

Two verified baselines establish the exact constraints:

1. **`v0.7.2` (`main`)** loads in < 1 ms, is compact, and ships working connectors (`native-theme-iced`, `native-theme-gpui`, `native-theme-egui` + `native-theme-egui-widgets`). However, its **flat struct-of-`Option`s model** hits hard limits:
   - Every new state combination adds ad-hoc fields (`button.hover_border_color`, `list.hover_border_color`, and next `list.inactive_hover_*`, `list.selected_hover_*`), cascading across >100 inheritance rules in `docs/inheritance-rules.toml` (including 40 documented `wrong_safety_nets`), 17 TOML presets (7 platform + 10 community), and every connector.
   - Core visual capabilities from the 6-platform gap survey (`docs/todo_v0.8.0_model-completeness-gap-map.md`, `C01`–`C28`) are missing or incomplete: multi-layer shadows, backdrop materials (Liquid Glass, Mica, Acrylic, vibrancy), unflattened translucent fills, wide-gamut Display P3 colors, per-corner continuous radii, per-side/gradient strokes, widget variants and control sizes, preset-level accessibility/contrast variants (`0.7.2` only reflects contrast via live OS readers), full typography ramps, declarative motion timings, window chrome states, and color-only palettes (every community theme duplicates 497 lines of geometry).
2. **Parked `v0.8.0-rc1`** aimed for full visual completeness, but exploded in complexity, runtime cost, and engineering/token overhead:
   - With only **1 widget (`button`)** implemented, `native-theme/src` doubled (51K → 103K LOC), `scripts/` grew from 19K → 51K LOC (`.py` scripts quadrupled 11K → 42K LOC, including a 316 KB `generate_preset.py` and 361 KB `check_facts.py`), bundled preset TOMLs reached 951 KB (for 1 widget), load time degraded from **< 1 ms to 0.3–40 s** with up to **1.4 GiB RAM**, `docs/facts/` grew to **66 MB**, model-completeness design docs reached **6.9 MB**, and the unsharded facts gate ran for **459 min (7.65 h)**.
   - Almost none of that cost came from visual fidelity. It came from five compounding choices: (a) encoding platform math as an interpreted TOML expression VM + CSS DOM selector engine, (b) proving that DSL panic-free via a runtime combinatorial validator, (c) generating presets from a 66 MB Cartesian fact matrix via Python codegen/gates, (d) modelling toolkit-internal animation/scroll-physics runtime engines inside a theme crate, and (e) maintaining multi-megabyte cross-referenced specs/ledgers through multi-pass review loops.

**This architecture preserves the visual fidelity of `C01`–`C28` while eliminating all five sources of accidental complexity.**

## 2. Principles and Explicit Non-Goals

### Guiding Principles

1. **Compiled Rust for platform logic; simple data for overrides.** Platform derivations (OKLab standalone accents, `color-mix`, `KColorScheme`/`KColorUtils`, Material 3 HCT, WinUI curves, Apple Dynamic Type) belong in normal `rustc`-checked Rust functions — not an interpreted TOML expression VM.
2. **Two pure phases: resolve once per context, query infallibly in nanoseconds.** `Theme::resolve(&ThemeContext)` runs platform derivations once (< 0.5 ms), producing an immutable, concrete `ResolvedTheme`. Draw-loop queries evaluate concrete values with zero panics, zero expression parsing, and zero heap allocations.
3. **One composable visual vocabulary, zero unnecessary abstraction.** Every widget uses the same compact visual primitives (`Color`, `Paint`, `Corners`, `Stroke`, `ShadowLayer`, `Transform`, `TextStyle`, `IconStyle`, `FocusIndicator`, `Transition`, `PartStyle`). Widgets that vary by state/variant use compact rule tables; static widgets (`Tooltip`, `Separator`, `LayoutMetrics`) hold direct concrete fields.
4. **True to every platform, ergonomic for every toolkit.** No fake DOM trees or font-metric callbacks in core queries. Connectors pass a single lightweight `Copy` query (`StyleQuery<V>`, or bare `WidgetState` in the common case).
5. **Verified facts without meta-machinery bloat.** Keep zero invented platform values via inline upstream source citations, compiled golden vector tests for every derivation formula, and targeted `os-probe` checks — not a 66 MB fact DB and 42K LOC of Python gate scripts.
6. **Native by default, expressive for fancy themes.** The same visual primitives that render Liquid Glass, Mica, and WinUI elevation natively also power custom palettes, glassmorphism, neon glows, brutalist shadows, and animated hover transforms cleanly.

### Explicit Non-Goals (The Anti-Bloat Contract)

To protect binary size, compile time, runtime speed, and maintainability, `v0.8.0` explicitly rejects:

- **No TOML expression language or runtime AST evaluator.**
- **No CSS DOM ancestor/sibling matcher or `FontMetrics` callback in core queries.**
- **No runtime combinatorial proof validator (`validate/combos`).** Concrete resolved values + Rust's type system guarantee infallible queries by construction.
- **No toolkit animation runtime engines, scroll-fling physics engines, or interaction-recency queues** (including no frame-by-frame `ripple.rs` shader engine). `native-theme` supplies exact declarative timing/curve/spring/ripple data; GUI toolkits drive their own frame loops.
- **No runtime main-thread OS widget bitmap rendering** (such as offscreen AppKit `NSButton` rendering into caches). Control glyphs use verified geometry/color/stroke tokens plus platform icon loaders so every preset works identically on every OS and thread.
- **No machine-parsed `docs/facts/` database, Python preset codegen, or multi-hour combinatorial facts gate.**
- **No proc-macro model generator (`native-theme-derive`) or `inventory` inheritance registry.**
- **No multi-megabyte markdown widget catalogues, ledgers, or doc-linter loops.** Design docs stay concise; Rust types and doc comments own per-widget field documentation.

## 3. Architectural Decisions

Every decision below weighs all viable alternatives, their pros and cons (including honest cons of the chosen design), and why the chosen design is the best long-term 1.0 solution.

### D1 — Scope, Platforms, Flavors, Mobile Availability, and Issue #4 (`v0.7.3`)

- **Platforms (8 bundled presets):** `adwaita` (GTK 4 / libadwaita), `kde-breeze` (Plasma 6 Breeze), `macos-monterey` (macOS 12–15 Aqua), `macos-tahoe` (macOS 26+ Liquid Glass), `windows-11` (WinUI 3 / Fluent 2), `material-3` (Material 3 / Compose), `ios-13` (iOS 13–18), and `ios-26` (iOS 26+ Liquid Glass).
- **Platform flavors (`Flavor::Default | Kirigami | Expressive`) — options weighed:**
  - *Option A (Separate presets: `kde-kirigami`, `material-3-expressive`):* Avoids a flavor axis, but duplicates 80–90% of `kde-breeze` and `material-3` rules and obscures that Kirigami and Qt Widgets share one live KDE OS configuration.
  - *Option B (Single preset + `ThemeContext::flavor` — **chosen**):* `kde-breeze` defaults to Qt Widgets (`Default`) with opt-in `Kirigami`; `material-3` defaults to Baseline (`Default`) with opt-in `Expressive`. Other presets ignore inapplicable flavors cleanly. *Con:* Adds one 1-byte field to `ThemeContext` and flavor branches in two builders; worth avoiding two redundant presets.
- **Widget scope — options weighed:**
  - *Option A (All 118 controls from `C24` in `0.8.0`):* Re-creates the months-long scope explosion that stalled `v0.8.0-rc1`.
  - *Option B (Minimal ~10-widget subset):* Regresses working `0.7.2` connectors and showcases.
  - *Option C (All 25 widgets + `window` chrome + `layout` metrics from `0.7.2`, plus `radio` split from `checkbox` and first-class `menu_bar` — **chosen**):* Achieves 100% parity with `0.7.2` (27 sections), fixes Material 3's 20 px radio vs 18 px checkbox conflict and KDE's `menu_bar` titlebar/tools-area chrome, and lets `C24` additions (`badge`, `search_field`, `date_picker`, `toast`, etc.) land non-breakingly in `0.8.x` via `#[non_exhaustive]` on `ResolvedTheme`.
- **Desktop-only widgets on mobile presets (`ios-13`, `ios-26`, `material-3`) — options weighed:**
  - *Option A (`Option<Widget>` — `None` when absent):* Strictly records absence, but forces every connector and desktop showcase to unwrap every widget and invent inconsistent toolkit fallbacks (which blocked `ios-26` in `0.7.2` on 38 missing desktop fields).
  - *Option B (Always-present widget tagged `WidgetOrigin::{Native, Synthesized}` — **chosen**):* Every widget is always queryable without unwrapping. Where a platform genuinely lacks a desktop control (e.g., `status_bar`, `splitter`, `tooltip` on iOS), the builder synthesizes a cohesive style strictly from that platform's own verified `ColorRoles`, `Typography`, and `Corners`, tagged `WidgetOrigin::Synthesized`. *Con:* Synthesized defaults still require basic upkeep and strict consumers must check `.is_native()` if they want native-only gating; worth never unwrapping or falling back to unthemed defaults.
- **Issue #4 and skipping `v0.7.3` — options weighed:**
  - *Option A (Ship `v0.7.3` on `0.7.x` first):* Adds throwaway flat fields to `ListTheme` (`inactive_hover_*`, `selected_hover_*`) across 17 presets, `property-registry.toml`, `inheritance-rules.toml`, 3 connectors, showcases, and captures — all deleted immediately in `0.8.0`.
  - *Option B (Skip `v0.7.3` and solve all remaining issue #4 items natively in `v0.8.0` — **chosen**):* Both `v0.7.3`-earmarked items (`L2`: hovered row in an unfocused list; `L3`: selected + hovered row via a new clean-room `qt_lighter` with HSV saturation-overflow handling verified against black-box Qt vectors — noting `qt_lighter` was not yet implemented on `v0.8.0-rc1`) AND the remaining KDE leftovers (`L4` list row highlight margin vs padding, `S1–S4` scrollbar states/outlines, `Z1–Z3` optional `min_size`/dialog limits, menu shortcut text) fall out naturally from `v0.8.0`'s parts and `WidgetState` bitflags. Leaving `main` clean also preserves the option for a dependency-only `0.7.3` if an upstream toolkit bump urgently needs one.

### D2 — Two-Phase Pure Resolution & Compiled Rust Platform Builders

- **Preset representation — options weighed:**
  - *Option A (Static TOML per preset, `0.7.2`):* Fast (< 1 ms), but duplicates light/dark geometry, pre-flattens translucent colors over one background, and relies on >100 fragile inheritance rules.
  - *Option B (Interpreted TOML rules + expression VM, parked `v0.8.0-rc1`):* Expressive, but requires a custom AST, combinatorial validator, and megabyte TOMLs (0.3–40 s load, 1.4 GiB RAM).
  - *Option C (Hybrid: raw TOML constant tables + Rust derivation code):* Saves some Rust syntax, but keeps runtime TOML parsing mandatory for built-in presets and splits each platform across two files/languages.
  - *Option D (Compiled Rust `ThemeSource` platform builders + pure `Theme::resolve(&ctx) -> ResolvedTheme` — **chosen**):* Zero runtime parsing for bundled presets, compile-time checked by `rustc`, compact machine code, < 0.5 ms resolve, ~50–100 KB resolved RAM, and allows `serde`/`toml` to be fully optional. *Con:* Editing a built-in platform preset requires editing Rust rather than a data file; acceptable because platform presets change rarely, require platform-verified citations anyway, and user/custom themes still support TOML via `ThemePatch` (D8).
- **Stateless `resolve()` & two top-level types vs internal caching — options weighed:**
  - *Internal cache inside `Theme` (`Mutex`/`ArcSwap`) + separate `SystemTheme` (`0.7.2`):* Splits the entry point across three top-level types (`Theme`, `SystemTheme`, `ResolvedTheme`), adds interior mutability and cache eviction policies, and complicates multi-window apps (e.g., an active main window + an inactive utility window simultaneously).
  - *Single `Theme` (`Clone + Send + Sync`, zero-alloc for bundled presets) + pure stateless `Theme::resolve(&self, ctx: &ThemeContext) -> ResolvedTheme` (**chosen**):* Retires `SystemTheme` cleanly so users learn only **two** top-level types (`Theme` → `ResolvedTheme`). `ResolvedTheme` is `Clone + PartialEq + Send + Sync + Debug`, records its effective resolved `context: ThemeContext`, `preset: Option<Preset>`, and `name: Arc<str>`, and resolves fast enough (< 0.5 ms) that apps/connectors simply hold `Arc<ResolvedTheme>` and rebuild only on OS watcher events or focus changes.

### D3 — Sparse Bitflag Queries, `StyleQuery<V>`, and Orthogonal Axes

- **Query architecture — options weighed:**
  - *Option A (Flat fields per state, `0.7.2`):* Field explosion; fails on combined states (`checked + hover`, `selected + hover`), variants, and sizes.
  - *Option B (DOM-style CSS ancestor/sibling selector tree, `v0.8.0-rc1`):* Forces immediate-mode (`egui`) and functional (`iced`) toolkits to synthesize fake DOM trees and `FontMetrics` callbacks.
  - *Option C (28 bespoke `XxxPatch` / `XxxQuery` structs):* Reintroduces proc-macro boilerplate and verbose query construction.
  - *Option D (Two-level context + one generic `StyleQuery<V>` + sparse `RuleSet` over 3 shared prop enums — **chosen**):* Only **3** property-patch enums (`PartProp`, `TextProp`, `IconProp`) and **1** generic query struct (`StyleQuery<V = ()>`) exist crate-wide, paired with concise Rust builder helpers (`widget.when(sel).body(...).label(...)`). Static widgets (`Tooltip`, `Separator`, `LayoutMetrics`) store concrete fields directly — `RuleSet` is used only on parts that actually vary. *Con:* Cannot automatically match arbitrary deep CSS ancestor chains (e.g., "a popover opened from inside a header bar") without the caller passing the current `surface`; in practice every GUI toolkit already knows which surface it is currently painting (`Surface::Popover` vs `Surface::HeaderBar`), making explicit `surface` passing both simpler and faster.
- **Level 1 — `ThemeContext` (window/app scope, passed to `resolve()`):**
  - `scheme: Scheme` (`Light | Dark`), `contrast: Contrast` (`Normal | Increased | High`), `motion: MotionPreference` (`Full | Reduced | None`, covering both GNOME's `reduced-motion` and `enable-animations = false` / KDE `AnimationDurationFactor == 0`), `reduced_transparency: bool`, `bold_text: bool`, `button_shapes: bool`, `differentiate_without_color: bool`, `window_active: bool`, `overlay_scrollbars: bool`, `text_scale: f32`, `density: Density` (`Compact | Standard | Touch`), `direction: Direction` (`Ltr | Rtl`), `flavor: Flavor`.
  - Covers 100% of `C06` and `C23` without bloating draw-loop queries.
- **Level 2 — Single generic `StyleQuery<V = ()>` (`Copy`, 8–12 B):**
  - Shared fields: `state: WidgetState`, `size: ControlSize` (`Mini | Small | Regular | Large | ExtraLarge`), `surface: Surface` (`Window | View | HeaderBar | Sidebar | Card | Dialog | Popover | Tooltip | Osd`), `position: GroupPosition` (`Single | First | Middle | Last`), `orientation: Orientation` (`Horizontal | Vertical`), and `variant: V`.
  - **Ergonomic common case:** Every ruled part getter takes `impl Into<StyleQuery<V>>`, and `From<WidgetState>` is implemented for all `StyleQuery<V: Default>` — so 80% of call sites write a one-liner (`resolved.checkbox.indicator(WidgetState::CHECKED | WidgetState::HOVER)` or `resolved.button.body(WidgetState::HOVER)`), while full queries use builder methods (`ButtonQuery::primary().pill().state(WidgetState::HOVER)`).
  - **Widget-specific `V` axes (only where needed — 4 variant enums):**
    - `Button`: orthogonal `ButtonVariant` (`Standard | Primary | Secondary | Destructive | Outlined | Flat | Glass | Link`) × `ButtonShape` (`Default | Pill | Circle | Square`), while toggles and dialog defaults use `WidgetState::CHECKED` and `WidgetState::DEFAULT`. Cleanly expresses `Primary + Pill`, `Destructive + Pill`, `Glass + Circle`, and `Flat + CHECKED` with zero illegal combinations (`Primary + Destructive`) and zero `:not(...)` selector logic.
    - `Input` / `TextArea`: `InputVariant` (`Standard | Outlined | Filled | Search | Borderless`).
    - `Tab`: `TabVariant` (`Standard | Document | Pill | Segmented`).
    - `List`: `ListVariant` (`Plain | InsetGrouped | Sidebar | Table`) + `alternate: bool` (row parity for striped views, keeping `GroupPosition` clean).
  - **`WidgetState` (hand-written `u32` bitflags, zero dependencies):** `HOVER`, `PRESSED`, `FOCUSED`, `FOCUS_WITHIN`, `FOCUS_VISIBLE`, `UNFOCUSED_VIEW`, `DISABLED`, `CHECKED`, `SELECTED`, `INDETERMINATE`, `OPEN`, `DEFAULT`, `INVALID`, `READ_ONLY`, `VISITED`, `DRAGGED`, `DROP_TARGET`, `SCROLLED`.
  - **Why `UNFOCUSED_VIEW` instead of `UNFOCUSED`:** Keeps `WidgetState::SELECTED` intuitively returning active/emphasized selection by default (critical for toolkits that do not track per-list focus), avoids any contradiction with `FOCUSED` (keyboard focus on an element itself), and cleanly distinguishes an unfocused list inside an active window (issue #4 `L2`) from an inactive OS window (`ThemeContext::window_active == false`).
- **Rule precedence & storage — options weighed:**
  - *CSS specificity scoring:* Complex to debug, diverges across platforms, and makes `ThemePatch` overrides unpredictable.
  - *Explicit stated order (last-match-wins) + ordered exclusive-state groups (**chosen**):* Deterministic single-pass evaluation. Each `RuleSet` holds optional ordered exclusive groups (`&'static [WidgetState]`, e.g., WinUI's `&[DISABLED, PRESSED, HOVER]`) applied before matching, plus `required_states` / `forbidden_states` masks. All property patches in a `RuleSet` live in **one flat `Arc<[Prop]>` buffer** indexed by `(start: u16, len: u16)` per rule — one allocation per part at `resolve()`, **no `smallvec` dependency**, cache-hot ~30 ns evaluation, zero allocations per query or `ResolvedTheme::clone()`.

### D4 — Compact Unified Visual Building Blocks (`C01`–`C28`)

- **`Color` representation — options weighed:**
  - *8-bit `Rgba([u8; 4])` (`0.7.2`):* Clips Display P3 colors (`C28`) and unclamped OKLab intermediate values.
  - *Tagged color-space enum (`Srgb | DisplayP3 | Oklch`):* Requires mixed-space conversion rules on every blend/mix operation.
  - *Extended-sRGB `f32` `Color { r, g, b, a }` (**chosen**, exhaustive):* Represents Display P3 losslessly (channels may lie outside `0.0..=1.0`), uses one arithmetic space matching AppKit/UIKit extended sRGB, and provides `.to_srgb8()`, `.to_premultiplied_srgb8()`, `.clamped()`, `.composite_over()`, and Display P3 helpers. *Con:* 16 B instead of 4 B, and sRGB8 toolkits must clamp out-of-gamut P3 colors via `.clamped().to_srgb8()`.
- **Memory layout of `PartStyle` — options weighed:**
  - *Unboxed inline enums / `SmallVec`s:* Recursive `Paint::Layers`, 4-side `Stroke`, dual `FocusIndicator` strokes, inline `RippleSpec`, and shadow lists inflate `sizeof(PartStyle)` to ~1.5 KB (slow copies on every query) and pull in `smallvec`.
  - *Compact value core + `Arc`-shared rare/complex sub-blocks (**chosen**):* 95% of paints are `Solid(Color)` and most parts have no shadows, ripples, or complex strokes. Sharing complex variants keeps `sizeof(Paint)` = 24 B, `sizeof(Stroke)` = 32 B, and `sizeof(PartStyle)` **≤ 256 B** (3–4 cache lines), with **zero heap allocation on `PartStyle::clone()`** (`Arc::clone` only when present) and zero collection dependencies. *Con:* One heap allocation per complex/shadowed part during `resolve()` (never during queries) and pointer indirection when reading complex fills/shadows.
- **The visual blocks:**

| Block | Representation | Gap-map coverage |
|---|---|---|
| `Color` | Exhaustive extended-sRGB `f32` `(r, g, b, a)` + `.to_srgb8()`, `.clamped()`, `.composite_over()` | `C04`, `C28` |
| `Paint` | `None \| Solid(Color) \| Complex(Arc<ComplexPaint>)` holding non-recursive `PaintLayer`s (`Solid`, `LinearGradient`, `RadialGradient`, `Material(MaterialSpec)` with `BlendMode`). Platform builders pre-bake stacked fills and Material state-layer overlays into concrete `Paint` values once during `resolve()` so `RuleSet` queries only `Arc::clone` (**zero heap allocations per query**) and connectors render one unified `fill`. | `C03`, `C04`, `C08`, `C27` (`resolve()` swaps materials to opaque/inactive fallbacks under `reduced_transparency` or `!window_active`) |
| `Corners` | `Uniform(f32) \| PerCorner([f32; 4]) \| Pill \| Concentric { inset, min_radius }` + `CornerCurve::{Circular, Continuous}` (`Pill` already covers circles on square boxes and capsules on bars; no unused `Elliptical` variant) | `C11` |
| `Stroke` | `None \| Uniform { width, color, align } \| Complex(Arc<ComplexStroke>)` (per-side widths/colors, gradient strokes, `StrokeAlign::{Inside, Center, Outside}`) | `C12`, `C27` |
| `ShadowLayer` | `Option<Arc<[ShadowLayer]>>` (`offset_x/y`, `blur`, `spread`, `color`, `inset`) + `ResolvedTheme.elevations` ramp | `C01`, `C02` (Material surface tint resolved directly into fills during `resolve()`) |
| `Transform` | `scale`, `rotation_deg`, `translation`, `origin` (28 B `Copy`, identity default) | `C13`, `C14`, `C22` |
| `FocusIndicator` | `Option<Arc<FocusIndicator>>` (`kind: Ring \| Fill \| Underline`, `stroke`, `offset`, `corners`, optional `inner_stroke`, `trigger: FocusTrigger::{Always, KeyboardOnly}`) — always populated on focusable target parts (`checkbox.indicator` vs `button.body`) and overridable by state rules (e.g., `INVALID` red ring), serving both global-struct and per-draw-call connectors | `C15` |
| `RippleSpec` | `Option<Arc<RippleSpec>>` (8 B; declarative Material press ripple: `color`, `bounded`, `enter_ms`, `exit_ms`) | `C08` |
| `Transition` | `Option<Transition>` (`duration_ms`, `delay_ms`, `timing`) | `C14` |
| `PartStyle` | Lean box style (≤ 256 B: `fill`, `stroke`, `corners`, `shadows`, `opacity`, `transform`, `padding`, `margin`, `min_size`, `max_size`, `focus`, `ripple`, `transition`, `cursor`) — `min_size`/`max_size` use `[Option<f32>; 2]` so unconstrained dimensions are never conflated with exact sizes (issue #4 `Z1`/`Z2`) | `C07`–`C13`, `C22` |
| `TextStyle` / `IconStyle` | Separate lean structs for text/icon parts using shared `Arc<str>` font family (zero-allocation clone; fallback chain lives once on `Typography`, not repeated per `TextStyle`) | `C18`, `C19` |

- **Multi-part widgets (`C13`):** Every widget exposes its visible parts explicitly (e.g., `Button`: `body`, `label`, `icon`; `Checkbox`: `indicator`, `checkmark`, `label`; `Radio`: `indicator`, `dot`, `label`; `Switch`: `track`, `thumb`, `label`; `Slider`: `track`, `active_track`, `thumb`, `tick`; `Tab`: `bar`, `tab`, `label`, `indicator`, `close_button`, `close_icon`; `Input`: `field`, `text`, `placeholder`, `helper_text`; `Menu`: `panel`, `item`, `item_label`, `shortcut`, `icon`, `submenu_arrow`, `separator`; `MenuBar`: `bar`, `item`, `item_label`), with both per-part getters and a combined `parts(query)` convenience method.

### D5 — Semantic Surface-Aware Color Roles

- **Color role structure — options weighed:**
  - *Option A (Extend `0.7.2`'s flat 25-color `ThemeDefaults`):* Cannot model KDE's 7 color sets, libadwaita's surface hierarchy, or iOS's elevated dark surfaces (`C05`, `C06`).
  - *Option B (Embed selection colors in every `SurfaceColors` record):* Bloats non-selectable surfaces (`tooltip`, `osd`) and blurs item selection vs inline text selection (`C17`).
  - *Option C (Platform-keyed `HashMap<String, Color>` alongside typed roles, `v0.8.0-rc1`):* Exposes raw upstream names (e.g., WinUI's 40 brush keys), but introduces stringly-typed lookups and platform-specific branching in portable apps.
  - *Option D (Typed 9-surface `SurfaceColors` + dedicated global/selection/status roles — **chosen**):*
    - **Named surfaces** (`window`, `view`, `header`, `sidebar`, `card`, `dialog`, `popover`, `tooltip`, `osd` — naturally carrying iOS elevated dark surfaces on `card`/`dialog`/`popover`, Material's surface container ladder, and KDE's `Complementary` on `osd`): each holds 5 concrete `Color`s (`background`, `foreground`, `foreground_muted`, `border`, `divider`).
    - **Selection & highlights:** `selection: SelectionColors` (item/list selection) and `text_selection: SelectionColors` (inline text), each `{ background, foreground, unfocused_background, unfocused_foreground }`, plus `find_highlight` and `scrim` (modal backdrop dimming).
    - **Global semantic roles:** `accent` (`fill`, `foreground`, `standalone`), `focus_ring`, `caret`, `link`, `link_visited`, `disabled_opacity`.
    - *Con:* Does not expose every vendor-internal brush token by upstream string name; acceptable because every visible control uses those internal tokens directly in its compiled widget `RuleSet`, keeping the public color API 100% typed and portable.
    - **No model inheritance:** Platform builders compute every role directly, retiring `docs/inheritance-rules.toml` permanently.
- **Status roles (`error`, `warning`, `success`, `info`, each `{ fill, foreground, standalone }`) — options weighed:**
  - *Option A (`Option<StatusColors>` when a platform lacks a named token):* Forces every connector (`iced`, `gpui`, `egui`) and portable app to invent inconsistent fallbacks (the exact trap `v0.8.0-rc1` reversed twice in D6).
  - *Option B (Always-present concrete `StatusColors` tagged `origin: RoleOrigin::{Native, SystemColor, Harmonized}` — **chosen**):* Platforms with dedicated tokens (`adwaita`, `kde-breeze`, `windows-11`) use them (`Native`); `macos-*`/`ios-*` use Apple's own `systemRed`/`systemOrange`/`systemGreen`/`systemBlue` (`SystemColor`); `material-3` uses its native `error` role and Material 3's documented HCT `harmonize` rule toward primary for `warning`/`success`/`info` (`Harmonized`). Portable apps never unwrap; connectors never invent arbitrary defaults; provenance stays 100% transparent.

### D6 — Typography, Font Matching, Icons, Window Chrome, and Layout Metrics

- **Typography (`Typography`, `C18`) — options weighed:**
  - *Platform-keyed text style map (`v0.8.0-rc1`):* Preserves vendor names (`bodyLarge`, `largeTitle`), but prevents portable code from naming a heading or caption without mapping tables.
  - *Typed 11-slot semantic ramp + shared platform metadata (**chosen**):* Slots (`display`, `title1`..`title4`, `headline`, `body`, `callout`, `subheadline`, `caption`, `monospace`), each a lean `TextStyle` (`family: Arc<str>`, `color: Color`, `size_px`, `weight`, `style`, `width`, `line_height`, `letter_spacing`, `optical_size`, `decoration`, `blend_mode`), paired with shared platform-level `fallbacks: Arc<[Arc<str>]>`, `emoji_family: Arc<str>`, `rendering: TextRendering` (`antialiasing`, `hinting`, `subpixel_order`, `smoothing`), `font_dpi: f32`, and `font_whole_pixels: bool` (Qt/KDE).
  - **`font_dpi` vs `text_scale`:** Point-stated sizes convert to logical pixels via `font_dpi` (72 on Apple, 96 default on Windows/Linux, or KDE's forced font DPI / `Xft.dpi` from `SystemOverrides`) *before* `ctx.text_scale` applies — preventing pixel-stated fonts from scaling wrongly. `ctx.text_scale` applies linearly on GNOME/Windows, via `android_non_linear::FontScaleConverter` on Material 3, and via the nearest Apple Dynamic Type category on macOS/iOS; when a live OS reader supplies already-scaled font sizes, `theme.context()` reports `text_scale = 1.0` so nothing scales twice.
  - **System font resolution (`fonts.rs` / `system-fonts` feature):** Preserves `0.7.2`'s proven `fonts::select_face` (CSS Fonts Level 4 §5.1–§5.2 matching, upgraded to match `width` from `C18`), `fonts::system_face` (including macOS Core Text lookup for `"SF Pro"`/`"SF Mono"`), and `fonts::substitute_family` (fontconfig).
- **Icons, animated spinners, and control glyphs (`C13`, `C19`) — options weighed:**
  - *Retire `AnimatedIcon` vs keep `AnimatedIcon` + `spinners.rs`:* Keeping **`AnimatedIcon` (`Frames` / `TransformAnimation`) and `load_icon_indicator` (`spinners.rs`)** is essential because `gpui` cannot rotate raster/BMP images, `iced`'s pixel rotation produces noisy edges on high-viewBox SVGs, and freedesktop icon themes ship animated `process-working` strips. The `spinner` widget complements `AnimatedIcon` with vector spinner diameter/stroke/color/period tokens.
  - *Runtime AppKit offscreen control rendering (`v0.8.0-rc1` R11) vs measured glyph tokens:* Rendering `NSButton` checkboxes/arrows at runtime requires main-thread AppKit calls, breaks cross-OS previews, ignores custom accents/palettes, and adds bitmap caches. Measuring exact glyph geometry/stroke/color on widget parts (`checkbox.checkmark`, `radio.dot`, `expander.arrow`, `combo_box.chevron`) + preserving `icons`, `freedesktop`, `sficons`, `winicons`, `rasterize`, and **`native-theme-build`** (upgraded from `Rgba` to `Color`, adding `IconStyle` and `IconRole::mirrors_in_rtl()`) works on every platform and thread.
  - **`ResolvedTheme.icons` (`IconThemeSpec`):** Carries the resolved `set: IconSet`, scheme-matched `theme: Option<Arc<str>>` (e.g., `"breeze"` vs `"breeze-dark"`), and context `sizes: IconSizes` (toolbar, small, large, dialog, panel) so connectors load platform icons consistently.
- **Window chrome (`WindowChrome`, `C20`) — options weighed:**
  - *Put `maximized`/`fullscreen`/`tiled_edges` in `ThemeContext`:* Forces re-resolving every widget whenever a user maximizes or snaps a window.
  - *Dedicated `WindowChrome::frame(WindowState)` query (**chosen**):* Keeps window snap/maximize O(1) with zero re-resolve (while active/inactive comes solely from `ThemeContext::window_active` so chrome, traffic lights, and controls stay coherent), accurately providing title bar geometry/fills, caption/traffic-light button styles & layout order, window corners/border/shadow, and per-edge tiled corner suppression (modal backdrop dimming lives once on `ColorRoles::scrim`).
- **Layout & pointer metrics (`LayoutMetrics`, `C26`, `C22`):** Global `widget_gap`, `container_margin`, `window_margin`, `section_gap`, `cursor_size_px`, `cursor_theme`, and RTL direction via `ThemeContext::direction` (`resolve()` returns physical left/right geometry/corners/strokes for the active direction so connectors never double-mirror). Widget-specific conventions live once on their owning widgets (`DialogWidget::button_order`, `TabWidget::indicator_side`, `ExpanderWidget::arrow_side`) with zero duplicated fields. (Tooltip/popover auto-flip placement math stays in toolkits or an optional `0.8.x` pure helper.)

### D7 — Declarative Motion, Caret, and Visible Timings

- **Motion representation — options weighed:**
  - *Option A (No motion data, `0.7.2` except dialog entrance):* Misses `C14` and `C21`; connectors hardcode arbitrary durations.
  - *Option B (13 platform animation/scroll-physics engines + per-property transition maps, parked `v0.8.0-rc1`):* Massive core complexity for frame loops GUI toolkits already own.
  - *Option C (Declarative `MotionTokens` + single `Option<Transition>` per `PartStyle` + `CaretSpec` + `UiTimings` — **chosen**):*
    - `Transition { duration_ms: u32, delay_ms: u32, timing: Timing }`, where `Timing` covers `Linear`, `CubicBezier(f32, f32, f32, f32)`, `Spring { mass, stiffness, damping }`, `Steps(u16)`, plus tiny pure-math named curves (`SineInOut`, `ExpoOut` — 3 lines each for Qt/libadwaita curves that are not exact cubic Béziers).
    - `MotionTokens` holds platform standard/fast/emphasized/spring presets and `theme_change` policy (while `dialog_entrance` lives once on `DialogWidget`).
    - Under `ctx.motion == MotionPreference::Reduced` or `None` (or `SystemOverrides::animation_scale`), `resolve()` automatically scales or collapses/replaces transitions per each platform's policy.
    - `CaretSpec` (`C16`: color, width, blink on/off/timeout, shape) and `UiTimings` (`C21`: tooltip show/hide/reshow, double-click interval, drag threshold, scrollbar auto-hide, menu hover-open delay, key repeat).
    - *Con:* Parts with two simultaneously differing property durations (rare) use the primary part transition plus `MotionTokens`; toolkits drive their own interpolation and scroll fling physics.

### D8 — First-Class Customized and Fancy Themes

- **Customization architecture — options weighed:**
  - *Option A (497-line preset TOMLs per community theme, `0.7.2`):* Massive geometry duplication; community themes look non-native on every OS.
  - *Option B (General layered rule-DSL with expression VM, `v0.8.0-rc1`):* Overcomplicated and still banned palettes on macOS/iOS due to literal facts.
  - *Option C (Three progressive tiers over only 3 public concepts — `Theme`, `Palette`, `ThemePatch` — **chosen**):*
    1. **Tier 1 — Color-Only `Palette` (~20–25 colors + `scheme: Scheme`):** Bundled community palettes (Catppuccin Latte/Frappé/Macchiato/Mocha, Dracula, Nord, Solarized Light/Dark, Tokyo Night, Gruvbox Light/Dark, One Dark) shrink from 497 lines to ~30 lines each, retiring `0.7.2`'s invented light variants of dark-only schemes. Applied over *any* platform preset (including macOS/iOS, where semantic palette mapping replaces Apple's literal colors while preserving Apple geometry/materials), the platform builder derives coherent hover/pressed/disabled/focus/inactive/material-tint colors automatically.
    2. **Tier 2 — Declarative `ThemePatch` (Rust builder, or external TOML/JSON via `Theme::from_toml` when the `toml`/`serde` feature is enabled):** Standalone theme files (`Theme::from_toml`) specify `base = "auto" | "<preset>"` (`"auto"` picks `Preset::detect()` with zero OS reader I/O; live OS overrides use `Theme::from_system()?.with_patch(...)`), optional `name`, single `palette` (name or inline `[palette]` table) or dual `[palettes]` (`light` + `dark`), and `accent`, plus the base-independent `ThemePatch` fields: overrides to `colors`, `typography`, `metrics` (`corner_scale`, `spacing_scale`), any widget's base/state rules (using `PartProp`/`TextProp`/`IconProp`, including multi-layer `Paint`s; static widget style parts accept unconditional overrides), and optional `custom_colors` / `custom_metrics` (`BTreeMap`, empty/zero-alloc on built-ins) for app-specific fancy tokens. External deserialization (`from_toml`) and `ThemePatch::validate()` strictly reject invalid values (non-finite floats, negative sizes, opacity outside `0.0..=1.0`, state selectors on static widgets) with `Result<_, Error>`, while infallible Rust builder methods clamp/sanitize out-of-range floats so `Theme::resolve()` never panics or propagates `NaN`.
    3. **Tier 3 — Programmatic Rust (`with_transform` / `ThemeSource`):** Either a post-resolve closure `theme.with_transform(|resolved: &mut ResolvedTheme| { ... })` (stored as `Arc<dyn Fn(&mut ResolvedTheme) + Send + Sync>`) or implementing `ThemeSource: Send + Sync` directly for algorithmic/generative or zero-`serde` design systems.
- **Palette × Scheme mismatch — options weighed:**
  - *Silently apply a dark palette under `Scheme::Light`:* Broken — light-mode derivation rules (shadows, translucent overlays, contrast direction) run over dark colors.
  - *Silently drop the palette on mismatch (`v0.8.0-rc1` R19):* Surprises apps calling `.with_palette(Palette::dracula()).resolve_current()` on a light OS.
  - *Explicit single-scheme lock + dual-scheme pairing (**chosen**):* `.with_palette(p)` locks the effective color scheme during `resolve()` to `p.scheme` (also updating `resolved.context.scheme` and `resolved.icons.theme` accordingly) so a dark-only palette always renders coherently with dark-mode platform rules; `.with_palettes(light, dark)` tracks `ctx.scheme` automatically across OS light/dark transitions (and `.with_palette_for(scheme, p)` enables single-slot opt-in). Under `Contrast::High`, palettes suspend automatically to preserve OS accessibility colors unless explicitly opted out.
- **Custom accent derivations across platforms:** On `kde-breeze`, `.with_accent(c)` runs clean-room `kde_accent` (`applyScheme()`); on `material-3`, `m3_role` HCT; on `adwaita`, `adw_standalone` OKLab; on `windows-11`/`macos-*`/`ios-*` (whose vendor accent ramp formulas are unpublished), live OS reads preserve the exact WinRT/`NSColor` ramp, while explicit `.with_accent(c)` or a `Palette` computes a clearly documented perceptual OKLCH ramp so accent customization works coherently on all 8 presets.
- **Unambiguous 4-step layer precedence:**
  1. Base `Preset` / `ThemeSource` (platform geometry, rules, derivation formulas).
  2. Live `SystemOverrides` (OS fonts, DPI, timings, accessibility defaults, and scheme-matched OS colors).
  3. Explicit `Palette` (3a), then explicit `.with_accent(...)` (3b — overriding the palette's default accent, e.g., Catppuccin Mocha + Pink). Both replace color inputs *before* platform derivations run so every hover/pressed/disabled/inactive state derives harmoniously while keeping live OS fonts, DPI, timings, and accessibility flags.
  4. `ThemePatch`es (appended after preset rules in stated order) and `with_transform` hooks, applied last onto the resolved output. *(Use `Palette`/`.with_accent()` when you want platform state derivations to recompute automatically; use `ThemePatch` for direct concrete overrides — where your rules win without flashing back to preset state colors, and you can pair base and state rules directly.)*

### D9 — Live OS Readers, Platform Detection, and Watchers

- **Separating detection from live reading — options weighed:**
  - *Option A (`0.7.2`'s asymmetric `from_system()`):* Silently returned a static preset on Linux without reader features while returning an error on macOS/Windows.
  - *Option B (Explicit separation — **chosen**):*
    - `Preset::detect()` / `Theme::for_current_platform()`: infallible on all targets (including WASM and headless CI), zero reader features needed, detects OS generation (`OsVersion`) or Linux DE (`XDG_CURRENT_DESKTOP`) and returns the matching bundled preset.
    - `Theme::from_system()`: requires the platform's reader feature (`native`, or `kde`/`portal`/`macos`/`windows`), reads live OS settings into a detected `ThemeContext` plus a typed **`SystemOverrides`** struct — separating scheme-independent settings (fonts, `font_dpi`, `text_rendering`, `animation_scale`, caret blink / timings, accent + Windows ramp, non-fatal `diagnostics` for partial fallbacks like a missing KDE `.colors` file) from **context-scoped `(Scheme, Contrast)` color slots** (macOS populates Light/Dark × Normal/Increased Contrast `NSColor`s, while KDE/Windows populate only the active OS `(Scheme, Contrast)` so toggling `ctx.scheme` in-app falls back cleanly to the preset's opposite-scheme colors instead of painting Light `kdeglobals` colors over `Scheme::Dark`) — and returns a clear `Error` if the feature is off or reading fails.
    - `Theme::from_system_or_default()`: 1-line infallible fallback to `Theme::for_current_platform()`.
- **Sync vs async `from_system()` — options weighed:**
  - *Async `Reader` trait + `async-trait` + global `pollster` (`0.7.2`):* Pulls `syn`/`quote`/`proc-macro2` (`async-trait`) and `pollster` into every build even though macOS, Windows, and KDE readers are 100% synchronous and the public API itself is synchronous.
  - *Synchronous public API & `ThemeReader` trait, isolating `pollster::block_on` strictly inside the `portal` feature (**chosen**):* Eliminates `async-trait` globally and removes `pollster` from non-portal builds. *Con:* Async apps wanting non-blocking portal reads run `from_system()` on a blocking pool thread — already best practice for OS filesystem/registry/AppKit reads.
- **No dropped OS preferences:** `Theme::from_system()` exposes `theme.context()` (pre-populated with live OS `scheme`, `contrast`, `motion`, accessibility flags, `text_scale`, and `overlay_scrollbars`) and one-call `theme.resolve_current()`. Re-resolving with a tweaked context (`theme.context().with_window_active(false)`) preserves every live OS setting.
- **Watchers & mobile readers:** Preserves feature-gated `watch::on_theme_change` (debounced, signal-only `ThemeChangeEvent::Changed`) for live desktop updates, automatically invalidating `detect` caches before invoking the callback so re-reading `Theme::from_system()` never sees stale cached state. Native iOS/Android readers remain a clean post-`0.8.0` addition; until then mobile apps supply `SystemOverrides` directly.

### D10 — Performance, Binary Size, Dependencies, and Safety

- **Hard engineering targets** (verified by fast `cargo test` size/timing checks):
  - `Theme::resolve(&ctx)`: **< 1 ms** (target **< 0.5 ms**).
  - Widget part query: **< 100 ns**, zero heap allocations.
  - `ResolvedTheme` memory footprint: **< 256 KB** for all widgets combined.
  - Compiled size of all 8 bundled presets: **< 150 KB** total.
- **Dependency pruning:**
  - **Removed from `native-theme`:** `native-theme-derive` (proc-macro), `inventory` (registry), `serde_with` (proc-macro), `async-trait` (proc-macro), and `arc-swap` (replaced in `detect.rs` with `std::sync::RwLock`, also dropping `rustversion`).
  - **Retained / gated:** `unicase` (zero transitive dependencies, needed for CSS Fonts Level 4 caseless matching in `fonts.rs`); `pollster` (zero transitive deps, gated behind `portal` only); hand-written `u32` `WidgetState` bitflags (zero deps).
- **Default Cargo features — options weighed:**
  - *Option A (`default = ["palettes", "serde", "toml"]`):* `Theme::from_toml()` works with zero feature flags, but pulls `serde_derive` (`syn`/`quote`/`proc-macro2`) and `toml` into every app that only uses native presets and Rust builders.
  - *Option B (`default = ["palettes"]`; `serde`, `toml`, and OS readers opt-in — **chosen**):* Matches `egui`, `glam`, `uuid`, `chrono`, and `url` (and `0.7.2`'s opt-in `native`/`kde`/`portal`/`macos`/`windows` reader features). Because bundled presets, palettes, and Rust `ThemePatch` builders need zero parsers, default builds compile with **zero proc-macros and 1 tiny dependency (`unicase`)**. Apps loading live OS settings enable `features = ["native"]` (or per-OS features), and apps loading external `.toml`/`.json` theme files enable `features = ["toml"]` or `features = ["serde"]`. *Con:* Requires opting into `toml` for file-based custom themes; easily documented on `Theme::from_toml`.
- **Safety & hygiene:** Keeps `#![warn(missing_docs)]`, `#![deny(clippy::unwrap_used)]`, `#![deny(clippy::expect_used)]`, and `#![deny(unsafe_code)]` at crate root, with localized `allow(unsafe_code)` + `// SAFETY:` comments strictly confined to OS FFI reader/icon/font/watcher modules (verified by `tests/unsafe_safety_comments.rs`).

### D11 — Factual Rigor, Verification, and Licensing

- **Verification strategy — options weighed:**
  - *Option A (66 MB machine-parsed `docs/facts/` + Python codegen + 7.65 h combinatorial gate):* Unmaintainable runtime and token burn.
  - *Option B (Untracked manual values):* Risks drift and invented numbers.
  - *Option C (Inline source citations + compiled golden vector tests + targeted OS probes — **chosen**):* Every native constant/formula carries a concise inline citation (`// libadwaita 1.10.0 _buttons.scss:20`, `// Breeze 6.8.2 breezehelper.cpp:670`, or `// os-probe macOS 26`); every derivation algorithm runs fast golden vector tests in `cargo test` generated by `tools/*-vectors`; Apple/WinUI values are checked against `tools/os-probe` outputs and pinned upstream commits (`sources.toml`). *Con:* Does not exhaustively re-verify every static pixel constant against an automated 7.65 h matrix; mitigated by golden formula vector tests, automated invariant tests (contrast, finite/non-negative geometry, non-empty fonts), and showcase visual checks.
- **Licensing (preserving `v0.8.0-rc1` D10):**
  - Core code: `MIT OR Apache-2.0 OR 0BSD`.
  - LGPL/GPL references (Qt/KDE `KColorScheme`, `KColorUtils`, `QColor::lighter`, `QFont`, GTK/Pango, libadwaita): strict clean-room Rust verified against black-box test vectors.
  - Apache-2.0 ports (`material-color-utilities` HCT, AOSP non-linear font scaling) and MIT port (`microsoft-ui-xaml` text curve) stay in clearly marked files with upstream notices and `native-theme/NOTICE` (no `ripple.rs` engine port). Only `native-theme/Cargo.toml` overrides `license = "(MIT OR Apache-2.0 OR 0BSD) AND Apache-2.0 AND MIT"`; the workspace root (`native-theme-build` and connectors) keeps `MIT OR Apache-2.0 OR 0BSD`.

### D12 — Connector Architecture and Long-Term Stability

- **Connector integration model — options weighed:**
  - *Global theme-struct mapping only:* Loses per-widget states/variants/parts (`egui::Visuals` alone cannot express pill primary buttons vs standard buttons).
  - *Per-widget queries only:* Forces redundant queries for global colors/typography/spacing.
  - *Hybrid (`ResolvedTheme` globals + zero-alloc per-widget queries — **chosen**):* Connectors (`native-theme-iced`, `native-theme-gpui`, `native-theme-egui`, `native-theme-egui-widgets`) populate global toolkit theme structs from `resolved.colors`/`typography`/`layout`/`icons` and style individual widgets cleanly via `resolved.<widget>.<part>(query)` — no DOM emulation, no `FontMetrics` callback.
- Where a toolkit cannot yet draw a property (e.g., backdrop blur material, multi-layer shadows, or spring transitions), the connector uses the structured fallback (`material.fallback`) and notes the toolkit limit concisely in its README. As upstream toolkits improve, connectors simply read fields already present on `PartStyle` with **zero breaking changes to `native-theme`**.
- **Lean connector verification:** Replace brittle line-number-citing parity prose with focused mapping accuracy tests, contrast/sanity invariants, and showcase smoke/visual tests.

### D14 — API Preview, SemVer Longevity (`0.8.0` → `1.0`), and `C01`–`C28` Disposition

**Exhaustive vs `#[non_exhaustive]` boundary:** Fixed math, bitflag, and closed-domain value primitives (`Color`, `Edges`, `Paint`, `Stroke`, `StrokeSide`, `Corners`, `GradientStop`, `ShadowLayer`, `Transform`, `Transition`, `WidgetState`, `EdgeFlags`, `Scheme`, `Direction`, `Orientation`, `ButtonKind`, `ListKind`, `RoleOrigin`, `WidgetOrigin`, `DialogButtonOrder`, `ArrowSide`, `TabIndicatorSide`, `WindowsAccentRamp`) are **exhaustive** so callers construct and match them directly without ceremony. Extensible theme, style, query, selector, config, and error structs/enums (`ResolvedTheme`, `ThemeContext`, `StyleQuery`, `RuleSelector`, `ColorRoles`, `SurfaceColors`, `SelectionColors`, `Typography`, `TextRendering`, `IconThemeSpec`, `LayoutMetrics`, `UiTimings`, `MotionTokens`, `CaretSpec`, `WindowChrome`, `PartStyle`, `TextStyle`, `IconStyle`, `MaterialSpec`, `SystemSnapshot`, `SystemOverrides`, `Error`, and all variant/shape/kind/prop enums) are **`#[non_exhaustive]`** with builder methods so `0.8.x` → `1.0` can add widgets, variants, states, and visual fields non-breakingly.

```rust
// 1. Live OS theme (`features = ["native"]`; falls back cleanly to detected preset if off/headless)
let theme = Theme::from_system_or_default();
let resolved = theme.resolve_current();
let bg = resolved.colors.window.background;
let is_dark = resolved.is_dark();

// Common 80% query — pass WidgetState directly:
let cb = resolved.checkbox.indicator(WidgetState::CHECKED | WidgetState::HOVER);
let hovered_btn = resolved.button.body(WidgetState::HOVER);

// Full orthogonal query when variant/shape/size/surface matters:
let pill_cta = resolved.button.body(
    ButtonQuery::primary()
        .pill()
        .size(ControlSize::Large)
        .state(WidgetState::HOVER),
);

// Re-resolve for an inactive window without losing live OS settings:
let inactive = theme.resolve(&theme.context().clone().with_window_active(false));

// 2. Native platform geometry + bundled community palette (single-scheme or auto light/dark pair)
let mocha = Theme::preset(Preset::MacosTahoe)
    .with_palette(Palette::catppuccin_mocha())
    .resolve_current();
let adaptive = Theme::from_system_or_default()
    .with_palettes(Palette::catppuccin_latte(), Palette::catppuccin_mocha())
    .resolve_current();

// 3. Fancy custom theme from TOML (`features = ["toml"]`; `base = "auto"` uses Preset::detect(), zero I/O)
let custom = Theme::from_toml(include_str!("neon-glass.toml"))?;
let resolved = custom.resolve(&ThemeContext::dark());

// 4. Programmatic tweak on top of the live OS theme
let tweaked = Theme::from_system()?
    .with_accent(Color::from_hex("#7b2ff7")?)
    .with_patch(ThemePatch::new().corner_scale(1.25))
    .resolve_current();
```

**`C01`–`C28` Gap-Map Disposition:**

| Capabilities | Disposition in `v0.8.0` |
|---|---|
| `C01`–`C08` (shadows, elevation, materials, color composition, color roles, variant axes, states, state layers/ripple) | **Core** (D3, D4, D5, D7; declarative ripple only, no shader engine) |
| `C09`–`C13` (variants, control sizes/density, corners/curves, strokes, multi-part widgets) | **Core** (D3, D4, D6; Material Expressive polygon morphs deferred to `0.8.x`) |
| `C14`–`C17` (motion, focus indication, text caret, selection & highlights) | **Core** (D3, D4, D5, D7; declarative motion only, no runtime/fling engines) |
| `C18`–`C23` (typography/font matching, icons/spinners, window chrome, timings, pointer, accessibility variants) | **Core** (D3, D4, D6, D7; no runtime AppKit offscreen widget rendering) |
| `C24` (new controls beyond `0.7.2`) | **`radio` + `menu_bar` in `0.8.0`**; remaining controls incrementally in `0.8.x` via `#[non_exhaustive]` (D1) |

| `C26`–`C28` (layout/RTL, gradients, extended-sRGB / Display P3) | **Core** (D3, D4, D6; popup auto-flip placement math stays in toolkits or optional `0.8.x` helper) |
